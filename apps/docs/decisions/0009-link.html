Jig · decision 0009

Link

Jig has no link. Adding one has to answer what a link is in a system whose only interactive vocabulary is Button's — and how a component that must render an <a> reaches a recipe written for a <button>.

  • Built
  • 2026-08-28
  • 6 decisions

01Context

Nothing in Jig renders a standalone anchor today. The only link styling in the system is internal to Token — linkToken and labelLink in packages/components/src/token/token.css.ts — and both exist to serve a pill, not to be reused. A consuming app that wants a link writes its own <a> and picks its own colour.

The sharing half of the request is already a solved shape. Button's recipe is not private: IconButton and ToggleButton both import { button } from '../button/button.css' and call it with color, size and iconOnly. That is the established route to “looks like a Button”, and a third caller is not a new pattern. The recipe's base is close to element-agnostic — appearance, border, display: inline-flex, padding, radius, and focusRing — all of which an <a> wears without complaint.

Two parts of it do not transfer. :disabled never matches an anchor, so every disabledBg and disabledText in the recipe is dead weight on a link. And cursor: pointer is set in the base because a <button> does not get one by default; an <a href> already does.

Worth stating plainly, because it constrains every option below: a link is not a button. <a href> activates on Enter alone, <button> on Enter and Space; assistive technology announces “link” against “button”, and users decide whether to middle-click, copy the target or open a new tab on that announcement. So the question here is only ever about appearance. Whichever options are accepted, a navigation control renders an anchor with a real href.

One live dependency: Button gained a fifth variant, smoke, immediately before this document. Anything that shares the recipe inherits it, and inherits the next one too — which is an argument for sharing and a reason to be careful about what the shared surface promises.

Already settled by precedent

Everything here follows an existing rule and is not up for debate in this document. Listing it is what keeps the decision count honest.

  • No as prop. Polymorphism stays on layout and typography components, via PolymorphicProps in packages/components/src/polymorphic.ts. Link renders an anchor, full stop.
  • size is sm | md | lg, the same union as ButtonSize.
  • Icons come from the curated set as icon plus iconPosition, exactly as Button declares them, and are sized by the component through buttonIconSize — never by the caller.
  • Focus is the shared focusRing, not a border highlight. Link draws no border of its own, which is the test 0002 D4 set.
  • No spacing props. Spacing comes from the parent Stack or Grid; box dimensions go through style.
  • The ref forwards and is typed HTMLAnchorElement. refs.test.tsx enforces it.
  • Ships the five-file set — link.tsx, link.css.ts, link.stories.tsx, link.test.tsx, index.ts — plus an export from packages/components/src/index.ts.
  • No new primitives, and no new colour ramp. Corrected 2026-08-28: this originally read that a text link's colour “already exists as color.text.accent”. D3 came back saying the text variant should inherit its colour from the parent, under which it needs no colour token at all — and color.text.accent keeps the consumers it already had rather than gaining one.
  • Theming stays :root-scoped.
  • No disabled link is offered in any option below. An anchor without href is not focusable or activatable, and :disabled does not match one. A control that can be turned off is a Button; a link that should not be followed is not rendered.

02Decisions

Accept one option per decision, or reject the whole set and leave a note. Notes are the refinement channel — partial acceptance goes there in plain English.

Settled over two rounds. D1, D2 and D4 were accepted first. D3 came back open with a note that made the underline a prop and the type inherited; it was rebuilt, and the two questions the note opened became D5 and D6. All six are now decided, and every option is kept — including the ones not taken and the original D3 that was replaced — because the reasoning is the point of the record. The resulting API is §03.

D1 · link-shape

What visual vocabulary Link offers

The request is for a link that can look like a button. The open question is whether it also covers the ordinary underlined link in a sentence — the thing most people mean by “Link” — and if so whether one component carries both or two components split them.

D2 · style-reuse

How Link reaches Button's styles

“Inherit or share the button styles” has three plausible mechanisms, and they differ in what happens the next time Button changes — which, on the evidence of smoke landing last week, is soon.

  • Zero new machinery. This is the existing pattern, and the third and fourth callers cost nothing that the second did not.
  • Button's variants stay in one place. A retune of color.button.* or a sixth variant reaches Link without anyone remembering to update it.
  • One stylesheet rule per variant, shared across four components — the recipe is emitted once. stylesheet.test.ts already guards against duplication here.
  • Link inherits the recipe's dead weight: four :disabled declarations per variant that can never match an anchor, and a cursor: pointer the anchor already had.
  • Couples Link to Button's variant union. Deliberate, but it means Button can no longer add a variant without asking what it means on a link.

Decided · 2026-08-28 Import the recipe, as its siblings do. link.tsx imports button and buttonIconSize from ../button/button.css and becomes the fourth caller of a recipe that three components already share.

One consequence follows from D3's note and is worth writing down before it is built: the text variant must not call the recipe at all. The recipe's base sets a font size, a font family, padding, a radius and display: inline-flex — every one of which contradicts a link that inherits its type from the parent, and inline-flex would stop it wrapping mid-sentence. So variant="text" takes a separate rule in link.css.ts and only the five box variants go through button(). The decision to share still stands; it shares across five variants rather than six.

D3 · text-link-type · revised

Where the text variant's type comes from

Reopened · 2026-08-28 The original D3 was left open. It offered three fixed treatments — accent or inherited colour, crossed with underline always or on hover. The note rejected the frame rather than the options:

“underline should be a boolean prop, and the base styles of the type should inherit from the parent element. if it's easier or better to have Link inherit the Typography props directly, that would be great. external should also be a prop, which would place an icon to the right of the text.”

That settles two things and opens three. Settled: the underline is a prop, not a fixed treatment, so “always or on hover” is no longer a question the system answers on the caller's behalf; and the text variant takes its colour from the parent rather than from color.text.accent. Reopened below is how far “inherit from the parent” goes — colour only, or the whole type ramp, or Typography's props outright — which is the part the note flagged as worth choosing rather than assuming. The underline default is now D5 and external is now D6.

One correction to the document's own argument, not just to this decision: the settled list claimed a text link's colour “already exists as color.text.accent”. Under an inherited colour it does not need a token at all, and color.text.accent keeps the consumers it already had. §01 is corrected.

Given that the text variant inherits, the open question is how much. “Colour” and “the type” are different amounts of inheritance, and the second interacts with size: a sm | md | lg ramp is meaningful for the five box variants and means nothing for a link whose size comes from its surroundings.

Each specimen puts the same link in three contexts — body copy, a heading, and a caption — because that is where the options differ. Judge them on whether the link looks like it belongs to the text around it.

Decided · 2026-08-28 Inherit, plus with. The text variant declares no colour, family, size or weight of its own and takes them from whatever encloses it; with names a Typography preset for the standalone case.

The precedence the option left open is now settled: an explicit with wins. That was this option's one named cost — “nothing says which wins when both are present” — and accepting it means answering it. A prop the caller passed at the call site beats an ambient value it did not, which is the only reading under which with is usable at all. Absent with, nothing is declared and inheritance does the work.

Two consequences for the build. size does nothing on variant="text": its type comes from the parent or from with, never from the sm | md | lg ramp, which stays meaningful only for the five box variants. And with is the only prop borrowed from Typography — not balance, not the spacing props, not as. A Link is an anchor and takes its spacing from its parent.

D4 · router-integration

How a consumer swaps in their router's link

Most apps that would use this do client-side routing, where a bare <a href> triggers a full page load. Jig cannot depend on a router, so the component needs a way to hand its markup to one — or a decision that it will not.

This is the one place as would normally be reached for, and it is unavailable: polymorphism stays on layout and typography components. So the options are the ones that do not widen that rule.

A render prop

Recommended

Backed by useRender from @base-ui/react@1.7.0 — a public export

next/link
<Link
  href="/docs"
  variant="primary"
  render={<NextLink href="/docs" />}
>Docs</Link>

react-router
<Link render={<RouterLink to="/docs" />}>

already in the codebase
togglebutton.tsx uses Base UI's
render callback for the same job
  • Base UI is already the foundation (0001) and useRender is a documented public entry point at @base-ui/react/use-render in the pinned 1.7.0 — verified against the registry, not from memory. No new dependency.
  • Merges rather than overwrites: className strings are joined and handlers composed, so Jig's classes and the router's onClick both survive. Hand-rolled cloning gets this wrong.
  • One prop name that will be right for every future component with the same problem, and ToggleButton already exposes the concept internally.
  • A second way to spell the element, sitting next to the as rule and looking like an exception to it. Needs the docs to say why it is not one.
  • The caller writes the target twice — once as href for Jig, once on the router's element.

  • Honest about what is being shared: this decision is entirely about appearance, and a class name is appearance.
  • Everything the component does beyond styling is lost — icon rendering and sizing, and any external-link handling — so the caller rebuilds it and gets it slightly wrong.
  • Publishes the recipe's call signature as public API. Renaming a variant becomes a breaking change for consumers who never rendered a Jig component.

Nothing — a plain anchor

Link always renders <a href>; routing is the app's problem

<Link href="/docs">Docs</Link>
  → <a href="/docs">   full page load

the app's own wrapper, once

  return <NextLink
    href={props.href}
    legacyBehavior passHref>
    <Link {...props} />
  </NextLink>;
}
  • Smallest possible surface, and it is the correct component for the many links that really are external or cross-document.
  • Defers a decision that a real consumer's routing setup would inform better than this document can.
  • Every app writes the same wrapper, and the wrappers rely on router-specific escape hatches — legacyBehavior is deprecated in Next's App Router, so the recipe rots.
  • The failure is silent and slow: a link that works but does a full reload looks fine in review and is found in a performance audit months later.
Decided · 2026-08-28 A render prop, backed by useRender from @base-ui/react@1.7.0.

The cost the option named stands and needs answering in the docs: as is refused on every component and render is accepted here, which looks like an exception. It is not one. as asks the component to be a different element and pick up that element's prop types; render hands the component's own props and classes to an element the caller has already constructed. Link is always an anchor either way.

D5 · underline-default · new

What the underline prop defaults to

The note settles that the underline is a boolean prop rather than a fixed treatment, so the system no longer decides always-or-on-hover for the caller. What it still has to decide is the default — and what false means, since with an inherited colour (D3) the underline is the only thing left distinguishing a link from the text around it.

That is the whole weight of this decision. Under the original D3 an un-underlined link still had the accent to fall back on; under an inherited colour it has nothing.

Decided · 2026-08-28 Defaults true; false means never. A text link is underlined unless the caller turns it off, and turning it off removes the underline in every state rather than deferring it to hover.

The cost is accepted with it: nothing stops underline={false} being used in running text, where — with D3's inherited colour — it produces a link with no visual distinction at all. The prop trusts the caller, and the place it is meant for is somewhere the link is already obviously a link: a nav row, a breadcrumb, a card that is entirely a target.

Scope, which the decision implies rather than states: underline belongs to variant="text". The five box variants take their whole appearance from the button recipe, which draws a filled or ghosted box and no text decoration; an underline inside one would be a second affordance on a control that already reads as pressable. So link.css.ts sets text-decoration: none on the box variants and underline has no effect there. Flagged rather than assumed — say so if the intent was for it to apply across all six.

D6 · external-affordance · new

What the external prop does

The note asks for external to place an icon to the right of the text. That settles the glyph and its position — arrow-square-out from the curated set, at the end — and leaves what else the prop is responsible for. The candidates are target="_blank", rel, and an announcement for assistive technology, and they are not one bundle: a link can leave the site without opening a tab, and opening a tab is the part a user notices.

There is also a collision to resolve. Link takes icon and iconPosition from Button's vocabulary (D1), and external wants the same slot. Each option below says how it lands.

Marker and rel

Recommended

The glyph means “this leaves the site” — which is true whether or not a tab opens

Built on Base UI, and released under MIT.

Read the RFC

works on the text variant and the box variants alike

  • Says only what it knows. The glyph marks a destination outside the app; whether to hand the user a new tab is a judgement about their task, which the call site has and the component does not.
  • rel="noopener noreferrer" costs nothing and closes a real hole when the caller does add target="_blank" and forgets it — the common mistake, prevented without taking the decision away.
  • Resolves the collision cleanly: external owns the end slot, so passing iconPosition="end" alongside it is a type error, and icon with the default start still works — a glyph at each end is a legitimate thing to want.
  • A caller who wants a new tab writes target themselves, and then owes the announcement themselves too. The prop helps with the marking and not with that.

Marker, new tab, announcement

One prop for the whole external-link convention

<Link href="https://…" external>

   target="_blank"

  • The announcement matches the behaviour. A link that opens a tab without telling a screen reader user is a real failure, and bundling makes it impossible to get half right.
  • One prop for what most teams write as a four-part snippet, which is the kind of thing a design system is for.
  • Decides on the user's behalf that leaving the site means leaving the page. That is contested as a UX default — it takes the back button away — and it is not what “external” means.
  • A caller who wants the marker without the tab has to abandon the prop and rebuild the icon by hand, losing the sizing the component owns.
  • Needs the visually-hidden text to be translatable, which the component cannot do — so it ships an English string into every locale.

  • Leaves rel="noopener" to be remembered at every call site that adds target="_blank". It is free to add and the omission is a genuine security hole, so declining to add it is a decision to let that happen.
  • Barely earns a prop. If it only renders a glyph, icon="arrow-square-out" iconPosition="end" already does it.
Decided · 2026-08-28 Marker, new tab, announcement. external renders the arrow-square-out glyph after the label and sets target="_blank", rel="noopener noreferrer" and a visually-hidden “(opens in a new tab)” so the announcement matches the behaviour.

Both of the option's costs are accepted rather than solved. The new tab is now the component's opinion, not the call site's — a link that leaves the app takes the back button with it, and a caller who wants the marker without the tab cannot use the prop. The announcement ships as an English string into every locale, because a component cannot reach a translation layer it has no knowledge of. If that becomes a real problem the smallest fix is an override prop for the string; that is a later decision and is deliberately not being added here.

One rule carried across from the option that was not chosen. The collision between external and the inherited icon / iconPosition was spelled out under Marker and rel and not restated here, but it is orthogonal to what separated the three and something has to resolve it: external owns the end slot, so passing iconPosition="end" alongside it is a type error, while icon at the default start still works — a glyph at each end is legitimate. Flagged because it is being carried rather than chosen.

03The API, as decided

04Deliberately not proposed

  • Automatic external-link detection — still not proposed, though the prop it guarded now is. This section originally ruled out external-link handling altogether, adding that “if it is wanted, it should be an explicit external prop”. The note asked for exactly that, so it is D6. What stays out is the detection: sniffing href for a different origin and setting the prop implicitly. Whether a destination counts as leaving the app is a fact about the product — a docs subdomain usually does not — and a URL cannot answer it.
  • A :visited treatment. Browsers restrict what can be styled on :visited, and the system has no token for it. Worth revisiting only for a documentation site, where it earns its keep.
  • A disabled prop. Covered in the settled list: it cannot be made to work on an anchor, and faking it with aria-disabled plus a removed href produces a control that is announced but not reachable.
  • Spacing props on Link. The rule stands — spacing comes from the parent.

What the proposal under-specified

  • Where with's presets come from. D3 said “a Typography preset” without saying whether Link reaches Typography's recipe or restates the values. Neither works as written: the recipe's base sets color: color.text.primary and a font family, so wearing it would defeat the inheritance the same decision asked for — and restating sixteen blocks is the drift D2 was argued on. So the presets were extracted to a shared typeStyles map that carries the four type properties and no colour. That extraction is the one thing here that touched a shipped component.
  • The underline cannot live on the anchor. D5 was written as though underline decorates the link, and the obvious implementation puts text-decoration on the <a>. That underlines everything inside it, including the space in front of the external marker — and an SVG takes no text decoration, so the rule runs a space past the last word and then stops dead. The underline is carried by a span around the label instead, which is also closer to what the prop means. Same structure Token already uses for its own label.
  • The separator before the external marker is load-bearing. The accessible name algorithm concatenates inline elements without a separator and trims each one, so a leading space inside the hidden “(opens in a new tab)” span is discarded and the name comes out as Base UI(opens in a new tab). A non-breaking space is trimmed too — both were tried. It has to be a bare text node in the anchor, which is what ships; on the box variants a whitespace-only text node in a flex container is not rendered, so the Button recipe's gap still owns the spacing there.

A cost D6 did not price

Making iconPosition="end" a type error alongside external requires a discriminated union, and a union breaks prop spreading. A caller who holds a LinkProps-typed object cannot spread it into a <Link> and then set external or iconPosition — TypeScript cannot narrow the spread to either arm. That is not hypothetical: it broke two of this component's own stories, which now destructure the two discriminants out of args before spreading.

Wrapping a Jig component is an ordinary thing to do, so this will be met again. It is recorded rather than fixed because the ban is what D6's outcome settled, and because the alternative — resolving the collision at runtime by letting external win the end slot and rendering icon at the start — is a decision, not an implementation detail. Worth its own proposal if the friction shows up in real use.

Worth a future proposal

  • The English announcement. D6 accepted that “(opens in a new tab)” ships untranslated. Now that it is real, the cheapest fix is visible: an override prop for the string, or a locale-aware wrapper. Neither is added here.
  • Nothing consumes color.text.accent in running text. The token was introduced so emphasised text tracks the primary button's hue, and the text link — its most obvious consumer — inherits instead. It still has consumers, but the original argument for it is now weaker than the document's §01 assumed.
  • A size that means nothing on one variant. variant="text" size="lg" type-checks and does nothing, which D1 and D3 both named. The type could express it — the same union machinery as external — at the same spreading cost. Left alone deliberately.
