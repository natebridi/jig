Slider

The behaviour is settled — Base UI's slider, edge-aligned thumb, optional stepper buttons, optional value bubble while dragging. What is open is how it should look, and three of the four decisions below are visual.

01Context

A slider needs managed focus, keyboard stepping and a full ARIA range contract, so 0001 D2's behaviour test puts it on Base UI. @base-ui/react 1.7.0 ships Slider.Root, Label, Value, Control, Track, Indicator and Thumb, which covers everything except the two things asked for on top: stepper buttons and a value bubble. Both are ours to build.

Base UI sets data-dragging and data-focused on both the root and the thumb, so the bubble in D2 is styled from state the library already publishes rather than from React state of our own — the same rule 0002 D3 settled for Input.

Why the thumb is edge-aligned

thumbAlignment is fixed at edge and is not a prop. The difference only shows at the extremes, which is exactly where it matters:

Already settled

  • Built on Base UI, @base-ui/react at ~1.7.0. 0001 D1, D2, D4.
  • Props, not compound parts. label, description and error are props, per 0002 D2's standing rule: ease of use beats expressiveness at our layer, because the expressive layer already exists underneath.
  • Validity comes from Base UI's data attributes, not our own state. 0002 D3.
  • All the standard range props pass through — min, max, step, largeStep, value, defaultValue, onValueChange, onValueCommitted, disabled, name, and format/locale for Intl.NumberFormat.
  • Single value only. Range sliders change the prop type to an array and multiply every visual decision here by two thumbs; deferred rather than guessed at.
  • The thumb takes focusRing. 0002 D4's rule sends bordered controls to a highlighted border instead — but a thumb is a mark rather than a field boundary, and a colour change on a 2px ring around a 17px circle is not a perceivable focus indicator. Cheap to flip if it looks wrong in place.
  • Stepper buttons are IconButtons with minus and plus from the curated set, and they carry required labels.
  • No as prop, no spacing props. Slider is neither a layout nor a typography component.

Every slider below is rendered from real token values — color.button.primary.base-bg for the fill, color.control.border for the track, the radius and spacing ramps for the rest — in the light theme regardless of this document's.

02Decisions

D1 is the one that sets the character of the component; D2–D4 sit inside it.

D1 · track-treatment

Track and thumb treatment

Three characters, each shown at 60%, then disabled, then at rest against an Input so the visual weight can be compared to something already in the system.

Classic rail

Recommended

4px track, 1.05rem hollow thumb

  • Reads instantly as a slider at any size, and the hollow thumb keeps the fill colour meaning "amount" rather than "handle".
  • The thumb is the largest hit target of the three, which matters most on touch.
  • The most conventional of the three — it looks like every other slider.

Inset rail

1.17rem track, thumb sits inside it

  • Visual weight matches an Input, so a slider in a form column does not read as a hairline between two solid fields.
  • The filled portion is large enough to carry a value label inside it later if that is ever wanted.
  • The grip is a small mark rather than a graspable handle, which reads as less obviously draggable.
  • Nothing else in the system is this heavy yet, so it sets a tone the rest of the components would have to answer.

Hairline

2px track, small solid thumb

  • Quietest of the three. Good for a settings panel with many sliders where the row rhythm matters more than any one control.
  • Least ink, so it sits comfortably beside dense text.
  • A 0.72rem thumb is below the comfortable touch target and would need an invisible hit area, which is a thing to get wrong.
  • Disabled and enabled are hard to tell apart at this weight, as the second row shows.
Decided · 2026-08-16 Hairline. A 2px track with a 0.72rem solid thumb.

Chosen against the recommendation. The two objections raised against it were not rejected on the merits — they become obligations on the build, recorded here so they are solved rather than rediscovered:

  • The thumb needs a hit area larger than itself. 0.72rem is 11.5 px, and WCAG 2.2 SC 2.5.8 sets a 24×24 px minimum at AA. The thumb ships with an invisible expanded target — a pseudo-element, not padding, so the visual mark stays 0.72rem while the pointer target does not. D4 makes this sharper at sm, where the thumb scales down further.
  • Disabled needs more separation than the specimen had. At 2px, a lightness shift alone left enabled and disabled nearly identical. The disabled state drops the indicator fill to the track colour entirely, so the difference is the presence of the fill rather than its shade.

D2 · value-display

When the value is visible

A bubble while dragging was the ask. The open part is whether it also appears for keyboard users, who change the value with arrow keys and never drag anything. Base UI publishes data-dragging and data-focused separately, so all three are equally easy to build.

The bubble is ours, not Base UI's, so it uses native CSS anchor positioning against the thumb — the hand-rolled overlay rule from 0001 D3.

Drag and focus

Recommended

[data-dragging], [data-focused]

60

shown here on keyboard focus — note the focus ring

  • Keyboard and pointer users get the same information. Arrowing a slider with no readout is guesswork.
  • Costs nothing extra — it is one more attribute in the same selector.
  • The bubble appears on tab-through, which is more motion on a form full of sliders.

Drag only

[data-dragging]

same focused state — no value anywhere

  • Quietest. The bubble only ever appears as a direct result of the pointer the user is already moving.
  • Literally what was asked for.
  • A keyboard user arrowing from 60 to 65 has no way to know they did, as the specimen shows.

Always, beside the label

A static readout; no bubble at all

Sweetness 60

no motion, no overlay, always readable

  • No overlay, no anchor positioning, no appearing and disappearing. The simplest thing that works.
  • The value is readable before you touch the control, which a bubble never is.
  • Not what was asked for, and the readout is far from the thumb — the eye has to travel while dragging.
  • Needs a label to sit beside, so an unlabelled slider has nowhere to put it.
Decided · 2026-08-16 Drag and focus. The bubble appears on [data-dragging] and [data-focused], so keyboard users get the same readout as pointer users. Positioned with native CSS anchor positioning against the thumb, per 0001 D3's rule for hand-rolled overlays.

This pairs well with D1: with a hairline track and a small thumb, the bubble is the main confirmation that anything is happening.

Amended 2026-08-17, after the build. The decision is unchanged; the implementation did not deliver it. [data-focused] is derived from Field, and Slider is deliberately not inside one, so it was never set — the bubble appeared only while dragging, and keyboard users saw nothing at all. Replaced with :focus-within on the root, which depends on nothing but the DOM and also covers the stepper buttons — the case that surfaced the bug, and one a thumb-only signal would never have caught.

D3 · stepper-layout

Where the stepper buttons go

Off by default, on with a prop. The question is where they sit, which is a layout decision with a real consequence: whichever arrangement is chosen, the track gets shorter, and the buttons have to line up with the track's centre line rather than its box.

Flanking

Recommended

minus left, plus right

  • Direction is unambiguous — decrease is on the side the value decreases toward.
  • Matches the mental model of the track as a number line.
  • Costs width at both ends, so the track is shortest of the three options.
  • The two buttons are far apart, so repeatedly nudging back and forth means crossing the whole control.

Trailing pair

both after the track

  • The two buttons are adjacent, so fine adjustment needs no travel between them.
  • Track starts flush left, which lines it up with a label above and with fields in the same column.
  • Neither button points anywhere — the pair has to be read rather than recognised.
  • Reads as a number stepper bolted on rather than part of the control.

No buttons at all

Track only; arrow keys are the fine control

the widest track, and one control to build

  • Smallest component, longest track, nothing to align.
  • Rules out the case that prompted the request — a pointer user who needs exactly 61, not roughly 60.
  • Puts precise adjustment behind the keyboard, which touch users do not have.
Decided · 2026-08-16 Flanking. Minus left, plus right, off by default and enabled with a prop. The buttons align to the track's centre line rather than its box, and take their size from the same ramp D4 sets.

D4 · size-ramp

Whether Slider has a size ramp

Button and Input both take sm | md | lg, and 0002 gave the system a size.control ramp of 1.69 / 2.41 / 2.65rem. A slider has no box, so the ramp would govern the row it occupies and the thumb inside it. The question is whether it should participate at all.

Ramp on the row

Recommended

size.control sets the row; thumb and track scale within it

1.69 / 2.41 / 2.65rem — same ramp as Button and Input

  • A slider in a form row lines up with the Input above it and the Button beside it, which is the whole reason size.control exists.
  • The stepper buttons in D3 get their size from the same ramp rather than a separate choice.
  • Inherits 0002's irregular ramp — md to lg is only 3.8px, so md and lg sliders look nearly identical.

One size

No size prop

one row height, one thumb, nothing to choose

  • A slider's thumb is a touch target, and shrinking it to sm makes it worse for the users who most need it big.
  • Three fewer variants to build, test and document, and no ramp irregularity to inherit.
  • Breaks the sm | md | lg convention that every other interactive component follows, so a form with mixed sm controls has one that will not follow.
Decided · 2026-08-16 Ramp on the row. sm | md | lg drives the row height from size.control — 1.69 / 2.41 / 2.65rem — with the track and thumb scaling inside it.

Two known consequences carried in deliberately: the ramp's irregular md → lg step from 0002 D1, and the interaction with D1 above — a hairline thumb at sm is the smallest mark in the system, which is what makes the expanded hit area non-optional rather than a nicety.

03The API, on the recommended set

04Deliberately not proposed

  • Range sliders. Base UI supports them by passing an array, but two thumbs multiply every decision above — which thumb owns the bubble, what the steppers do, how the thumbs behave on collision. A separate document once single-value is in use.
  • Vertical orientation. Base UI takes orientation="vertical" for free, but every specimen here assumes a horizontal row and the layout props in 0003 do not describe a fixed-height control well.
  • Marks and tick labels. No case yet, and they interact with the value bubble in ways worth designing rather than discovering.
  • A slider inside Field. Slider carries its own label; whether it should share Input's Field wiring is a consistency question better answered when a third form control lands.

  • src/slider/ — new. slider.tsx, slider.css.ts, slider.stories.tsx, slider.test.tsx, index.ts; exported from src/index.ts.
  • apps/playground/src/App.tsx — two sliders added to the recipe form.

thumbAlignment="edge" has a testing cost nobody anticipated Base UI keeps the thumb at visibility: hidden until it can measure the control, and jsdom performs no layout — so under test it never becomes visible.

The effects compound. getByRole('slider') finds nothing at all by default. Adding { hidden: true } recovers the role, but the accessible name computes to empty inside a hidden subtree, so a { name } filter still never matches. Confirmed by swapping the single prop to center, where every query passes unchanged.

Resolved by querying getByLabelText(name, { selector: 'input[type="range"]' }), which asserts the same label-to-input association without depending on layout the environment does not do; one test still asserts the role directly. This is not slider-specific — every Base UI component that measures before painting will do the same thing to its tests, so Select, Menu and Popover should expect it.

Both D1 obligations are in the code and verified in the output
  • Hit target. .thumb::after emits width:1.5rem;height:1.5rem centred on the mark — 24 px, the WCAG 2.2 SC 2.5.8 minimum — while the visible thumb stays 0.58/0.72/0.86 rem across the three sizes. A pseudo-element rather than padding, so the mark's size is untouched.
  • Disabled. The indicator's background switches to color.control.disabled-bg, which is the track's own disabled colour — so the fill disappears rather than dimming, exactly as the obligation required.
Smaller findings
  • A token name is now doing double duty. The indicator and thumb are filled with color.control.active-border. The value is right — it aliases the primary button's blue, so the slider's fill and the primary action cannot drift apart — but the name says "border" and it is being used as a fill. Worth renaming to color.control.active the next time the control set is touched.
  • "The thumb takes focusRing" needed a detail the settled item did not have. The thumb is a div; the focusable element is an input Base UI nests inside it. The ring is applied with .thumb:has(:focus-visible) rather than to the thumb directly.
  • The description needed an imperative escape hatch. Thumb's props land on the wrapping div, so aria-describedby cannot reach the input declaratively. It is set through inputRef in an effect, with a comment pointing at the Field integration that 0004 §04 deferred and that would replace it.
  • Stepper arithmetic snaps to the grid measured from min. A slider with min={1} step={3} steps 1, 4, 7, 10 rather than 3, 6, 9. The component is always value-controlled internally so the steppers and drags share one code path.
Correction — 2026-08-17 · the bubble never worked for keyboard D2 was implemented against an attribute that does not exist in this configuration.

The stylesheet showed the bubble on [data-dragging] and [data-focused]. Base UI publishes data-focused from Field, alongside valid, invalid, touched and dirty — and 0004 §04 deliberately kept Slider out of a Field. So it was never set on the root or the thumb, and the "and focus" half of D2 silently did nothing. Only dragging ever showed a value.

Fixed with :focus-within on the root. It covers the thumb, and it covers the stepper buttons, which was the reported case — data-focused could not have covered those even had it worked, since pressing a stepper never focuses the thumb.

Three tests now pin it. They assert the DOM condition that drives the CSS rather than a computed style, since jsdom applies no stylesheet. One wrinkle worth knowing for the next component: jsdom's selector engine caches dynamic pseudo-classes, so asking matches(':focus-within') before and after a focus change in one test returns the first answer twice. Each case renders fresh and asks once.

The general lesson: Base UI's state attributes are not all published by the component you are using. The Field-derived set — focused, touched, dirty, valid, invalid — is inert outside a Field, and nothing warns you. Styling against one is worth an explicit check that it is set.
