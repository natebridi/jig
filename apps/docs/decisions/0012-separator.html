Jig · decision 0012

Separator

A one-pixel rule. The interesting part is not drawing it — it is which element carries it, whether a screen reader should hear about it, and which token colours it, since the system has never drawn a line that was not a field's border.

  • Built
  • 2026-08-31
  • 4 decisions

01Context

Nothing in Jig draws a rule today. The only borders in the system are the ones around field-like controls — input.css.ts and combobox.css.ts, both using color.control.border — and there is no semantic for a line that divides rather than encloses.

Base UI, since the brief asked

Base UI ships a Separator. Verified against the registry rather than from memory: @base-ui/react is on 1.7.0, published 2026-08-04, not deprecated, already pinned here as ~1.7.0. So using it would add nothing to install.

It is also, in full, this — the whole of node_modules/@base-ui/react/separator/Separator.js once the boilerplate is stripped:

0001 D2 already settles what to do with that. Its rule: “a new component is built on Base UI when it needs managed focus, portalling, or an ARIA relationship beyond a label. Everything else is hand-rolled. This is the rule new proposals are checked against.” A separator needs none of the three, and the source above confirms there is nothing to lose by declining. So whether to build on Base UI is not a decision in this document — it is settled, and the code is the evidence.

Two facts checked against the specs rather than asserted, because both bear on the options below. From ARIA in HTML: <hr> has an implicit role=separator, and the only roles an author may put on it are none and presentation — so <hr role="presentation"> is the spec-sanctioned way to make a rule decorative, and writing role="separator" on an <hr> is explicitly not recommended, being redundant. From WAI-ARIA 1.2: separator is a structure role when not focusable and a widget role when it is. Everything here is the non-focusable kind; a focusable separator is a splitter, which is a different component.

Already settled by precedent

  • Hand-rolled, not Base UI — 0001 D2's behaviour test, with the source above as evidence that nothing is given up.
  • No spacing props. A separator is spaced by the Stack or Grid it sits in, like every other component.
  • No as prop. Polymorphism stays on layout and typography components.
  • orientation is horizontal | vertical, defaulting to horizontal.
  • One pixel, and no size ramp. A rule is a hairline; a thicker divider is a surface, and would want color.surfaces.* and its own proposal.
  • The ref forwards to the rendered element and refs.test.tsx pins it.
  • Ships the five-file set plus an export from packages/components/src/index.ts.
  • Theming stays :root-scoped.

02Decisions

All four accepted in one round. Three carried notes: one recording why the element choice matters more than the document argued, one asking whether the accessibility default is genuinely best practice — answered in D2's outcome, where it is split into the half that is and the half that is not — and one setting the new token's values, which corrects a claim in D3 above.

D1 · element

All three render an identical hairline. What differs is what the element means before any ARIA is added, and how much has to be undone to style it.

  • Neutral. A div carries no meaning the component has to override, so the role says exactly what is intended and nothing else.
  • One element for both orientations. An <hr> turned on its side is still a “thematic break” in the document, which a toolbar divider is not.
  • Nothing to reset. <hr> arrives with a UA border and block margins that have to be zeroed before the rule can be drawn, and those defaults differ between engines.
  • Two ARIA attributes to get right, where <hr> would need none — the exact work the platform already did.
  • A div in the markup says less to someone reading the DOM than an <hr> does.

  • The decorative case is the one the spec blesses: none and presentation are the only roles an author may put on an <hr>, and they mean exactly “this is a picture”.
  • Reads unambiguously in the DOM and in a snapshot test.
  • <hr> means a thematic break between paragraph-level content. Between two toolbar buttons, or as a vertical rule, that is a claim about the document that is not true.

Decided · 2026-08-31 <div role="separator">, with the note recording why:

“I will likely add additional styling options in the future, so div is safest.”

That is a better reason than the ones the option was argued on. An <hr>'s UA defaults are a one-time reset, but every future treatment — a dashed rule, a gradient, an inset — would be fought against them again in whichever engine disagrees. A div starts from nothing and stays there.

D2 · announced

Whether a separator is announced

A rule between two sections may be the only thing marking the boundary, in which case a screen reader should say so. A rule between toolbar buttons that already sit in a labelled group is decoration, and announcing it is noise. The component cannot tell which it is. Each specimen shows what a screen reader walks through.

A decorative prop

Recommended

Announced by default; decorative opts out

<Separator />
“Ingredients, heading”
“separator”
“Method, heading”

<Separator decorative />
“Bold, toggle button”
“separator”
“Align left, toggle button”

  • The call site is the only place that knows whether the rule carries meaning, and this is the only option that lets it say so.
  • Defaulting to announced fails safe: a caller who thinks about it can silence it, and one who does not gets the semantics rather than losing them silently.
  • The prop name matches the widely-used precedent, whose API table lists decorative with no stated default — omitting it leaves the separator semantic, which is the same behaviour proposed here.
  • A prop on a component that otherwise has one, for a distinction most callers will not think about — so the default will carry almost all real usage.
  • Gets it wrong by default in toolbars and menus, which are where separators are most common.

  • Simplest possible surface: one prop, one behaviour, nothing to decide at the call site.
  • Matches what Base UI's own component does, so anyone moving between the two finds the same thing.
  • The specimen is the argument against it. In the place separators are most used, the announcement is pure noise and there is no way to turn it off.
  • Pushes callers who care towards wrapping the component in an aria-hidden div, which is worse than a prop.

Always decorative

The rule is a picture; structure comes from elsewhere

“separator”
“Method, heading”
— the headings already mark the boundary

  • Honest about how the rule is nearly always used: as visual punctuation beside structure that already exists in headings, lists and labelled groups.
  • One behaviour, no prop, and never noisy.
  • Removes the option of a meaningful separator entirely. Where a rule genuinely is the only boundary marker, a caller has no way to say so and has to hand-roll the element.
  • Names the component Separator and then refuses to be one, which is the sort of thing that gets rediscovered as a bug.
Decided · 2026-08-31 A decorative prop, announced by default. The note asked for a check rather than agreement:

“I want to follow a11y best practice here, which seems like it is the recommendation, please flag if not.”

Half of it is best practice and half of it is a judgement call, so here is the split. Exposing the choice is the practice: only the call site knows whether a rule carries meaning, and both hiding a meaningful separator and announcing a decorative one are real failures. Nothing in the standards decides the default. WCAG does not require a separator to be exposed, ARIA does not require it to be hidden, and MDN's role page confirms only that a non-focusable separator “can still be perceivable by a screen reader user when using a reading cursor” — not that it must be.

The honest argument against the default chosen here: the places separators are most used — toolbars, menus, button groups — already carry their structure in a labelled group or a list, so the rule is decoration and the default will be wrong more often than right. Defaults usually favour the common case, and by that reasoning decorative should have been the default.

It stands anyway, on one argument: the two failures are not symmetrical. A caller who passes nothing and gets an announced separator has added noise, which is audible and gets reported. A caller who passes nothing and gets a silent one has lost information, and nobody notices. Flipping it is a one-character change if real use says otherwise.

D3 · line-token

Which token colours the line

The system has never drawn a line that was not enclosing a field, so color.control.border is the only candidate that exists. Whether that is the right name for a rule is the question. The specimens draw the same divider in each candidate, on the body surface and on a card, in both themes.

A new color.line

Recommended

Its own name — warm.200 light, warm.500 dark

  • Names the thing honestly. A rule divides; a border encloses. The system already makes this distinction elsewhere — sliderSet's own comment refuses to borrow surfaces.inverse on the grounds that “a mark is neither a surface nor text”.
  • Corrected 2026-08-31: this originally read that the token would ship “at the same value as color.control.border, so nothing changes visually today”. That is now true in light only. The note asked for a warm line in both themes, so dark takes warm.500 rather than color.control.border's gray.500 — the same lightness, 45.4%, with the warm ramp's chroma. A divider in dark is therefore very slightly warmer than the field borders around it, deliberately. The point of the separate name stands either way: retuning field borders no longer drags every divider in the product with it.
  • A bare token rather than a group, exactly as color.focus is. No set to fill out for a component that needs one colour.
  • Two tokens with identical values on the day it ships, which reads as duplication until the first time one of them moves.
  • A new semantic to keep in both themes and in the parity check, for one pixel.

Reuse color.control.border

Identical pixels, no new token

  • Nothing to add, nothing to keep in parity, and a divider is guaranteed to match the fields it sits among.
  • Honest in one real sense: a hairline on a surface and a hairline around an input are the same visual weight, and keeping them equal is a defensible intent rather than an accident.
  • The token's own comment in utils.ts defines controlSet as the surface shared by input, select, combobox and textarea. A divider is none of those, and reading it there tells you nothing.

Decided · 2026-08-31 A new color.line, a bare token beside color.focus, with the note setting its values:

“Use warm in both light and dark.”

So {color.warm.200} in light and {color.warm.500} in dark — the same lightness dark borders already sit at, 45.4%, taken from the warm ramp instead of the neutral one. The document's claim that the token would ship at color.control.border's value is corrected above: it does in light, and deliberately does not in dark, where field borders stay gray.500 and a divider runs very slightly warmer.

Worth knowing rather than discovering: this is the first place the two themes stop mirroring each other's hue choice for the same kind of mark. It is a small divergence and an intentional one, but it means “dark uses gray where light uses warm” is no longer a rule that holds across the system.

D4 · vertical-length

How a vertical separator gets its length

A horizontal rule fills the width it is given. A vertical one is one pixel wide with no intrinsic height, so without something to size it, it renders as nothing at all. Hover nothing here — the specimens differ in what happens when the row's height changes, which the second stage in each shows.

Stretch to the row

Recommended

align-self: stretch — the flex parent sets the height

BoldItalicUnderline
BoldItalicUnderline

the rule follows the row, whatever the row is

  • Works with no caller input in the case that matters — a vertical rule almost always sits in a flex row, which is what a Stack is.
  • Tracks the row automatically. A taller neighbour, a wrapped label or a bigger button size all move the rule with them.
  • No height prop, so nothing to keep in step with the content beside it.
  • Silently renders nothing outside a flex or grid parent, which is a confusing first encounter and cannot be caught by the type.
  • Stretches to the full row, so a rule that should stop short of the row's padding needs the caller to inset it.

The caller sets a height

Height through style, like every other box dimension

BoldItalicUnderline
BoldItalicUnderline

the rule stays put as the row grows — deliberate, or stale

  • Follows the standing rule that box dimensions go through style rather than becoming props, so it needs no new API at all.
  • Predictable: the rule is exactly as long as it was told to be, in any parent.
  • A rule shorter than the row — inset from the padding — is the common toolbar treatment, and this is the only option that gives it directly.
  • Every vertical separator becomes a hand-tuned number that goes stale the moment the row's height changes, which is exactly the kind of drift the size ramp exists to prevent.
  • Renders as nothing when the caller forgets, with no clue as to why.

Stretch, with an inset

Stretches, and can be pulled back from both ends

  full height of the row

<Separator orientation="vertical"
  inset="300" />
  stretched, less a spacing step at
  each end — the toolbar treatment

and horizontally, the same prop insets
the ends of the rule from the edges
<Separator inset="400" />
  • Covers both the full-bleed and the inset rule with one prop, in both orientations, on the spacing scale rather than in pixels.
  • Keeps the automatic sizing while answering the case that pure stretching cannot.
  • A second prop before anyone has asked for it, on a component with two. Strictly additive later, which is an argument for waiting.
  • Blurs the line the system draws between a component's own props and spacing, which belongs to the parent.
Decided · 2026-08-31 Stretch to the row. A vertical separator takes align-self: stretch and its length from the flex or grid parent.

The cost the option named is accepted: outside such a parent it renders nothing, silently, and no type can catch that. The story and the prop documentation both have to say it, since that is the only place a caller will find out.

03The API, as decided

04Deliberately not proposed

  • A labelled separator — a rule with “or” or a section name set into it. A real pattern, but it is a layout with two rules and a centred label, and it wants its own decisions about the label's type and tone. Additive later.
  • A focusable separator. WAI-ARIA makes separator a widget role when focusable, with aria-valuenow and a keyboard model — that is a splitter for resizing panes, and a different component with a different name.
  • A thickness or size ramp. One pixel. Anything heavier is a surface rather than a rule, and would take color.surfaces.*.
  • Decorative variants — dashed, dotted, gradient. No consumer, and each is a new token or a new rule to maintain for an effect that is usually a mistake.
  • Refactoring anything onto it. Nothing in Jig draws a rule today, so there is no migration — only new use.

05As built

Built 2026-08-31. All four decisions went in as accepted, and the proposal was accurate — the only divergence is one attribute the document showed being omitted, explained below.

Files

  • Added packages/components/src/separator/ — the five-file set.
  • Changed packages/tokens/src/semantics/color-light.ts and color-dark.ts — color.line, a bare token beside color.focus, at warm.200 and warm.500.
  • Changed packages/tokens/src/validate.ts — color.line added to REQUIRED_SEMANTICS, so losing it is a build error rather than an unstyled rule.
  • Changed src/index.ts, refs.test.tsx, api.types.test.tsx.

The one divergence

D1's specimen showed aria-orientation being set only for the vertical case, on the understanding that horizontal is the role's default and therefore redundant. As built it is set for both.

The reason is a failure to verify rather than a change of mind. Two attempts to read the default off the published specs — the separator role definition and the aria-orientation property definition — both returned pages truncated before the table that would confirm it. Rather than ship an omission resting on an unverified assumption, the attribute is explicit in both orientations, which is what Base UI's own component does and which cannot be wrong either way. If someone later confirms the default, dropping it for the horizontal case is a one-line change with no behavioural risk.

What the proposal got right

  • decorative needs no aria-hidden. Omitting the role is enough — an empty div with no role contributes nothing to the accessibility tree. Asserted directly: with decorative, the element has neither a role nor an aria-orientation, and no separator is findable even with hidden elements included.
  • Stretch works with nothing passed. In the toolbar story the rule measures 39px against a row of 39px and buttons of 39px — it tracks the row rather than a number anyone typed.
  • The token needed no set. ThemeColors already allows a bare Token at the top level, which is how color.focus is declared, so color.line slotted in beside it without touching the type.

A concern from D3's outcome, now withdrawn

D3's outcome flagged that a warm line in dark would be “the first place the two themes stop mirroring each other's hue choice”, and that “dark uses gray where light uses warm” would stop being a rule that holds. That concern does not apply. The dark ramp is being moved to warm generally, so color.line is early rather than exceptional, and it will be consistent with the rest by the time the shift lands. Recorded so the warning is not read later as an outstanding problem.

Worth a future proposal

  • The vertical failure is still silent. Outside a flex or grid parent a vertical separator renders nothing, and no type can catch it. The prop documentation and a dedicated story say so, which is all that was available — a dev-only warning when the computed height is zero would be a genuine improvement and is a tooling decision rather than a design one.
  • The decorative default may be the wrong way round. D2's outcome sets out the argument in full. Nothing in the build changed it; it is a question for real use.
  • color.line has one consumer. If a Dialog header rule, a table row divider or a CodeBlock bar wants the same line later, it should read this token rather than reaching for color.control.border again.

Verification

pnpm turbo typecheck test: 12 tasks, 154 tests, all passing.
