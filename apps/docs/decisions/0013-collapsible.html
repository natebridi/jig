Jig · decision 0013

Collapsible

A button that shows and hides a panel below it. Base UI does the measuring and the ARIA, and the brief keeps its prop names — so what is actually open is what the trigger is made of, how its type gets set, which glyph marks it, and whether a closed panel is still there to be found.

  • 2026-09-03
  • 5 decisions

01Context

Nothing in Jig shows and hides in place today. Dialog (0008) opens over the page, Tooltip and Combobox portal a popup out of flow. All three take content off the document and put it back unchanged. A collapsible leaves it in flow and changes the height of everything below it, which is a different problem: the panel has to be measured before anything can animate to its height, and the closed state has to decide whether the content exists at all.

Base UI, checked against 0001 D2

0001 D2's rule is the test: “a new component is built on Base UI when it needs managed focus, portalling, or an ARIA relationship beyond a label.” A collapsible needs the third. The trigger carries aria-expanded, and when open it points at the panel it controls — an id Jig would otherwise have to mint and thread itself. Verified in the installed source rather than from the docs, @base-ui/react/collapsible/trigger/CollapsibleTrigger.js:

Registry check rather than memory: npm view @base-ui/react reports 1.7.0 as both the latest version and the only dist-tag, with no deprecated field. packages/components/package.json already pins ~1.7.0 as a dependency, so this component installs nothing.

Accordion is not in this document

Base UI also ships an Accordion — it is right there in node_modules/@base-ui/react/accordion — which is a set of collapsibles with roving focus and an optional one-open-at-a-time rule. That is a separate component with its own decisions (roving tabindex, heading levels around each trigger, whether opening one closes the rest), and it is deliberately not smuggled in here as a group prop. This document proposes the single disclosure.

One checkable fact that D2 turns on

packages/styles/src/reset.css.ts styles exactly three selectors: :root, html, body, and h1..h6, p. It does not touch button. So a <button> inside a Jig app still arrives wearing the user agent's font — roughly 13.3px of system UI — unless a rule says otherwise. Button's recipe says otherwise by setting family, size and weight; Link's text variant says otherwise by declaring font: inherit so it can take the type around it. The trigger has to pick one of those two postures explicitly. There is no third, do-nothing option.

Already settled by precedent

Everything here follows an existing rule and is not up for debate in this document. Listing it is what keeps the decision count honest.

  • Built on Base UI. The trigger→panel aria-expanded / aria-controls pair is exactly 0001 D2's “ARIA relationship beyond a label”, and the height measurement is not something to reimplement.
  • Base UI's prop names are kept as-is, per the brief: open, defaultOpen, onOpenChange and disabled on the root, hiddenUntilFound and keepMounted on the panel. No renaming is on offer anywhere below.
  • One flat component, not compound parts. Dialog (0008) folds Base UI's Root / Portal / Popup / Title / Close behind a single component with slot props, and Combobox and Slider do the same. So <Collapsible>, not <Collapsible.Trigger>.
  • The trigger's visible content is label, not trigger. Dialog's trigger already means “an element that opens this”, and Collapsible owns its button rather than accepting one — reusing the name for a different idea is how a system stops being learnable. label matches Combobox and IconButton.
  • Controlled and uncontrolled both, via open and defaultOpen, exactly as Dialog does it.
  • No as prop — polymorphism stays on layout and typography components, via polymorphic.ts.
  • No spacing props. Spacing comes from the parent; a caller who wants air around it reaches for Stack. Box dimensions go through style.
  • The ref types to the rendered element and is asserted in refs.test.tsx. It lands on the root <div> — the element a caller would size — matching ScrollArea's note there.
  • Focus is the ring from focus-ring.ts, not a border highlight. The trigger is a button, not a field, and the checklist's rule (0002 D4) is that only components drawing their own outline highlight it instead.
  • The indicator glyph is sized and placed by the component, never by the caller — the same rule buttonIconSize establishes for Button.
  • Motion is hand-declared in collapsible.css.ts with a prefers-reduced-motion: reduce guard, because Jig has no motion tokens: tooltip.css.ts uses 120ms, slider.css.ts 120ms, scrollarea.css.ts 160ms, each guarded in place. A duration ramp is its own proposal, not a rider on this one.
  • Theming stays :root-scoped.
  • Ships collapsible.tsx, collapsible.css.ts, collapsible.stories.tsx, collapsible.test.tsx, index.ts, and the export from src/index.ts.

02Decisions

Accept one option per decision, or reject the whole set and leave a note. Notes are the refinement channel — partial acceptance goes there in plain English. D1 · trigger-chrome

What the trigger is made of

The trigger is a full-width <button>. The question is whether it borrows Button's recipe, draws its own quieter row, or takes a rule that makes it read as a section. This is first because it constrains D2: Button's recipe sets a font family, size and weight, which is precisely what a type prop would then have to fight — the collision 0009 D3 hit when Link tried to wear a Typography preset inside the Button recipe.

D2 · trigger-type

How the trigger's type is set

The brief asks for this one directly: the type style of the trigger should be changeable. What is open is the mechanism, and with it the default. Recall from the context section that a <button> gets nothing from the reset, so whatever is chosen has to be declared — including “inherit”.

There is a live precedent for two of the three. 0009 D3 gave Link a with prop naming a Typography preset, built from the same typeStyles map Typography's own variant is built from and imported rather than restated — see the comment at the top of typography.css.ts, which says two hand-maintained copies of sixteen presets is precisely the drift a design system exists to prevent. Whatever is chosen here, it imports that map.

D3 · indicator

The disclosure glyph

Which glyph marks the trigger, which end it sits on, and how it moves. In all three options it comes from the curated set, is sized in em so it tracks whatever D2 sets, and can be turned off with indicator={false} for a trigger that is already obviously one. What is being chosen is the default.

Jig has one existing precedent for a caret: Combobox puts a static caret-down at the trailing edge (combobox.tsx:300). It does not rotate, because a combobox's popup is not in flow below it.

Decided · 2026-09-03 Plus, swapping to minus. plus while closed, minus while open, at the trailing edge, sized in em so it tracks whatever with sets. Taken over the rotating caret this document recommended, which settles two things that were open:
  • The indicator has no motion. Two glyphs cannot be tweened, so collapsible.css.ts declares no transition on it and there is nothing for the prefers-reduced-motion guard to cover here — that guard is left for the panel height alone.
  • plus now carries two meanings in the system: “create a new thing” wherever else it appears, and “reveal this panel” here. Worth knowing before the next component reaches for it.

indicator={false} remains the escape hatch for a trigger that needs no glyph.

D4 · panel-mounting

What a closed panel leaves behind

Base UI exposes two panel props, and the brief keeps both names: keepMounted holds the content in the DOM behind a plain hidden, and hiddenUntilFound holds it behind hidden="until-found", which browsers open when the user's find-in-page matches text inside it. Both default to false upstream, so a closed panel is not in the document at all. What is open is whether Jig ships those defaults or overrides one.

The stakes are ordinary and familiar: a support page built from collapsibles where Ctrl-F finds nothing. Support for the attribute is no longer the obstacle it was — the figures below are from MDN's browser-compat-data, fetched today rather than recalled.

  • A collapsible costs nothing while closed. A panel holding a chart, a form or a data fetch does not mount, and does not run its effects, until it is opened.

Both stay one prop away, and the findability case is documented where a caller will meet it: the Storybook story for FAQ-style content passes hiddenUntilFound.

D5 · change-callback

What onOpenChange hands back

Base UI's signature is (open, eventDetails), where the details object carries reason, event, cancel(), allowPropagation(), isCanceled, isPropagationAllowed and trigger. Two shipped Jig components have already answered this question, and they answered it differently — which is the only reason it is a decision here rather than a line in the settled list.

ToggleButton's shape

Recommended

Specimen — the signature, and what it buys

onOpenChange?: (
  open: boolean,
  details: CollapsibleChangeDetails
) => void

interface CollapsibleChangeDetails {
  // veto the change; the panel does not move
  cancel: () => void
  readonly event: Event
  readonly isCanceled: boolean
}

<Collapsible
  label="Delivery address"
  onOpenChange={(open, details) => {
    if (!open && form.isDirty) details.cancel();
  }}
>
  • Follows the brief — Base UI's signature, not a narrowed one.
  • ToggleButton is the closer precedent: a two-state control where vetoing a change is a thing callers actually want.
  • Refusing to collapse over unsaved work is a real requirement, and this is the only shape that can express it.
  • A second details interface to maintain, near-identical to ToggleChangeDetails. If a third appears, they should be one shared type — and that is a refactor this document does not do.

Dialog's shape

Specimen — the signature, and what it costs

onOpenChange?: (open: boolean) => void

<Collapsible
  label="Delivery address"
  onOpenChange={setOpen}
>

<Collapsible
  onOpenChange={(open) => {
    if (!open && form.isDirty) /* nothing to call */
  }}
>
  • The signature almost every caller wants, with nothing extra in the way.
  • Matches Dialog, the component a Collapsible is most often reached for alongside.
  • Vetoing is unreachable. A caller who needs it has no route except dropping to Base UI directly, which is exactly what the wrapper is meant to prevent.
  • Widening it later is a breaking change for anyone who typed their handler.
Decided · 2026-09-03 ToggleButton's shape. onOpenChange?: (open: boolean, details: CollapsibleChangeDetails) => void. Base UI's details object is passed straight through and re-typed down to { cancel, event, isCanceled } — the subset worth calling — matching ToggleChangeDetails rather than Dialog's narrowed (open) => void. details.cancel() vetoes the change, which is what makes “do not collapse over a dirty form” expressible at all. If a third component wants this shape, the interfaces should become one shared type rather than a third near-copy.

What the proposal got wrong

The document assumed a Base UI part that does not exist. D3's specimens and the surrounding prose were written as though an Indicator part were available to hang the glyph on. @base-ui/react/collapsible exports exactly three parts — Root, Trigger, Panel (collapsible/index.parts.d.ts) — and no indicator among them. The swap needs the open state, and with defaultOpen that state belongs to Base UI, so the trigger is rendered through its render callback and the glyph is chosen from state.open. That is ToggleButton's existing pattern, so the fix cost nothing; the lesson is that this document verified the package's version against the registry but never its parts against the source, while quoting three other files line by line.

What it under-specified

  • Where the panel's padding goes. The height transition runs on the panel element, so padding declared there is animated with it and leaves the panel a few pixels tall when closed. Content spacing had to move to an inner box (content in the stylesheet), which is a structural detail no option mentioned.
  • The trigger's text alignment. A full-width <button> centres its text by default, which would have floated the label away from the panel copy and quietly undone the alignment D1 was chosen for. text-align: left is load-bearing, not cosmetic.
  • The disabled state. Five decisions and the settled list between them never said what a disabled trigger looks like, even though disabled was listed as a kept Base UI prop. It takes color.text.muted and drops the pointer cursor, chosen by eye rather than by decision.
  • Whether anything else reaches the root. Nothing said, and the first draft forwarded nothing — so id, data-* and aria-* were silently dropped. ScrollArea is the precedent that settles it: the other wrapper whose root is a plain div extends HTMLAttributes<HTMLDivElement> and spreads. Collapsible now does the same.

Two bugs only the playground caught

Both were invisible to the unit tests and to Storybook, and both surfaced within minutes of putting the component on a real page next to everything else.

  • :disabled matches nothing on this trigger. Base UI builds it with focusableWhenDisabled: true, so a disabled trigger never receives the native disabled attribute — it stays in the tab order carrying aria-disabled="true", which is what lets a screen reader reach it and announce that it is unavailable. The stylesheet had hooked :disabled, so a disabled trigger rendered at full contrast with a pointer cursor and looked entirely live. Now hooked on the attribute, with a test asserting the shape the CSS depends on.
  • Consumer props were dropped. Writing data-testid on a Collapsible in the playground — as the ScrollArea and Dialog examples on the same page already do — compiled cleanly and then did nothing, because TypeScript exempts hyphenated JSX attributes from excess property checks and the component spread nothing onto its root. See the forwarding note above.

What it got right

D1's central claim was checked in a browser and holds: with no horizontal padding on the trigger, the label's left edge, the panel copy and the prose below all land on the same pixel. D2's typeStyles import worked exactly as 0009 D3's did for Link — one map, no second copy. D4's reading of the Base UI defaults was accurate, and both mounting modes behave as the specimens drew them.

Not verified

The height transition could not be watched running. Base UI clears data-starting-style inside AnimationFrame.request, and the automated browser here never brings a tab to visibilityState: "visible", so requestAnimationFrame is starved and both the attribute and the animation clock freeze. What was confirmed in the live DOM: Base UI publishes a real measured --collapsible-panel-height (31px and 64px in two cases), the panel resolves to exactly that height once the transition is taken out of the way, and the emitted stylesheet carries all three rules — height:var(--collapsible-panel-height);transition:height .16s ease-out, the [data-starting-style] / [data-ending-style] pin to zero, and the prefers-reduced-motion guard. The interpolation itself is the one thing taken on trust.

Questions for a future proposal

  • A shared change-details type. CollapsibleChangeDetails is the second hand-written copy of { cancel, event, isCanceled }, after ToggleChangeDetails. D5's outcome predicted this; the third one should not be written, it should be a shared type.
  • Motion tokens. Three components now hand-declare a duration (120ms, 160ms, and this one at 160ms) and each repeats its own reduced-motion guard. The settled list deferred a duration ramp; it is now the most-repeated literal in the component layer.
  • Accordion. Deliberately excluded from this document. Nothing built here blocks it — but the trigger's render path and the panel's inner content box are the two pieces it would have to share rather than restate.
