Jig · decision 0011

Combobox

A filterable field with grouped options and multiple selection, on Base UI's Combobox. Most of it is settled by the field conventions Input already set — what is open is how the caller hands over items, and what selection looks like.

  • Built
  • 2026-08-28
  • 4 decisions

01Context

Base UI ships a Combobox at @base-ui/react/combobox. Verified against the registry rather than from memory: @base-ui/react is on 1.7.0, published 2026-08-04, not deprecated, and it is the version already pinned in packages/components/package.json as ~1.7.0. Minors have landed roughly monthly — 1.3.0 in March, 1.7.0 in August. No new dependency.

Both features asked for are first-class parts, not things to build: Combobox.Group and Combobox.GroupLabel for grouping, and Combobox.Chips, Combobox.Chip and Combobox.ChipRemove for multiple selection. The root takes multiple, and its items prop is typed readonly any[] | readonly Group<any>[], where a group is { items: readonly Item[], … } — so grouped data is a shape Base UI already understands rather than one Jig would invent.

Virtualization is out of scope by request. Base UI has a virtualized prop; this component will not set it, and the list renders every item it is given. That is a real ceiling and it is being accepted knowingly.

The surface is already drawn. color.control.* exists and its own comment in packages/tokens/src/utils.ts says it is shared by every field-like control “so Select and Combobox inherit this surface without another decision”. The control height comes from size.control.*, derived in 0002 D1 precisely so a bordered control lines up with a Button of the same size. Nothing here needs a token.

Already settled by precedent

  • Base UI's own positioning is correct here. 0001 D3 scoped the native anchor-positioning rule by origin: hand-rolled overlays use CSS anchor positioning and the Popover API, Base UI overlays use Base UI's. Combobox.Popup requires ComboboxPositionerContext and both pull floating-ui-react, and that is not debt. Tooltip stays hand-rolled and is not booked for migration.
  • No new tokens. color.control.* for the field, color.surfaces.popover for the list, color.token.* for any chip.
  • size is sm | md | lg, with the control height from size.control.* rather than from padding (0002 D1).
  • Focus highlights the border, and focusRing is not spread. A bordered control matches :focus-visible on click as well as on keyboard focus, so doing both double-paints it. color.control.activeBorder is the treatment (0002 D4).
  • label, description and error are props, not composable parts — so the accessible wiring between them cannot be left out. 0002 D2, and Dialog reaffirmed it in 0008 D1.
  • className and style land on the field wrapper; everything else spreads to the control. Input records why: a flexGrow aimed at the layout child silently did nothing when it landed on the input.
  • The popup list scrolls in a ScrollArea (0007), not a bare overflow region.
  • No as, no spacing props. The ref types to the input element and refs.test.tsx pins it.
  • Ships the five-file set plus an export from packages/components/src/index.ts.

02Decisions

All four accepted in one round. D4 went against the recommendation with a note challenging one of the document's own claims; the claim was wrong, the option's tradeoffs are corrected in place, and D4's outcome records what actually remains. Every option is kept, including the ones not taken.

D1 · api-shape

How the caller hands over items

Base UI exposes about two dozen parts. Input and Dialog both chose props over parts, but neither had to carry a caller's data. A Combobox does, and the items are the whole component — so the question is whether they arrive as an array or as children.

An items array

Recommended

Data in, field out — the parts stay inside

<Combobox
  label="Assignee"
  items={[
    { value: 'ada',  label: 'Ada Lovelace' },
    { value: 'alan', label: 'Alan Turing' },
  ]}
  value={value}
  onValueChange={setValue}
/>

Base UI's own data path: `items` is typed
readonly any[] | readonly Group<any>[]
and drives filtering and the input's label
  • The same argument 0002 D2 and 0008 D1 already made, applied once more: the wiring that must not be forgotten is not the caller's to assemble.
  • Uses Base UI's own items path, which is what drives internal filtering and what itemToStringLabel reads. Rendering items as children means re-implementing filtering to match.
  • Grouping falls out for free, because a group is just a different shape in the same array — see D2.
  • An item that needs custom content — an avatar, a two-line row, a trailing badge — has no way in without a further prop.
  • Hides two dozen Base UI parts behind one signature, so a caller who needs one of them has to drop to Base UI wholesale.

Composable parts

Jig-styled parts, mirroring Base UI

<Combobox.Root value={v} onValueChange={setV}>
  <Combobox.Label>Assignee</Combobox.Label>
  <Combobox.Input />
  <Combobox.List>
    <Combobox.Group>
      <Combobox.GroupLabel>
        Engineering
      </Combobox.GroupLabel>
      <Combobox.Item value="ada">
        <Avatar src={ada} /> Ada Lovelace
      </Combobox.Item>
    </Combobox.Group>
  </Combobox.List>
</Combobox.Root>
  • Any item content a caller can imagine, which is the one thing the array cannot give them.
  • Base UI's own docs transfer directly, and nothing is hidden.
  • A Combobox with no Combobox.Label renders happily and is announced unlabelled. The type cannot require a child, so the failure is silent — the exact argument 0002 D2 settled against.
  • Ten or more exports to document and to keep in step with Base UI's part list across minors that land roughly monthly.
  • Contradicts two decided documents without new evidence, leaving three components in one system answering the same question differently.

items, plus renderItem

The array, with an escape hatch for the row

<Combobox
  label="Assignee"
  items={people}
  renderItem={(person) => (
    <>
      <Avatar src={person.avatar} />
      <Stack>
        {person.name}
        <Typography tone="muted">
          {person.email}
        </Typography>
      </Stack>
    </>
  )}
/>
  • Keeps the props API and its guarantees, and answers the custom-row case the plain array cannot.
  • Additive later: shipping without it and adding it when a real consumer needs it costs nothing and breaks nobody.
  • Two ways to describe an item from the first release, and a caller has to decide which before they know the difference.
  • A render prop is where filtering and display quietly diverge — Base UI filters on itemToStringLabel, not on what the render prop drew.
Decided · 2026-08-28 An items array. Data in, field out; the two dozen Base UI parts stay inside the component.

The cost stands as named: an item that needs custom content — an avatar, a two-line row — has no way in. renderItem was the third option and is strictly additive, so it can be built the day a real consumer needs it rather than guessed at now.

D2 · grouping-shape

How grouping is expressed

Base UI accepts either a flat array or an array of groups, where a group is an object carrying an items array. The question is what Jig asks the caller to hand over, and every specimen renders the same result — so judge the call site, not the picture.

Nested groups in items

Recommended

The shape Base UI already reads

items={[
  { label: 'Engineering', items: [
    { value: 'ada',  label: 'Ada Lovelace' },
    { value: 'alan', label: 'Alan Turing' },
  ]},
  { label: 'Design', items: [
    { value: 'grace', label: 'Grace Hopper' },
  ]},
]}

Base UI's Group<Item> is exactly
{ [key: string]: unknown; items: Item[] }
so this needs no translation layer
  • Handed straight to Base UI. No mapping, no place for Jig's idea of a group to drift from the one doing the filtering.
  • Group order and item order within a group are both explicit, which a derived grouping cannot express.
  • One prop covers both cases: the same items is flat or grouped, and the type discriminates on the presence of items.
  • Data that arrives flat — which is how an API usually returns it — has to be reshaped by the caller before it can be passed.
  • A union type on the most important prop, so a mistyped group is reported against the whole array rather than the offending entry.

A groupBy accessor

Flat data, grouped by a key

items={[
  { value: 'ada',   label: 'Ada Lovelace',
    team: 'Engineering' },
  { value: 'alan',  label: 'Alan Turing',
    team: 'Engineering' },
  { value: 'grace', label: 'Grace Hopper',
    team: 'Design' },
]}
groupBy={(person) => person.team}
  • Takes the shape an API actually returns, with no reshaping at the call site.
  • One flat array type rather than a union, so a bad item is reported where it is.
  • Jig has to group and order the result itself, then hand Base UI the nested shape anyway — a translation layer that exists only to undo the caller's convenience.
  • Group order becomes an accident of item order, or needs a second prop to control. That is the usual next request.
  • Re-groups on every render unless memoised, and the memo key is a function the caller supplies inline.

Group children

Groups as markup, items still as data

<Combobox label="Assignee">
  <Combobox.Group label="Engineering"
    items={engineers} />
  <Combobox.Group label="Design"
    items={designers} />
</Combobox>

but Base UI needs the whole set on the
root to filter, so this has to be read
back out of children before render
  • Reads well, and group order is obvious and explicit.
  • Leaves room for per-group props later without touching the item shape.
  • Base UI filters from items on the root, so the children would have to be walked and flattened before render — the most machinery of the three for the same result.
  • Introduces a compound part after D1 recommends against compound parts, so the API would be half of each.
Decided · 2026-08-28 Nested groups in items. A group is { label, items }, handed to Base UI unchanged — no mapping layer and nowhere for Jig's idea of a group to drift from the one doing the filtering.

items therefore takes a union, and flat data has to be reshaped by the caller. Both were named and both are accepted.

D3 · multiple-display

What multiple selection looks like

With multiple, something has to show what is already chosen. Base UI provides Combobox.Chips for this, and Jig has a Token whose height was derived from size.control in 0006 specifically so it nests inside a field of the same size with a spacing step of air around it. The question is whether that intent gets used.

D4 · filtering-ownership

Who owns filtering

Base UI filters items internally by default, and also accepts filter (a match function) and filteredItems (a pre-filtered list, for filtering done elsewhere). Whether Jig exposes those decides whether this component can ever back a server-side search, and that is easier to settle now than to retrofit.

Internal only

Items in, filtering handled

<Combobox label="Assignee" items={people} />

no filtering props at all
Base UI matches on the item label

a server-backed search would have to
drop to Base UI, or re-pass items on
every keystroke and fight the internal
filter that runs over them again
  • Smallest surface, and correct for the case this is being built for: a known list of options.
  • Nothing to document and no way to configure it wrongly.
  • Double filtering is the failure mode: a caller who fetches matches from a server passes an already-filtered list, which Base UI then filters again against the query and empties.
  • Corrected 2026-08-28: this originally read “the retrofit is a breaking change to the most-used prop's semantics, not an addition”. That is wrong, and the note challenging it was right. Base UI's filter is null | fn | undefined and it branches on filterProp !== undefined, so adding the passthrough later is an optional prop whose absence preserves today's behaviour exactly — additive, not breaking. The real residual cost is smaller: until those props exist, a field that needs server-side search has no route inside Jig at all, and the caller drops to Base UI for that one field, where it will not match the others without duplicating the control styling.

Internal, with an opt-out

Recommended

Filtered by default; filter={null} hands it over

the common case, unchanged
<Combobox label="Assignee" items={people} />

and when the server already filtered
<Combobox
  items={results}
  filter={null}
  onInputValueChange={search}
/>

filter={null} is Base UI's own signal to
stop matching — not an invention here
  • Two props, both Base UI's own: filter accepts a matcher or null, and onInputValueChange already exists on the root.
  • Removes the double-filtering trap by making “I already filtered these” sayable, which is the failure a consumer would otherwise report as a bug.
  • Costs nothing when unused. The default is the internal filter, so the common call site is identical to the option above.
  • Opens the door to async search without answering it — no loading state, no debounce, no request cancellation. Those stay the caller's.
  • A null that means “off” on a prop that otherwise takes a function is a shape worth documenting carefully.

Async as a first-class mode

Jig owns the search lifecycle

<Combobox
  label="Assignee"
  onSearch={async (q) => fetchPeople(q)}
  loading={pending}
  debounce={250}
  emptyMessage="No one matches"
/>

a loading row while in flight
and a debounce Jig decides on
  • Answers the whole problem, including the loading state that the opt-out leaves to the caller.
  • One correct implementation of debouncing and out-of-order response handling, rather than one per consuming app.
  • Speculative. Nothing in the request needs it, and a search lifecycle designed without a real consumer is designed against a guess.
  • Request cancellation, retry, error display and stale-response handling all become Jig's, and none of them are typography.
  • Strictly additive later — it can be built on top of the opt-out without breaking anything, which is an argument for not building it now.
Decided · 2026-08-28 Internal only — against the recommendation, and the note that came with it was right on the point it challenged:

“Given I am the only consumer of this library, I don't see the risk in a future retrofit if the need arises, but I am open to reconsidering if it can be made clearer why this will be a dangerous change in the future.”

It cannot be made clearer, because it is not true. The document claimed the retrofit would be “a breaking change to the most-used prop's semantics”. Checking Base UI rather than restating the claim: filter is typed null | fn | undefined and the root branches on filterProp !== undefined, so a later passthrough is an optional prop whose absence reproduces today's behaviour exactly. Additive. The option's tradeoff list is corrected above rather than only here.

What survives is smaller and worth stating so it is recognised if it happens: with no onInputValueChange exposed either, a consumer cannot observe the query, so server-side search is not merely unconfigured but unreachable — the field would have to drop to Base UI wholesale, and would then not match the other controls without duplicating their styling. That is a day's work once, not a migration, which is the trade being accepted.

03The API, as decided

04Deliberately not proposed

  • Virtualization. Out of scope by request. Base UI's virtualized prop stays unset and the list renders every item. The ceiling is real — a few hundred rows — and turning it on later means owning row measurement, so it is a proposal rather than a flag.
  • A Select. A Combobox with the input made read-only is not a Select: different ARIA role, different keyboard model. Base UI ships a separate Select, and it shares this component's tokens and field props but not its implementation.
  • Creatable options — “add foo” when nothing matches. It needs an answer for what the created value is before it can have a UI, and that is a data question the design system does not get to settle.
  • The grid and row parts. Base UI supports a grid layout for items. No consumer, and it interacts with grouping in ways worth deciding separately.
  • Refactoring Tooltip. Reaffirming 0001 D3: two positioning systems is the settled state, not debt.

05As built

Built 2026-08-28. All four decisions went in as accepted. D3 could not be built as literally described and the divergence is set out below; the rest was accurate.

Files

  • Added packages/components/src/combobox/ — combobox.tsx, combobox.css.ts, combobox.stories.tsx, combobox.test.tsx, index.ts.
  • Changed src/index.ts — exports Combobox and its five types.
  • Changed refs.test.tsx, api.types.test.tsx — the ref lands on the input, the value type correlates with multiple, and filter / onInputValueChange are asserted absent.
  • No token changes. color.control.*, color.surfaces.popover, color.token.*, size.control.* and elevation.med all existed.

D3 could not be built as described

The option said “Jig Tokens as the chips”, and argued it on the grounds that “the component, the remove control and its accessible name all exist and are tested”. The remove control is the part that does not transfer.

  • Combobox.ChipRemove is a real button — useButton, nativeButton: true — and it is the only thing wired to the combobox's own removal. Base UI exposes no imperative remove: actionsRef carries unmount and nothing else.
  • Token renders its own remove <button>. Nesting the two is invalid HTML, and using Token's button instead would mean Jig owning the multiple-selection value state to compute removals itself — duplicating what ChipRemove already does, including its focus handling.
  • As built the chip wears Token's styles, not the Token component: token(), label, remove and tokenIconSize are imported from token.css.ts, and the button inside is Base UI's. Visually and in tokens this is what the specimen showed; what is not reused is the component.

The accessible name is preserved by hand — aria-label={`Remove ${label}`}, matching what Token derives — and is asserted in combobox.test.tsx.

Three bugs the tests caught that a screenshot would not have

  • The field had no accessible name. Field.Label wrapping Combobox.Label broke both: Combobox.Label and Combobox.Input each call useFieldRootContext and wire themselves into the surrounding Field.Root, so the Combobox parts are used directly and Field.Label is not.
  • onValueChange reported item objects, not values. Passing value={option} on each item made Base UI's currency the object while the public API promised Value. Items now carry value={option.value}; because { value, label } is Base UI's own LabeledItem shape, it resolves labels for display and filtering unaided, and itemToStringLabel and isItemEqualToValue both turned out to be unnecessary.
  • Chips rendered nothing, for the same reason — the selected array holds values, so the chip label is looked up from items.

And one only the browser caught

With multiple, the popup hung off the middle of the field. A plain <div> wrapper is not the anchor: Base UI anchors to inputGroupElement, and absent one it falls back to the input — which, after two chips, starts a third of the way across. The wrapper is Combobox.InputGroup, which registers itself as the anchor and carries Field's state as data attributes, so [data-invalid] and [data-disabled] now track the same source the error message does rather than being sniffed off the input with :has().

Worth a future proposal

  • Token has no field-sized step. D3 predicted this. At sm a chip sits close to the control's own height; it is legible but tight, and a nested size step is the fix if it grates.
  • A generic component fights Storybook's Meta. satisfies Meta<typeof Combobox> erases Value to unknown, so spreading args cannot narrow the single/multiple union — the two multiple stories write their props out instead. The same shape as the union-versus-spread cost recorded in 0009's As built, and a second instance is the point at which it is worth a rule rather than a workaround.
  • No Select yet. This shares its tokens and field props but not its implementation, as §04 says.
