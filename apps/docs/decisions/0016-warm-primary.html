Jig · decision 0016

A warm primary, and the end of the colour-set helpers

Primary becomes warm, which puts it on the same hue as secondary and means the two can no longer be told apart by hue alone. That breaks the one thing buttonSet was built to do — and auditing it turned up a contrast failure the shared ramp has been shipping quietly.

  • Built
  • 2026-09-05
  • 4 decisions

01Context

Three button variants take their colours from one function. buttonSet(hue, theme) in packages/tokens/src/utils.ts puts every variant at the same positions on its own hue's ramp, and the hue is the only thing that differs:

A warm primary breaks it directly: primary and secondary would resolve to the same six values. So the mapping has to differ per variant, and once it does, buttonSet's parameter is no longer carrying the difference — which is the question this document opens with and D3 answers.

What the audit found

Before changing anything, the current mapping was measured. Every fill was converted from its oklch source through sRGB to a WCAG contrast ratio against its own label colour. Button's md label is scale.300 — 0.97rem, about 15.5px — at weight 500, which is not WCAG large text, so the threshold is 4.5:1.

Which reframes this document. It is not only “make primary warm” — it is the first real test of whether a shared ramp mapping is the right way to hold button colour at all.

The other helpers are not the same problem

utils.ts exports seven set builders and only two take a hue. controlSet, ghostButtonSet, smokeButtonSet, scrollbarSet and sliderSet already hard-code their values and take nothing but the theme — they are colour objects with a function wrapped round them. tokenSet is the one place parameterisation genuinely earns its keep: twelve hues × two themes from one definition, and 0006 D2 settled that a Token's hues really are the same idea repeated. Any answer to D3 has to leave that alone.

Already settled by precedent

  • Variant names stay primary | secondary | danger | ghost | smoke. This changes what they resolve to, not what they are called, so ButtonVariant and the assertions in api.types.test.tsx are untouched.
  • The set shape stays base-bg / hover-bg / active-bg / disabled-bg / text / disabled-text. The checklist requires new states to extend that shape rather than rename it, and nothing here adds a state.
  • Token IDs stay kebab-case at source; the build camelCases them for .css.ts. No component changes: button.css.ts reads color.button.primary.baseBg either way.
  • Both themes keep full coverage. tokens-css.test.ts asserts that explicit light re-declares everything the dark media query overrides, so any remapping has to land in both or the theme forcing added in the token build breaks.
  • Danger stays red and ghost and smoke stay as they are. Ghost is already warm and already explicit; smoke's translucent veil is literal oklch for the reason recorded in utils.ts — an alias cannot carry alpha.
  • No new primitives. Every value proposed below is an existing step on the warm ramp.

02Decisions

Every button below is Button's real md geometry with the candidate fills applied, so hover and active are live. Ratios are computed from the ramp's oklch values, not estimated.

D1 · primary-mapping

How loud a warm primary is

With hue gone as the signal, weight is what makes primary read as the main action. All three candidates are a dark fill with light text in light theme and invert in dark; they differ in how far down the ramp the fill sits. Each is shown beside the recommended secondary from D2, because the pair is what matters, not the button alone.

warm.550 — softest

Specimen — live, hover it

light 550/50 · dark 150/700 · 8.22 : 1

  • Closest in weight to today's button, so the change reads as a hue swap rather than a redesign.
  • Comfortably AAA at 8.22:1.
  • Only two ramp steps clear of a heavier secondary, so the pair relies on the secondary staying light.
  • On the warm page surface it reads as dark grey rather than as a deliberate near-black; the warmth is barely perceptible at this lightness.

warm.600 — ink

Recommended

Specimen — live, hover it

light 600/50 · dark 100/700 · 10.82 : 1

  • Already the system's ink: text.primary, surfaces.inverse and slider.indicator are all warm.600 in light. The primary button becomes the same idea filled in rather than a new value.
  • 10.82:1, and it keeps three clear steps between the two variants at every state including hover and active.
  • Inverts cleanly: warm.100 on dark is the same relationship seen from the other side.
  • A near-black primary is a strong statement; on a dense form it can read as heavier than the action deserves.
  • Sits at the same value as body text, so a button and a paragraph share a colour — deliberate here, but it does flatten the palette.

warm.650 — strongest

Specimen — live, hover it

light 650/50 · dark 50/700 · 12.88 : 1

  • The most emphatic, and the widest separation from any secondary treatment.
  • Highest contrast of the three at 12.88:1.
  • Runs out of ramp for its own states: hover and active have to go to 700 and beyond, where the warm steps stop being distinguishable from each other.
  • Effectively black. At this point the hue is decorative and the decision to make primary “warm” stops being visible.
Decided · 2026-09-05 warm.600 — ink. Primary becomes the system's existing ink, filled in: the same value as text.primary, surfaces.inverse and slider.indicator in light, inverting to a light fill in dark. Starting values for the build, all real ramp steps:
  • light — base warm.600, hover warm.650, active warm.700, text warm.50
  • dark — base warm.100, hover warm.50, active warm.25, text warm.700

Measured after the fact against APCA as well: Lc 88.8 light and Lc 89.4 dark, comfortably past the Lc 75 body minimum. The disabled pair is unchanged.

D2 · secondary-mapping

What secondary becomes

Secondary cannot stay where it is. Today it is a mid-tone fill with light text at warm.450/50 — the same weight primary is moving to, and the one combination in the audit that fails AA. It has to step back, and how far is the question. Each specimen pairs it with D1's recommended primary.

Subtle fill, warm.100

Recommended

Specimen — on the page and on a card

light 100/600 · dark 600/100 · 10.37 : 1

  • The clearest hierarchy of the three: filled-dark against filled-light is legible at a glance and survives being photographed, printed or seen by someone who cannot separate the hues.
  • 10.37:1, up from today's failing 4.35:1 — the largest single accessibility gain in this document.
  • Matches the fills ghost already hovers to, so the two quiet variants share a vocabulary.
  • On the white card surface the light fill is close to the card itself; it reads as a button by its shape more than its colour.
  • A visible change for anyone already using secondary — it goes from loud to quiet, which is a different design intent, not just a different colour.

Heavier fill, warm.200

Specimen — on the page and on a card

light 200/600 · dark 550/100 · 8.48 : 1

  • Holds its own on a white card, where the lighter fill starts to disappear.
  • Still comfortably AAA, and still a large gain on today.
  • Closer to color.line and to the disabled fill, so a secondary button and a disabled primary become easier to confuse.
  • Leaves less room below it — ghost's hover fill sits at warm.100, so a ghost button hovered next to a secondary button reads as almost the same control.

Outlined, no fill

Specimen — on the page and on a card

1px warm.300 inset, text 600 · fills on hover

  • Reads identically on any surface, because it borrows none of it — the one option that behaves the same on the page and on a card.
  • Unmistakably a different kind of control from primary, not merely a lighter one.
  • Introduces a border to the button set, which no variant has today. That is a new property in the shape and a new decision about which token draws it — color.line divides, control.border encloses fields, and a button is neither.
  • Outlined and ghost then overlap: both are transparent at rest and fill on hover, separated only by a hairline.
Decided · 2026-09-05 Subtle fill, warm.100. Secondary steps back from a mid-tone fill with light text to a light fill with ink text, which is what keeps it distinct from primary now that both are warm. Starting values:
  • light — base warm.100, hover warm.150, active warm.200, text warm.600
  • dark — base warm.600, hover warm.550, active warm.500, text warm.100

This is the accessibility fix the audit forced: 4.35:1 → 10.37:1 under WCAG, and Lc 67.7 → 84.1 under APCA. The cost recorded with it stands — on the white card surface the light fill sits close to the card, so the button reads by its shape as much as its colour.

D3 · set-helpers

Whether the hue-parameterised helpers survive

The question the brief actually asked. Once each button variant has its own mapping, buttonSet(hue, theme) has one caller left — danger — and its parameter distinguishes nothing. The three options below are whole answers: each says what replaces it and where the values live.

Whichever is chosen, tokenSet stays parameterised. Twelve hues from one definition is the case where the abstraction is doing real work, and 0006 D2 settled that those hues are the same idea repeated.

Explicit objects, per theme file

Specimen — where a value would live

color-light.ts
 button: {
  primary: toColorTokens({
   'base-bg':  '{color.warm.600}',
   'hover-bg': '{color.warm.650}',
   'text':     '{color.warm.50}',
   …
  }),
  secondary: toColorTokens({…}),
 }

color-dark.ts
 the same shape, dark values
  • Every value is visible where the theme is declared. Reading color-light.ts tells you what light is, with nothing to follow into another file.
  • toColorTokens already exists and already does exactly this; it only needs exporting. No new abstraction is invented.
  • Divergent mappings stop being a special case — there is no shared assumption left to break next time.
  • Splits the light/dark pair across two files. Several comments in utils.ts exist precisely to explain the relationship between the themes — smoke's note that dark runs heavier because a white veil lifts less than a black one darkens. Those have nowhere to live once the halves are apart.
  • Duplicates the key names in both files, so a token added to one theme and forgotten in the other is a silent gap that only tokens-css.test.ts would catch.

Explicit objects, both themes together

Recommended

Specimen — where a value would live

semantics/buttons.ts
 export const buttons = {
  primary: themed({
   light: {
    'base-bg': '{color.warm.600}',
    'text':    '{color.warm.50}', …
   },
   dark: {
    'base-bg': '{color.warm.100}',
    'text':    '{color.warm.700}', …
   },
  }),
  secondary: themed({ … }),
 }

color-light.ts
 button: buttons.light
color-dark.ts
 button: buttons.dark
  • Keeps the two themes side by side, which is what makes a mapping reviewable — the interesting question is almost always “what does this become in dark?”.
  • Every variant's mapping is explicit and independent, so the divergence the brief needs costs nothing.
  • The paired shape makes a missing dark value a type error rather than a silent gap.
  • Keeps a home for the comments that explain the light/dark relationship, which is where most of the reasoning in utils.ts actually lives.
  • A new module and a new themed helper — a smaller abstraction than the ones being removed, but still one more thing than option A.
  • color-light.ts stops being the single place light is defined; the button block is now assembled elsewhere.

Keep buttonSet, add a second shape

Specimen — where a value would live

utils.ts
 buttonSet(c, theme) // danger only
 solidButtonSet(theme) // primary
 quietButtonSet(theme) // secondary
 ghostButtonSet(theme)
 smokeButtonSet(theme)

five builders for five variants,
four taking only the theme
  • Smallest diff. Nothing already written moves, and the light/dark pair stays together in each function.
  • Matches how ghostButtonSet and smokeButtonSet are already written, so the file stays internally consistent.
  • Ends with five builders for five variants, four of which take only a theme — which is a colour object with extra steps. The function is no longer abstracting anything.
  • Leaves buttonSet(hue, theme) in place with one caller, inviting the next variant to reuse a mapping that was only ever right for red.
  • Does nothing about the reason the audit failure went unnoticed: the values stay one indirection away from where the theme is read.
Decided · 2026-09-05 Explicit objects, per theme file — against this document's recommendation. buttonSet goes; each variant's colours are written out in color-light.ts and color-dark.ts through toColorTokens, which already exists and only needs exporting. No new module and no themed helper.

The cost this option was marked down for is now a build task. The two themes no longer sit side by side, so the comments in utils.ts that explain the relationship between them — smoke's note that dark runs heavier because a white veil lifts a dark backdrop less than a black one darkens a light one — lose their home. They are not to be dropped: where a value only makes sense relative to its counterpart, the comment moves to the half it explains and names the opposite value explicitly, so the pairing is still readable from one file.

tokenSet and tokenSets stay parameterised — twelve hues from one definition is where the abstraction earns its keep (0006 D2). controlSet, ghostButtonSet, smokeButtonSet, scrollbarSet and sliderSet are out of scope here; they already hard-code their values, and converting them is a separate tidy-up rather than part of this change.

D4 · contrast-floor

Whether a contrast floor becomes a rule

A variant shipped below AA and nothing caught it, because nothing was checking. Every mapping proposed above clears 8:1, so the immediate problem goes away either way — this decides whether the next one is checked.

A test asserts 4.5:1

Recommended

Specimen — what would run in CI

tokens: contrast.test.ts

for each button variant, each theme:
  resolve base-bg and text to sRGB
  expect(ratio).toBeGreaterThanOrEqual(4.5)

also the pairs already relied on:
  control base-bg / text
  token   base-bg / text
  surfaces.body / text.primary

catches today's 4.35 before it ships
  • The failure this document found was measurable and nobody measured it. A test is the only thing that makes that not recur.
  • The maths is thirty lines and has no dependency — it is the same conversion used to produce the audit table above.
  • Extends naturally to Token's twelve hues, which have never been checked at all.
  • A floor is not a design system. Passing 4.5:1 says nothing about whether two variants are distinguishable from each other, which is the harder property and the one D1 and D2 are actually about.
  • Locks the ramps: retuning a primitive could fail a test in a package that does not obviously own button colour.

Fix it, codify nothing

Specimen — the change, and what remains unguarded

this document fixes
  light secondary  4.35 → 10.37

still unchecked afterwards
  token, 12 hues x 2 themes
  control text on control fill
  every future variant
  • Nothing new to maintain, and the mappings here are so far clear of the floor that a test would not fire for a long time.
  • Keeps contrast a design judgement rather than a number to satisfy — and a passing ratio can still be a bad pairing.
  • The audit only happened because a variant was being changed. Nothing schedules the next one.
  • Leaves the twelve Token hues unmeasured, where the same shared-ramp reasoning applies and no one has looked.
Decided · 2026-09-05 Not codified here — deferred to APCA, elsewhere. The note, verbatim:

“I would like to codify, but if we can use the improved ACPA contrast algorithm, which is more complex and takes more than color into account (like font weight). I think that belongs elsewhere, since it'll be an integration test rather than a simple color contrast check.”

So this is not “codify nothing”. It is: a WCAG ratio check at the token layer is the wrong instrument, because the threshold depends on the size and weight the colour is finally rendered at — which the token layer cannot see. APCA takes both, so the check belongs where a rendered component can be measured.

Measured after the decision, and it leaves something behind. Under APCA the two variants this document changes land at Lc 84–89. Danger does not: it sits at Lc 67.7 light and Lc 72.7 dark, below the Lc 75 body minimum, and this document does not touch it. WCAG passed danger at 4.81:1, which is exactly the disagreement the note is about. Danger's mapping is a known gap from today, not a regression introduced here — and the first thing the APCA work should look at.

03As built

Built 2026-09-05 to the four accepted options. pnpm turbo typecheck test passes: 12 tasks, 223 tests across the three packages. No component code changed — button.css.ts reads color.button.primary.baseBg either way, which is what made this a token-layer change only.

  • packages/tokens/src/semantics/color-light.ts — primary, secondary and danger written out explicitly

What the build found that the decisions did not

  • A disabled secondary looked exactly like a hovered one. The disabled fill was inherited unchanged at warm.150 — which, once secondary moved down to warm.100, is its hover fill. The two states collided completely, and only the label colour told them apart. Fixed by holding the resting fill (warm.100) and letting the muted text carry the state, which is the answer smokeButtonSet already gives for the same reason. Only light secondary was affected; the other five combinations do not collide.
  • The disabled label has always been close to invisible. Measured across all six combinations: 1.59:1 in light and 1.36:1 in dark, identical for every variant. That is not something this change introduced — the same fill and text pair was in buttonSet before it — and WCAG 1.4.3 exempts inactive controls, so it is not a conformance failure. It is recorded because nobody had measured it and it is the sort of thing the APCA work should pick up.
  • The disabled values were never actually decided. D1 and D2's outcomes list them, but they were written into the record by this document rather than chosen from a specimen — the options only ever showed base, hover and active. The collision above is a direct result: an unexamined value carried through a change that invalidated it.

What the decisions got right

D3 was accurate about the scope of the work: removing buttonSet touched three files and no components, because the token IDs and the set shape were unchanged — which is what the settled list predicted. The theme-symmetry tests in tokens-css.test.ts passed without modification, confirming that writing the two themes out separately still produces the full override coverage that data-theme forcing depends on. And D3's build task was carried out: the light and dark notes now name each other's values where a mapping only makes sense as a pair — secondary's recessed fill in light against its raised fill in dark is the case that needed it most.

Questions for a future proposal

  • APCA, and danger with it. D4 deferred the check; the figures above say what it will find first. Danger's mapping is the one variant still below Lc 75, and it is untouched by this document.
  • A disabled treatment, decided rather than inherited. Two of the three findings above trace to the same gap: the system has never chosen what disabled looks like, it has only ever copied it. One shared pair applied to a solid primary, a quiet secondary and a red danger cannot be right for all three.
  • The remaining hard-coded builders. controlSet, ghostButtonSet, smokeButtonSet, scrollbarSet and sliderSet are now the only functions in utils.ts that take nothing but a theme. D3 scoped them out deliberately; converting them is a tidy-up that would leave only tokenSet parameterised, which is the one place it belongs.
