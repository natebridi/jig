Jig · decision 0006

Token

A small labelled pill — a chip — that carries a value: a filter, a tag, a selected entry in a multi-value field. Hand-rolled, because Base UI 1.7.0 ships no chip that works outside a Combobox. The interesting part is that it has to nest inside a text field, which turns "how tall is it" into a question about the token layer.

01Context

Nothing in the system today is a static labelled value. Button and ToggleButton are actions; Input is a field. A Token is neither — it is a rendered value that may optionally link somewhere or be dismissed. That makes it mostly a styling problem, with one hard constraint attached: it has to sit inside a text field with a stated 3px of air around it.

That constraint lands on the token layer rather than on the component. 0002 D1 established size.control.{sm,md,lg} because a bordered control cannot derive its height from padding the way Button does. A Token nested in that control inherits the same problem one level down: its height is the field's height minus the field's border minus the air. Every term in that subtraction is already a token.

Already settled by precedent

  • Hand-rolled, not Base UI. 0001 D2's behaviour test: a Token on its own coordinates nothing. Base UI 1.7.0 ships no Chip or Tag — its only chip parts are Combobox.Chip and Combobox.ChipRemove, and both open with useComboboxRootContext(), which throws outside a Combobox.Root. Checked in the installed combobox/root/ComboboxRootContext.js.
  • The recipe is what gets shared, not the component. When Combobox lands, its chips render Base UI's Combobox.Chip carrying token.css.ts's class — exactly the move IconButton and ToggleButton make against button.css.ts. That keeps the roving-tabindex behaviour with Base UI and the pixels with Jig.
  • size is sm | md | lg, matching ButtonSize and InputSize. What the values are is D1; the vocabulary is not open.
  • No as prop. Polymorphism stays on layout and typography components via polymorphic.ts. href swapping the element is a fixed two-way branch the component owns, not a caller-chosen tag.
  • No spacing props. Tokens get their gaps from the parent — typically a Stack direction="row" wrap. Width, including max-width for truncation, goes through style.
  • Labels truncate, they do not wrap. white-space: nowrap with text-overflow: ellipsis on the label span, unconditionally — a two-line token cannot fit a field of fixed height. The caller caps the width.
  • icon is an IconName from the curated set, sized by the component in em the way buttonIconSize is, and decorative — the label names the token, so the icon stays aria-hidden. Custom artwork goes through Icon's own children escape hatch, not through Token.
  • The remove control uses the x icon, which is already in the curated set (src/icon/generated/x.ts).
  • The remove button's accessible name is derived. Remove {label} when children is a string, with a removeLabel prop to override and to cover the case where it is not. Follows IconButton's rule that a control with no visible text of its own must carry a name — but unlike IconButton there is a visible label to borrow, so it is not required of the caller.
  • Focus is focusRing, not a highlighted border. 0002 D4's border rule is scoped to field-like controls that match :focus-visible on click. Token's interactive parts are a link and a button, which do not.
  • Corner radius is radius.400 (4.3px), the same value Button and Input use, so a token inside a field echoes the field's corner rather than introducing a pill shape the system has nowhere else.
  • Root-only theming, and the standard file set: token.tsx, token.css.ts, token.stories.tsx, token.test.tsx, index.ts, plus the export from src/index.ts.

02Decisions

Two are about the token layer, two about the API. Accept one option per decision, or reject the set and leave a note.

D1 · control-fit

Where the field-fit height lives

"Fits inside a text field with a 3px buffer" is a number derived from three existing tokens. The question is which layer performs the subtraction: the token layer, so the result is a named value other components can reach for; or the component's stylesheet, so nothing new enters the token file. A third answer avoids the subtraction entirely by reusing the ramp one step down — cheapest, but it does not hit the brief.

New size.token ramp

Recommended

md token in an md field — 2.68px each side

Design Research

1.95rem · 31.2px in 36.56px · buffer 2.68px

semantics/size.ts

// same helper shape as size.control
const nested = (ctrl, pad) =>
  round(rem(ctrl)
        - 2 * BORDER
        - 2 * rem(spacing[pad]))

token.sm = nested(control.sm, 100)
token.md = nested(control.md, 100)
token.lg = nested(control.lg, 100)

// 1.23rem   1.95rem   2.19rem
  • The relationship is written down where the other derived heights live, next to the comment in semantics/size.ts that already explains why size.control exists. Retuning the control ramp moves the token ramp with it, automatically.
  • The 3px becomes spacing.100 — a ramp value, not a constant, so nothing off-ramp enters the system.
  • Reachable by name from the multi-value field, from Combobox's chip row, and from anything else that later needs "the thing that nests in a control".
  • Three new semantic tokens shipped for one component, before a second consumer exists to justify them.
  • Bakes a 1px border width into the token layer, which is currently only ever written in input.css.ts.

calc() in token.css.ts

Identical pixels — the fork is where the number lives

Design Research

calc() · 31.2px in 36.56px · buffer 2.68px

token.css.ts

md: {
  height: `calc(
    ${size.control.md}
    - 2px
    - 2 * ${spacing[100]}
  )`,
}

// no change to packages/tokens
  • No new tokens, and no border width leaking into the token layer. The subtraction stays where the border it subtracts is a styling fact.
  • Resolves in the browser, so it tracks a themed override of --size-control-md that a build-time constant would miss.
  • The relationship is invisible from the token package — someone retuning size.control has no signal that a second ramp depends on it.
  • The next component that nests in a field copies the calc() rather than importing a value, which is how two subtly different heights start.

Reuse the ramp, one step down

Token md renders at size.control.sm

Design Research

1.69rem · 27.04px in 36.56px · buffer 4.76px

token.css.ts

sm: { height: ??? }
  // nothing below control.sm
md: { height: size.control.sm }
  // 4.76px buffer
lg: { height: size.control.md }
  // 4.76px buffer
  • Zero new values anywhere, and a token is guaranteed to be a height the system already renders.
  • Misses the brief by 1.8px a side, and the miss is uneven because the control ramp is uneven — md and lg share a padding step, so shifting by one puts lg's buffer somewhere else again.
  • There is no step below control.sm, so Token size="sm" has nothing to point at.
Decided · 2026-08-18 calc() in token.css.ts. No new semantic tokens. The height is composed in the component's own stylesheet from size.control.*, a literal 2px for the two borders, and spacing[100]. Pixels are identical to the derived ramp — 1.95rem at md, 2.68px of buffer — and the 3px still resolves to a value on the ratio ramp rather than a constant.

This accepts the cost the option names: semantics/size.ts carries no signal that a second height depends on size.control. Build obligation — extend the comment already in that file to say that token.css.ts subtracts from these values, so retuning the control ramp is known to move the token with it.

D2 · colour-vocabulary

What the color prop selects

Every existing coloured component names an emphasis: primary | secondary | danger | ghost. Tokens are the first thing in the system where colour carries meaning rather than weight — a red token is not a more important token, it is a different kind of thing. So the vocabulary is genuinely open, and the three answers below differ in how much freedom they hand the caller.

All three are semantic sets built in color-light.ts / color-dark.ts from the existing hue ramps — no new primitives either way.

Five semantic statuses

Recommended

Five sets under color.token.*

neutral accent success warning danger
  • Extends the vocabulary the system already has rather than replacing it — danger keeps meaning what it means on a button, and accent tracks color.text.accent.
  • Five sets to define, review for contrast, and keep honest in both themes. success and warning are new to the system and arrive with a use.
  • A caller cannot make a page of eleven-colour confetti by accident.
  • Colour-coded categories — the actual reason people reach for chips — have to be mapped onto five buckets, or they escape into className.

The hue ramp by name

All twelve hues, soft fill at {hue}.100 / {hue}.550

warm cool blue teal green lime yellow orange red fuschia purple gray
  • Matches what chips are actually for: labels, categories and user-assigned colours, where "which one" matters and "how urgent" does not.
  • One generated tokenSet(hue, theme) util covers all twelve, the way buttonSet already covers three — the cost is a loop, not twelve hand-written sets.
  • The first component in the system whose colour prop names a hue rather than a meaning. Restyling the palette later changes what every existing token looks like, with no semantic layer in between to absorb it.
  • Twelve foreground/background pairs to hold to contrast in both themes, and the darker hues (lime, yellow) are the hardest.

Reuse the button vocabulary

variant, color.button.*, no new tokens at all

primary secondary danger ghost
  • Zero new tokens, and the checklist's own instruction — reuse the existing vocabulary before inventing one.
  • The names do not mean anything here. A "primary" tag and a "secondary" tag is not a distinction anyone is trying to draw.
  • Button fills are sized for a button. At 31px with a 12.6px label they read as four loud buttons in a row, which is the opposite of what a value chip should do — visible above.
  • A token would then inherit button hover and active fills it has no interaction to justify.
Decided · 2026-08-18 The hue ramp by name. color takes a hue: warm, cool, blue, teal, green, lime, yellow, orange, red, fuschia, purple, gray. Generated by one tokenSet(hue, theme) in packages/tokens/src/utils.ts beside buttonSet and controlSet, producing color.token.{hue}.{base-bg, hover-bg, text} — three tokens across twelve hues and two themes.

Two things this settles that the option did not spell out, flagged here so they can be corrected before the build rather than after:

  • The default color is warm — the system's neutral family, and the one color.text.primary is already drawn from. Not gray, which would read cold against every other surface.
  • The twelve foreground/background pairs need a contrast pass at token scale before they ship. lime and yellow are the two most likely to move off {hue}.550.

D3 · emphasis

One visual weight, or a second axis

Button folds colour and weight into one prop: primary is both "blue" and "loud". Whichever way D2 goes, a Token's colour axis carries meaning, which leaves weight unclaimed — so it is either fixed by the component or exposed as a second prop. The cost is multiplicative: every emphasis is another full set of colour tokens.

Soft fill only

Recommended

One weight — no emphasis prop

Draft In review Shipped Blocked
Design Research

5 colour sets · 1 weight

  • A token is a value, not an action — a whole row of them should sit quietly under the text they annotate, and soft fill is the only weight that does at this size.
  • One set of colour tokens per colour. Nothing to hold to contrast twice.
  • Reads correctly nested in a field, where a solid fill competes with the field's own text.
  • No way to mark one token in a row as the selected or active one without reaching for className.
  • On a coloured surface, a soft fill can lose its edge — there is no outline weight to fall back on.

D4 · link-and-remove

Anatomy when a token is both a link and removable

href alone is easy: the whole pill is an <a>. onRemove alone is easy: a <span> with a <button> in it. Both together is not, because <a> may not contain a <button> and a <button> may not contain an <a> — interactive content cannot nest. Something has to give, and what gives determines how many tab stops a row of tokens costs.

The reference point is Base UI's own answer for the same problem inside a combobox: Combobox.Chip is a focusable <div> in a roving-tabindex list that handles Backspace and Delete itself, with Combobox.ChipRemove as a real <button> inside it. That works because the roving is coordinated by the combobox — a standalone Token has no such coordinator.

Decided · 2026-08-18 Container plus parts, with two refinements from the note:

“I do want to make sure the button has as big a hitbox as possible. Ideally right to the edge of the Token on top, right, and bottom. Make sure a link tag has a hover state.”

The hit area. The remove button is align-self: stretch with a −1px block margin to clear the transparent border, and a negative inline-end margin cancelling the pill's own padding — which the button re-pays as its own, so the glyph does not move while the target grows. Its right-hand corners take radius.400 to match the pill. At md that is a 20×31px target instead of 18×18px, running to three of the four edges. The left edge stays inside, because the label — which may be a link — is there.

The hover state. Adds a third token per hue, color.token.{hue}.hover-bg, one step in on the ramp: {hue}.150 in light, {hue}.600 in dark. A whole-pill link takes that fill on hover. When the anchor is only the label — the href plus onRemove case — the label underlines instead, because filling the whole pill would misreport what is clickable. The remove button uses the same hover-bg behind itself alone.

03The API, as decided

04Deliberately not proposed

  • A disabled prop. A Token is a rendered value, not a control with a state to suppress. "Cannot be removed" is expressed by omitting onRemove, "cannot be followed" by omitting href. If a multi-value field later needs to grey its whole chip row, that is the field's disabled state reaching in, and it can be proposed then.
  • onClick as an alternative to href. A pill that toggles rather than navigates is ToggleButton, which already exists and already has the pressed vocabulary. Two components should not both own that.
  • A TokenGroup, wrapping, or overflow collapse. "+3 more" needs a real dense field to design against. Rows come from Stack direction="row" wrap until then.
  • The multi-value field itself. This doc ships the pill. The combobox that holds a row of them is a later proposal, and it is where roving tabindex arrives — from Base UI, not from Token.
  • Avatars or images in the icon slot. icon stays an IconName, matching Button. Custom artwork goes through Icon's own children escape hatch.
  • A pill radius. radius.900 would make a capsule, which nothing else in the system is.
  • Hover and active fills. A non-interactive Token has no interaction to paint; the link and the remove button carry their own, and nothing else does.

What the proposal got wrong

  • The transparent border never existed. D4's outcome described the hit area as needing a −1px block margin “to clear the transparent border”. That border was an artefact of the proposal's own specimen CSS, left over from the outline weight D3 rejected — a soft-fill Token draws no border at all. align-self: stretch alone reaches the edges. Measured in the browser: 0px gap on top, right and bottom, at all three sizes.
  • The buffer is 2.72px, not 2.68px. See the table above. The 0.04px was rounding in the option that was not chosen.
  • The contrast worry was unfounded, and instructively so. D2's note predicted lime and yellow would be the pairs most likely to move off {hue}.550. They are the two highest-contrast pairs in light. All 24 pairs clear WCAG AAA — the lowest is warm at 7.83:1 in light, and every dark pair is above 10:1. The ramps are generated in OKLCH along one lightness curve, so equal steps give equal contrast whatever the hue; hue was never the variable. No pair needs to move.
  • Stack has no wrap prop. The API example in §03 wrote <Stack direction="row" wrap>. It does not exist — a wrapping row is style={{ flexWrap: 'wrap' }} today, which is what the stories and the playground do.

What it taught

  • The pill's padding had to become a custom property. The remove button cancels the pill's inline padding with a negative margin, and that padding changes per size — so it cannot be a constant in the button's rule. createVar() in token.css.ts, set by each size variant and read by the button. The hover fill uses the same trick across the twelve colour variants. Likely to recur wherever a part has to undo its parent's spacing.
  • Worth its own proposal: should Stack own wrap? A row of Tokens is the first place it is clearly wanted, and it is a layout prop rather than a box dimension, so it would not breach the rule that sends sizing through style.
  • Accurate everywhere else. The three-part anatomy, the derived remove-button name, the hue set, focusRing on the interactive parts and the truncation rule all went in as written, and the repo's guards caught nothing beyond the wrap slip.
