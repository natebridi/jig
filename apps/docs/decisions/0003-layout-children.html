Jig · decision 0003

Layout children

Stack and Grid position themselves well and their children barely at all. A real form makes that gap obvious — six wrapper divs and four inline gridTemplateColumns overrides in one screen. Grid becomes a fixed 24-column field that children span, and a single Box carries the child-side props for both containers.

01What the form actually needed

The recipe form in apps/playground/src/App.tsx is the evidence. Every workaround below is in that file today, and each one is a thing the layout props cannot say.

Revised before decision — 2026-08-16 The first draft proposed a different Grid and was redirected on review. It had columns={[1, 1, 4, 4, 'auto']} — arbitrary weight arrays per Grid — which required a CSS custom-property mechanism because track templates cannot be enumerated.

Redirected to the Carbon/MUI model instead: the grid has a fixed column count and children declare their span. That is a better fit and it removes a whole decision — with a fixed track, every value in the system is a closed set again, so Sprinkles handles all of it and no custom-property escape is needed. 16 columns was considered and dropped: it does not divide by three, and the Servings / Total time / Active time row would have been 5+5+6.

Already settled

  • Grid is a fixed 24-column field. One track definition, repeat(24, minmax(0, 1fr)), and children say how much of it they occupy. 24 divides by 2, 3, 4, 6, 8 and 12, so thirds, quarters and eighths are all exact.
  • Content-width layouts use Stack, not Grid. A fixed track has no auto column, so a row with a natural-width trailing control — the delete buttons — is a flex row. This is the rule for choosing between the two primitives, which the system has never stated.
  • One Box serves both containers. It carries span for Grid and grow for Stack, and the props that do not apply to its parent are simply inert. Accepted deliberately, in preference to a second Grid-specific container.
  • Everything is enumerable, so Sprinkles stays the only mechanism. No inline custom properties, no raw CSS in props.
  • Sibling grids align by construction. Two 24-column Grids of the same width share the same track positions, so repeated rows line up without subgrid or a shared template.
  • Grid gains align and justify matching Stack's existing props. Symmetry with an existing component, not a fork.
  • Every new prop takes the responsive object form, mobile-first, from the shared breakpoints. A prop that cannot be responsive is not finished.
  • Inline style stays legitimate for genuinely arbitrary values — a one-off maxWidth: '74rem' is not a layout prop waiting to be born.
  • Spacing props and as stay on layout components, and Box is one. No Base UI — 0001 D2's behaviour test puts layout in the hand-rolled column.

Specimens use real token values — control heights from size.control, gaps from the spacing ramp, borders from color.control — and render the light theme regardless of this document's.

02Decisions

Four questions the fixed-track model leaves open. D1 and D2 are the ergonomics of writing a form row; D3 is a scope question with a measurable cost; D4 is carried over unchanged from the first draft.

D1 · equal-shorthand

How you say "three equal fields"

Under a pure span model, the Servings / Total time / Active time row needs three wrappers at span={8} each — which is more to write than today's columns={3}. Most rows in a real form are equal divisions, so this is the common case getting worse to fix the uncommon one.

A second case tests each option: a gallery of five across. 24 does not divide by five.

Decided · 2026-08-16 columns distributes. columns={n} gives every unwrapped child a span of 24 / n. Only divisors of 24 — 1, 2, 3, 4, 6, 8, 12, 24 — are accepted; anything else is a type error rather than a rounding.

Precedence, now load-bearing: a Box with an explicit span always wins over the Grid's distribution, and a Grid may mix distributed and explicit children freely. With D2 landing on per-child spans, this is the rule that decides what an uneven row looks like, so it is stated here rather than left to the implementation.

D2 · collapse

How a row becomes a stack

This is the gap the screenshot shows most plainly: nothing in the form collapses. The ingredient row has four fields at 3 / 3 / 9 / 9, which is right at desktop and unusable at 380px. The spans are uneven, so a responsive columns shorthand cannot rescue it — the question is where the breakpoint is written.

A prop on the Grid

Recommended

collapseBelow="md" → every child spans 24 below md

<Grid collapseBelow="md" spacing="300">
  <Box span={3}><Input label="Measure"/></Box>
  <Box span={3}><Input label="Quantity"/></Box>
  <Box span={9}><Input label="Ingredient"/></Box>
  <Box span={9}><Input label="Preparation"/></Box>
</Grid>

below md —

  • One prop, one place, and it works for uneven spans — which is every interesting row.
  • Reads as the intent: "this row is a row from md up". The children stay declarative about proportion only.
  • Cheap: one extra class per breakpoint, not one per span per breakpoint.
  • A parent prop reaching into children's spans, which is the coupling D3 of the previous draft argued against.
  • All-or-nothing. A row where three of four fields should collapse still needs per-child values.

Responsive span per child

Each Box carries its own breakpoints

<Grid spacing="300">
  <Box span={{{ xs: 24, md: 3 }}}>…</Box>
  <Box span={{{ xs: 24, md: 3 }}}>…</Box>
  <Box span={{{ xs: 24, md: 9 }}}>…</Box>
  <Box span={{{ xs: 24, md: 9 }}}>…</Box>
</Grid>

the same breakpoint, four times,
in every row of every form

identical output · four times the authoring

  • No parent-to-child coupling. A child's layout is fully described by its own props.
  • Any collapse pattern is expressible, including partial ones.
  • Repeats the same breakpoint on every child of every row, which is where inconsistency creeps in — one field left at md while the rest moved to lg.
  • Nothing needs building, so it is really the "do less" option rather than a design.
Decided · 2026-08-16 Responsive span per child. No collapseBelow prop is built. A child's layout stays fully described by its own props, and a row collapses by every Box carrying span={{ xs: 24, md: … }}.

Chosen against the recommendation. Recorded because it changes what the other decisions have to carry: span must be responsive from the first commit rather than gaining breakpoints later, and there is no parent-level prop that can silently disagree with a child.

The verbosity concern is narrower than the proposal implied, given D1. An even row collapses through columns alone — columns={{ xs: 1, md: 3 }} distributes 24 then 8 — so only rows with uneven spans repeat the breakpoint per child. In the recipe form that is one row of four, not every row.

D3 · offsets

Offsets and start lines

A span says how wide; an offset says where. Indented sub-fields, a right-aligned action, a field that starts at column 13 with nothing to its left — all need a start position rather than document order. Nothing in the recipe form needs one, which is the argument for deferring, and every grid system eventually grows them, which is the argument for now.

It is not free. Enumerating start across 24 columns and five breakpoints is 120 declarations, against a stylesheet that is 756 today.

Decided · 2026-08-16 Defer. No start or offset props. Holds the stylesheet at roughly 856 declarations (+13%) rather than 976 (+29%), and adding them later is purely additive — no call site changes.

The known cost stands: the first layout that needs an offset reaches for style, and an inline style cannot carry a breakpoint. That is the trigger for revisiting this.

D4 · align-default

What a Stack does by default

Stack defaults align to 'start'. In a column that means children shrink-wrap horizontally, which is why the form opens with align="stretch" and style={{ width: 'stretch' }} on the same element. CSS's own initial value for align-items is stretch; Stack overrides it to start.

Each specimen is a column Stack of two fields and a row Stack of two buttons.

Chosen against the recommendation. Two consequences worth recording, because they are what the proposal offered to remove and now stay:

  • A column of full-width fields still needs an explicit align="stretch". The one in App.tsx line 35 stays.
  • Box must carry alignSelf. With the parent default at start, a single child that needs to fill has no other way to say so — and this is what replaces the style={{ width: 'stretch' }} workaround, rather than the default change doing it.

The same markup as App.tsx lines 33–76. Note the ingredient row: it has a content-width delete button, so by the settled rule it is a Stack containing a Grid, not a Grid.

04Deliberately not proposed

  • A FormRow or Field.Group abstraction. Tempting after looking at the ingredient list, but it would bake one form shape into the system on a sample size of one. Revisit after a second real form.
  • Container queries. The right answer for a field row that should collapse on its own width rather than the viewport's — which is exactly what the nested ingredient Grid wants, since it does not span the full page. A larger change, and its own document.
  • Row spans. grid-row has no case in the evidence and doubles the span surface.
  • A gutter scale distinct from spacing. Carbon separates them; nothing here yet needs it.

The CSS budget in D3 was measured wrong Both the baseline and the projection were bad numbers, and the real growth is much smaller.

D3 argued from "756 declarations today, 856 after". That count came from counting semicolons in the minified stylesheet — which misses every single-declaration rule, because minified CSS drops the last semicolon in a block. Utility classes are almost entirely single-declaration rules, so the metric was blind to exactly the thing being measured.

Measured properly, by file size on the same artifact before and after: 63,436 → 66,554 bytes, +3,118 (+4.9%) — against a projection of +13%. Retiring sixty long repeat(n, minmax(0, 1fr)) templates (~3,300 bytes) very nearly paid for the two hundred short grid-column: span n and distribution rules (~6,400 bytes) that replaced them.

This does not change the decision — deferring offsets still looks right on its own merits — but the number it was argued from was not real. Future proposals should quote bytes or rule counts, not semicolons.

The precedence rule is enforced by the cascade, not by code D1 said columns distributes but not how, and the mechanism turned out to decide whether the precedence rule was real.

Cloning children to inject a span breaks fragments, map and refs; :nth-child breaks on fragments. Distribution is instead one descendant rule per count per breakpoint: :where(.grid-3) > * { grid-column: span 8 }.

The :where() is the load-bearing part. It contributes zero specificity, so a Box carrying its own span class always wins in the cascade — the rule recorded in D1's outcome is a property of the stylesheet rather than a convention the component has to remember. A plain child of a distributing Grid carries no class at all, which is what the test asserts.

Gaps and surprises
  • Stack and Grid still cannot position themselves. The first draft's option was "Box plus self-props on containers", and only the Box half survived into the settled list. In the migration a nested Stack that needed to fill had no alignSelf of its own, so its parent had to set align="stretch" instead. That worked everywhere here, but it is a real gap and the fix is small — worth a follow-up rather than a rediscovery.
  • The form has more elements, not fewer. Three wrapper divs and five inline overrides became ten Box elements and zero inline layout styles. The win is that every one of them is typed and responsive, and the DOM is deeper for it — worth stating plainly, since section 03 reads as though it were a reduction.
  • D4's consequence landed exactly as recorded. alignSelf="start" on the two "Add…" buttons is what replaced flex: 0, and both width: 'stretch' workarounds went away by moving align="stretch" onto the parent Stacks.
  • A cached typecheck was hiding a pre-existing error. IconButton.label is required and the form's two trash buttons never had one; earlier full runs passed because the playground's typecheck was cached from before those buttons existed. Fixed by adding labels. The lesson is that "turbo typecheck test passes" is weaker evidence than it looks — --force is what actually checks.
