Jig · decision 0008

Dialog

A modal panel over a scrim. Base UI carries the behaviour that makes a dialog a dialog — focus trap, scroll lock, an inert background, focus returned to the trigger — so what is left is the shape of the API, what the scrim is made of, and how a long one scrolls. 0007 was split out of this and is built; Dialog is its first consumer.

01Context

Jig has one overlay today and it is not a precedent for this one. Tooltip is hand-rolled over the Popover API and CSS anchor positioning, because it is anchored to a trigger and coordinates nothing. A dialog is the opposite case: it is centred rather than anchored, and it has to trap focus, lock the page behind it, make that page inert, and hand focus back when it closes. That is exactly the behaviour test 0001 D2 wrote, so this is Base UI's Dialog at the ~1.7.0 pin.

Already settled by precedent

  • Base UI, per 0001 D2's behaviour test, at the ~1.7.0 range 0001 D4 pinned. Focus trap, scroll lock, inert background and focus restoration are all modal's job and none of it is reimplemented.
  • The Popover API and anchor positioning do not apply. Jig's rule that overlays use native anchor positioning is about anchored overlays; a dialog is centred in the viewport and has no anchor. Tooltip stays the only hand-rolled overlay.
  • Title and description are props, not parts, and they are what wires aria-labelledby and aria-describedby. Same rule and the same reasoning as 0002 D2: making them props means the accessible wiring cannot be left out by accident.
  • Opening is a wrapped trigger or the controlled pair, open / onOpenChange. Base UI 1.7's createHandle() imperative API is not exposed; agreed in scoping.
  • No nested dialogs. Nothing styles against --nested-dialogs, and the backdrop's forceRender is left alone. A confirm-on-close flow would be a nested alert, and that arrives with Alert or not at all.
  • An × in the top corner, always. Base UI's own guidance is that a modal dialog must contain a Dialog.Close so touch screen readers can escape the popup. AlertDialog will omit it — an alert is dismissed by choosing an action — and that is a difference in the wrapper, not in the stylesheet.
  • The scroll region is ScrollArea (0007), which was split out of this proposal precisely so its scrollbar was not designed as a dialog detail. Its mask marks the cropped edge; Dialog adds no rule of its own.
  • Corner radius is radius.400, matching Button, Input and Token. A larger radius for large surfaces is a system-wide change, not a Dialog one — see §04.
  • No as prop, no spacing props, root-only theming, and the standard file set with an export from src/index.ts.

02Decisions

The specimens are mock dialogs built from the real token values, over a scrap of page so the scrim has something to cover. Scroll the ones that scroll.

D1 · api-shape

Props for the frame, or composable parts

Input settled this for a component with three slots. A dialog has six — trigger, title, description, body, actions, close — and the actions row is the one people genuinely want to control. The question is whether 0002 D2's rule scales that far or breaks at it.

All three render the same dialog. It is drawn once below rather than three times, because the fork is in the source, not the pixels.

Props for the frame

Recommended

One component; the body is the children

<Dialog
  trigger={<Button>Delete</Button>}
  title="Discard changes?"
  description="Cannot be undone."
  actions={<>
    <Button variant="secondary">
      Cancel
    </Button>
    <Button variant="danger">
      Discard
    </Button>
  </>}
>
  Body content.
</Dialog>
  • The accessible wiring cannot be omitted: passing title is the only way to get a title, and it is what sets aria-labelledby. This is the whole of 0002 D2's argument and it holds harder here, where an unlabelled dialog is a worse failure than an unlabelled input.
  • The layout of the frame stays Jig's. Title, description and actions cannot be reordered into something the design system never drew.
  • actions is a slot, so the buttons themselves are still the caller's — count, order, variant and handlers.
  • A dialog that needs a custom header — an avatar beside the title, a status pill — has no way in short of dropping to Base UI.
  • Six props on one component, one of which takes a fragment of buttons, is a wide signature to read.

Composable parts

Jig-styled parts, mirroring Base UI

<Dialog.Root>
  <Dialog.Trigger>
    Delete
  </Dialog.Trigger>
  <Dialog.Popup>
    <Dialog.Title>
      Discard changes?
    </Dialog.Title>
    <Dialog.Description>
      Cannot be undone.
    </Dialog.Description>
    <Dialog.Body>
      Body content.
    </Dialog.Body>
    <Dialog.Actions>
      <Button>Discard</Button>
    </Dialog.Actions>
  </Dialog.Popup>
</Dialog.Root>
  • Any header a caller can imagine, and the same mental model as Base UI's own docs, so their examples transfer.
  • The pattern ToggleButtonGroup already uses — children rather than props — so the system is not uniformly one or the other today.
  • A dialog with no Dialog.Title renders happily and is announced as unlabelled. The type cannot require a child, so the failure is silent and only found by an audit.
  • Eight exports, eight files to document, and eight chances to compose them into an arrangement the design system never drew.
  • Contradicts 0002 D2 without new evidence, which would leave two components in the same system answering the same question differently.

Props, plus parts

The props API, and the parts for the rare case

the common case, as above
<Dialog title="Discard?" actions={…}>
  Body content.
</Dialog>

and, when the header is bespoke
<Dialog.Root>
  <Dialog.Popup>
    <header>
      {avatar} {title} {badge}
    </header>
    <Dialog.Body>…</Dialog.Body>
  </Dialog.Popup>
</Dialog.Root>

two public APIs, one component
  • Covers both the guarded common case and the bespoke one, without sending anybody to Base UI directly.
  • Two APIs to document, test and keep visually identical. When they drift, they drift silently — a fix applied to the props path leaves the parts path stale.
  • The escape hatch is the one with no accessibility guardrails, so the moment a caller needs a custom header they also lose the wiring the component existed to guarantee.
  • Roughly twice the surface for a component with no second consumer yet.
Decided · 2026-08-26 Props for the frame, with two refinements from the note:

“I do want a simplified dialog, but I don't want it to be rigid. As long as the props are optional, and the content can be anything, the first option is good. I do think I want an option to put the close button outside the dialog frame, so it may be safest to create a child element in Dialog.Popup that has the popup styles, but with the ability to place elements outside of that.”

Every frame prop is optional. The document proposed title as required — §03 said so outright — and that is corrected below. A Dialog with no title, no description and no actions is a plain panel around whatever the children are, which is what removes the rigidity the option's own tradeoffs admitted to.

That has one consequence worth naming. title was doing the accessible naming, so an untitled dialog has no accessible name at all. The caller passes aria-label instead, and a dialog with neither logs a development warning — the same answer 0005 reached for ToggleButton's value, where the type cannot express “required only in this case” and the runtime check is what remains.

The popup splits in two. Dialog.Popup keeps Base UI's behaviour and becomes a positioning box with no surface of its own and overflow: visible; an inner panel carries the background, radius, shadow and the clipping the scroll region needs. Anything that has to sit outside the frame — the close button first — is a sibling of the panel, absolutely positioned against the popup. A closePlacement="inside" | "outside" prop selects it, defaulting to inside; rename it freely at build time.

And a knock-on for later: with the surface on the panel, the element a future entry animation scales or fades is the panel, not the Popup. Motion is still §04's problem, but whoever picks it up should not have to rediscover that.

D2 · scrim-token

What the scrim is made of

Nothing in color.surfaces is translucent. Every semantic in the system is an alias to an opaque primitive, and an alias cannot add an alpha channel — so a scrim needs something the token layer has not done before. The three ways to get one differ in where the translucency is expressed and in what happens when the theme is retuned.

They are close to identical at rest, which is the point: judge them on what they cost, not on how they look. Each is drawn over the same scrap of page.

A token with alpha

Recommended

color.surfaces.scrim, a literal oklch

light oklch(0.12 0 0 / 0.5) · dark oklch(0 0 0 / 0.65)

  • The pipeline already supports it. Primitives are DTCG colours with colorSpace, components and an alpha field — every one of them carries alpha: 1 today, so a scrim is the same shape with a different number.
  • One name, one value, per theme. A designer changing how heavy the scrim feels edits a token rather than a component rule.
  • Light and dark can differ in more than opacity: dark goes to true black at 0.65, which a single formula over an ink colour cannot express.
  • The first semantic in the system whose value is a literal rather than an alias to a primitive, so it does not move when the palette does.

  • No new token at all, and it tracks the palette: retune the warm ramp and the scrim follows.
  • Stays an alias in spirit — the colour is still named, the translucency is a styling fact.
  • The percentage is the real decision and it ends up buried in a component stylesheet, which is exactly where a value nobody can find lives.
  • One formula has to serve both themes. Mixing the light theme's ink at 50% gives a warm brown-grey veil rather than a neutral shadow, and the only fix is a second branch — at which point it is a token with extra steps.

Opacity over an opaque token

surfaces.inverse at opacity: 0.5

background color.surfaces.inverse · element opacity: 0.5

  • Simplest of the three, and it reuses a semantic that already exists for exactly this idea — the inverse surface is the system's "not the page" colour.
  • Opacity is the property a transition animates most cheaply, so a fade-in is free.
  • Opacity applies to the whole element and everything in it. The backdrop holds nothing today, but it is the layer a future close-on-click affordance or a spinner would live on, and both would inherit the fade.
  • Couples the scrim's hue to a token chosen for tooltips. Retuning the inverse surface for tooltip legibility would silently restyle every dialog.
Decided · 2026-08-26 A token with alpha baked in. color.surfaces.scrim ships as a literal DTCG colour rather than an alias — oklch(0.12 0 0 / 0.5) in light, oklch(0 0 0 / 0.65) in dark — which is the same shape every primitive already has, with an alpha below 1.

It is the first semantic in the system whose value does not resolve to a primitive, so it will not move when the palette does. That is the cost the option named and it is accepted; the note to leave for whoever retunes the ramps is that this one token has to be checked by eye rather than by following an alias.

D3 · scroll-strategy

How a dialog taller than the screen scrolls

Base UI supports two shapes and they are structurally different. Inside: the popup stays fully on screen and an inner region scrolls, so the title and the actions never move — this is what ScrollArea was built for. Outside: Dialog.Viewport becomes the scroller and the whole popup travels through it, so a very tall dialog reads as one page.

Both specimens hold the same content in the same 250px stage. Scroll each.

Inside — the body scrolls

  • The actions are always on screen. A user cannot be shown a dialog whose only way forward is below the fold, which is the failure mode that matters — it looks like a dialog with no buttons.
  • The title stays visible, so a long body never loses its context.
  • Uses the component already built for it. 0007 exists because of this case, and its mask already marks the cropped edge.
  • On a short screen the body can be squeezed to very little between two fixed rows.
  • Content that should read as one continuous page — a printed agreement, a changelog — is split into a frame and a window.

Decided · 2026-08-26 Inside — the body scrolls. No scroll prop. The title and the action row are pinned and a ScrollArea (0007) sits between them, so the affirmative action is never below the fold. Dialog.Viewport is used for positioning only.

With the frame props now optional, a dialog with no title and no actions is just the ScrollArea filling the panel — which is the outside-scroll shape in everything but name, reached by passing nothing rather than by a second layout.

D4 · dialog-width

How wide a dialog is

Every other component takes its box dimensions through style — that is the standing rule, and it is why Token caps its own width with style rather than a prop. A dialog is the case that tests it: a confirm and a settings panel want visibly different widths, and picking one per call site is how a system ends up with eleven of them.

Note the rule forbids raw dimensions as props, not named ramps — Button and Input already take a size. Both options below are legitimate; they differ in whether width is a system decision or a call-site one.

A named size ramp

Recommended

Three widths, at true scale

size.dialog.sm   22rem   352px
size.dialog.md   30rem   480px   default
size.dialog.lg   42rem   672px

each capped for the viewport:
min(width, calc(100vw - 2rem))
  • Three widths across a whole product instead of eleven. That consistency is the reason to have a design system at all, and width is the dimension people diverge on fastest.
  • Matches the vocabulary Button, Input, Slider and Token already use, so size means the same kind of thing everywhere.
  • The viewport cap is decided once, in the component, rather than forgotten at each call site.
  • Three off-ramp values. The spacing ramp tops out at 8rem and the type scale does not apply, so 22 / 30 / 42rem are numbers chosen by eye — the first in the system that answer to nothing.
  • A genuinely unusual dialog — a media viewer, a diff — has to override with style anyway, so the ramp is a default rather than a constraint.

Width through style

The standing rule, unbent

<Dialog style={{ maxWidth: '30rem' }}>

the component still caps for the viewport:
maxWidth: `min(100%, calc(100vw - 2rem))`

no new values enter the token layer,
and no prop to keep in step with the
size ramps on other components
  • No off-ramp numbers anywhere, and the rule that box dimensions are not props stays uniform — which is worth something on its own.
  • Nothing to deprecate later if a ramp turns out to be the wrong three values.
  • Every call site picks its own width, and they will not agree. The system has no opinion on the one dimension a dialog is most defined by.
  • A caller who writes width instead of maxWidth, or forgets the viewport cap, gets a dialog that overflows a phone — a failure the component could simply have prevented.
Decided · 2026-08-26 A named size ramp. sm 22rem, md 30rem (default), lg 42rem, each capped by min(width, calc(100vw - 2rem)) so a narrow screen gets the margin rather than the overflow.

The three values are off-ramp and that was the argument against; they go in semantics/size.ts beside size.control as size.dialog.*, so they are at least named and in one place rather than spelled into a stylesheet. style still overrides for the genuinely unusual dialog.

03The API, as decided

04Deliberately not proposed

  • AlertDialog. Scoped out for this pass. It is a second Root and Trigger over this stylesheet, dropping the × and the outside-press dismissal; nothing here should make that harder, which is why the close button is settled as a wrapper concern rather than baked into the popup.
  • The imperative handle. Base UI 1.7's createHandle() would allow a confirm()-style call from a function with no trigger rendered. Agreed out of scope; it is additive if it is ever wanted.
  • Nested dialogs. No styling against --nested-dialogs, no forceRender on the backdrop.
  • Entry and exit animation. Base UI exposes data-starting-style, data-ending-style and onOpenChangeComplete, and Jig has no motion vocabulary at all yet — no duration or easing tokens. Inventing them inside Dialog is how a motion system ends up defined by whichever component needed it first. Its own proposal.
  • A larger radius for large surfaces. radius.400 is 4.3px, drawn for a button, and it does look tight on a 30rem panel. Changing that is a system-wide decision touching Box, CodeBlock and every future surface, not something Dialog should settle for everyone.
  • A drawer or sheet variant. Base UI ships a separate drawer; edge-anchored panels are not this component wearing a different prop.
  • modal={false} and trap-focus. Base UI's non-modal modes pass through untested. Jig designs the modal case; a non-modal panel is a different component with different rules about the page behind it.

Added after — 2026-08-26 The panel gained a drop shadow, from a new elevation ramp. Nothing in this document decided one; the shadow in D1's specimen was a literal in the specimen's own CSS. elevation.{lo, med, hi} now exist as themed $type: shadow tokens and the panel takes hi.

Two layers each — a tight contact edge and a broad ambient falloff — because a single layer reads as a grey halo. The ramp is a theme context of its own: the resolver previously swapped only colorLight / colorDark, so elevationLight / elevationDark were added alongside them. The dark ramp carries about four times the opacity at the same geometry, since the same alpha that lifts a surface off white is invisible on a dark page.

What the proposal got wrong

  • The viewport cap could not be written the way D4 showed it. 100vw counts the classic scrollbar's width, so calc(100vw - 2rem) overflows exactly the narrow screens the cap protects. Corrected in §03: the margin is the viewport's padding and the width is min(size.dialog.X, 100%) inside it, which needs no viewport unit at all.
  • “Outside” had no defined position, and the obvious one is broken. Hanging the close off the panel's trailing corner with a negative offset puts it past the edge of the screen as soon as the dialog is as wide as the viewport allows — on a phone, always. The popup reserves a strip above the panel instead, so the button has somewhere to be at every width. Verified in the browser: above the panel, right-aligned to it, inside the viewport.
  • The outside close cannot take text.inverse. The decision put it “over the scrim”, and the obvious foreground token flips with the theme — but the scrim is dark in both, so an inverted foreground disappears in dark mode. It carries surfaces.card and its own full radius instead, reading as a piece of the dialog rather than a mark on the scrim.
  • Every dialog's body sat 7.2px off-centre. ScrollArea reserves its scrollbar gutter unconditionally (0007 D1), so the content column was short on the trailing side whether or not anything scrolled — measured at 18.7px leading against 25.9px trailing. The body's trailing padding is now shortened by exactly that gutter, read from ScrollArea's newly exported constant so the two cannot drift. Measured again after: 18.7px on both sides.

What it taught

  • process is not typed in the components package, deliberately. D1's obligation called for a development warning, and process.env.NODE_ENV — the convention every React library uses — does not compile here, because adding @types/node would pull a Node global surface into a package that only runs in a browser. src/dev.ts declares it narrowly with a typeof guard. It is the first of these in the repo and the place the next one belongs.
  • Worth its own proposal: there is no way to remove the body's padding. D1's note asked that “the content can be anything”, and the case that exercises it — an image preview with the close outside — wants content reaching the frame's own edges. Neither className nor style reaches the body; both land on the panel. A bleed prop, or moving the padding out of the component, is a real decision rather than something to invent at build time, so the padding stands and the image sits inset.
  • Accurate everywhere else. The two-element popup, the optional frame props, the aria-label fallback, inside-scroll over a ScrollArea, the size ramp and the alpha token all went in as decided, and the alpha survived the token pipeline without any change to it.
