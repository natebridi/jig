Jig · decision 0019

Tabs

Base UI's tabs behaviour brought over whole, on a public surface smaller than the one it ships — plus a slot on either side of a tab's label, for an icon or a count.

  • Built
  • 2026-09-10
  • 4 decisions

01Context

Jig has no tabs. Base UI does, and its behaviour is the model: roving tabindex, arrow-key navigation, role="tablist" / tab / tabpanel wired up with the aria-controls and aria-labelledby pairing, and an indicator that tracks the active tab. That is the APG tabs pattern, and none of it is worth rewriting.

What is worth reconsidering is the surface. Base UI's Tabs is five parts — Root, List, Tab, Panel, Indicator — and every one of them is a component the caller places by hand. Jig has wrapped Base UI four times now and each time collapsed something: ToggleButtonGroup keeps one flat component with no separate item part (packages/components/src/togglebuttongroup/), Combobox takes its options as an items array rather than as children, and Dialog is a single component with props where Base UI has six parts. Against that, StructuredList exports three flat siblings — StructuredList, StructuredListRow, StructuredListCell — because rows and cells genuinely are caller-authored content.

Tabs sits between those two shapes, which is what makes the composition question real rather than a matter of taste. The decisions below are: how many components the caller places, how the active tab is marked, what a tab may hold besides its label, and what happens when the tabs do not fit.

What the registry says

packages/components/package.json pins @base-ui/react at ~1.7.0; 1.7.0 is what is installed. Latest is 1.8.0, published 2026-09-04, on a steady roughly-monthly cadence (1.5.0 2026-05-19, 1.6.0 2026-06-18, 1.7.0 2026-08-04). Not deprecated. Its only non-optional peers are React and React DOM; date-fns and @date-fns/tz are marked optional in peerDependenciesMeta and cost a consumer nothing. Tabs needs no dependency Jig does not already carry. Figures from npm view @base-ui/react version deprecated peerDependenciesMeta time, run 2026-09-10. The tilde pin means this proposal targets 1.7.0's API; the parts and props quoted below were read out of node_modules/@base-ui/react/tabs/*.d.ts, not from memory.

Already settled by precedent

Everything here follows an existing rule, an instruction already given, or Base UI's own default, and is not up for debate in this document. Listing it is what keeps the decision count honest.

  • One size. No size prop ships; if one ever does it has to be sm | md | lg matching ButtonSize.
  • activateOnFocus is fixed at Base UI's default, false: arrow keys move focus, Enter or Space activates. Manual activation is the APG's recommendation wherever a panel's content is not free to render, and it is the safer default to be stuck with.
  • loopFocus is fixed at Base UI's default, true. This diverges from ToggleButtonGroup, which exposes it — recorded deliberately rather than by oversight. No prop until something needs one.
  • orientation is exposed, as 'horizontal' | 'vertical' defaulting to horizontal — same shape, name and default as ToggleButtonGroup.
  • Each tab takes a required value, typed through a Value extends string generic on the root, as ToggleButtonGroup does. Base UI's any | null value and its positional-index fallback (defaultValue: 0) are not carried over.
  • No as prop. Polymorphism stays on layout and typography components plus ListItem (0014 D2); a tab is a <button> and a panel is a <div>.
  • No spacing props — a tab strip takes its spacing from its parent — and refs forward to the rendered element, typed, which refs.test.tsx enforces.
  • A tab draws no border of its own, so focus is the shared ring from packages/components/src/focus-ring.ts, not a border highlight (0002 D4).
  • No new primitives. Spacing comes off the ratio ramp, radius off radius.400, type through textStyle(); any tab-specific colours extend the color.button.* state shape as a semantic set.
  • keepMounted and renderBeforeHydration stay unexposed at their Base UI defaults. A hidden panel unmounts.

02Decisions

Accept one option per decision, or reject the whole set and leave a note. Notes are the refinement channel — partial acceptance goes there in plain English.

D1 · composition

How the parts compose

Base UI asks the caller to place four elements to get a working tab set, five with the indicator. Every option below renders the same DOM and the same ARIA, so the first question is how much of it the caller writes by hand — and the second, which this document originally missed and D1's outcome records, is what else may live inside the root. A tab set is often not only tabs and panels: a menu at the end of the strip, a persistent banner above the panels. Inferring the list closes that door; naming it leaves it open.

Three parts, list inferred

Recommended

Specimen — the call site

<Tabs defaultValue="usage">
  <Tab value="usage">Usage</Tab>
  <Tab value="props">Props</Tab>

  <TabPanel value="usage">…</TabPanel>
  <TabPanel value="props">…</TabPanel>
</Tabs>
  • Two levels of nesting instead of three, and one fewer import.
  • The list cannot be forgotten, mis-nested, or given two children it should not have.
  • Tabs has to partition its children by component identity. A .map() is fine (arrays flatten), but a <Tab> wrapped in a caller's own component is invisible to the split and lands in the wrong half.
  • Nothing in the types says which children go where; the rule lives in the doc comment.
  • Every child of Tabs has to be a Tab or a TabPanel. A menu beside the strip, or a banner between the strip and the panels, has nowhere to go.

Four parts, mirroring Base UI

Specimen — the call site

<Tabs defaultValue="usage">
  <TabList>
    <Tab value="usage">Usage</Tab>
    <Tab value="props">Props</Tab>
  </TabList>

  <TabPanel value="usage">…</TabPanel>
  <TabPanel value="props">…</TabPanel>
</Tabs>
  • No child inspection anywhere; every wrapper is explicit and composes with anything.
  • Matches StructuredList's flat-sibling export shape, and maps one-to-one onto Base UI's docs.
  • TabList is a place, not only a wrapper: anything that is neither a tab nor a panel composes as its sibling, and Tabs stays a behavioural wrapper with no styling of its own.
  • The extra wrapper is repeated at every call site, and for the plainest tab set it carries no decision of its own.
  • Four exports and four names to learn for the commonest possible case.

One component, items array

Specimen — the call site

<Tabs
  defaultValue="usage"
  items={[
    { value: 'usage', label: 'Usage',
      content: <Usage /> },
    { value: 'props', label: 'Props',
      content: <PropsTable /> },
  ]}
/>
  • One import, one component; the value/label/content triple cannot fall out of sync.
  • Follows Combobox, which already takes its options as data.
  • Puts arbitrary JSX inside a prop array — awkward to read, and worse to diff, once a panel is more than a line.
  • Every future per-tab prop widens the item type instead of being a prop on a component.
Decided · 2026-09-10 Four parts, mirroring Base UI. Not the recommendation, and for a reason the document had not weighed. Verbatim:

“I'm choosing this because it makes it clearer that other content could theoretically exist alongside Tablist and TabPanels, for extra composability. An extra menu, persistent messages, etc. Tabs should have no styling associated with it, it is a behavioral wrapper.”

The basis changed, so the body above changed with it: the three-part option had no con for the children it forbids, and this option's “boilerplate” con overstated the case. Both are corrected. Two things follow that were not decisions here and are now constraints on the build:

  • Tabs renders Base UI's root and nothing else — no layout, no spacing, no border. Every visual rule belongs to TabList, Tab and TabPanel.
  • The sliding indicator from D2 is therefore TabList's, not the root's; the strip is the positioning context.
  • Children of Tabs other than TabList and TabPanel render where they are written. Nothing filters them.

D2 · active-marker

How the active tab is marked

Base UI ships Tabs.Indicator: a span that publishes the active tab's measured position and size as CSS variables so a bar can be moved and resized to match. It is real machinery — a resize observer, a pre-hydration script for SSR — and it buys one thing, a bar that slides. The alternative is that the active tab draws its own mark and nothing is measured at all.

In every option the indicator stays internal: it is not a part the caller places. The strips below are live — click or tab into them.

Sliding underline

Recommended

Specimen

The bar takes the active tab's measured width and offset, so it tracks labels of any length.

  • The movement shows which tab you came from, which is the one thing a static mark cannot say.
  • Base UI does the measuring; the component only writes the CSS.
  • A resize observer per strip, and a one-frame flash after SSR unless renderBeforeHydration is turned on — which the settled list currently leaves off.
  • The bar is a positioned sibling, so the strip has to be a positioning context and cannot simply wrap.

Underline on the tab

Specimen

The mark is the active tab's own ::after. Nothing is measured, nothing observes resize, and it is correct before hydration.

  • No measurement, no observer, no hydration flash — the first paint is already right.
  • Wraps and scrolls without any extra thought, which D4 then gets for free.
  • The mark jumps rather than travels; on a wide strip the eye loses the relationship between the two tabs.
  • Drops a Base UI part the library maintains, so a later change of mind is a rewrite rather than a prop.

Segmented fill

Specimen

A raised card on a recessed track — the shape a ToggleButtonGroup already makes.

  • Reads as one control, and needs no rule under the strip to sit on.
  • Reuses the ghost button's hover and active fills; no new colour work.
  • Now nearly indistinguishable from ToggleButtonGroup, which is a different thing that does not swap a panel.
  • Does not read as a page-level section switcher, which is the case that prompted this.
Decided · 2026-09-10 Sliding underline. Base UI's Tabs.Indicator, kept internal — internal to TabList rather than to the root, which is what D1's outcome settles. No note.

D3 · tab-content

What a tab holds besides its label

Two live precedents disagree. Button takes icon and iconPosition, restricted to the curated IconName set and sized by the button at 1.4em. ListItem takes start and end as open ReactNodes, because a row's leading slot might hold an avatar or a swatch, not only an icon.

One thing does not carry over from ListItem: there, end is the slot allowed to be interactive, because it sits outside the row's anchor. A tab is the button, so both slots render inside it. Neither may hold anything interactive, in any option below — a button inside a button is invalid HTML and leaves one of the two unreachable.

start / end slots

Recommended

Specimen

<Tab value="alerts"
     start={<Icon icon="bell" />}
     end={<Token>12</Token>}>
  Alerts
</Tab>
  • Holds a Token, an avatar or a status dot, not only an icon — which is what was asked for.
  • Both ends available at once, and the names already mean this in ListItem.
  • Open ReactNode cannot stop a caller putting a button in; the rule is a doc comment and a test, not a type.
  • The icon case is wordier than Button's, for the same result.

icon / iconPosition

Specimen

<Tab value="alerts" icon="bell">
  Alerts
</Tab>
  • Shortest call site, and the curated IconName union makes a wrong icon a type error.
  • Sizing and spacing stay the parent's, exactly as Button already does it.
  • No count, no avatar, no token — the case that prompted the ask is the one it cannot serve.
  • One slot only: iconPosition chooses an end rather than filling both.

Both, icon as sugar

Specimen

<Tab value="team" icon="user">
  Team
</Tab>

<Tab value="alerts"
     end={<Token>12</Token>}>
  Alerts
</Tab>
  • Short for the common case, open for the rest.
  • Two ways to put an icon on the left, and a precedence rule between icon and start that has to be written down and tested.
  • The largest surface of the three, on a component whose stated goal was a smaller one.
Decided · 2026-09-10 start / end slots. Open ReactNodes on both sides, both non-interactive, taking ListItem's names without ListItem's rule about which end may hold a control. No note.

D4 · overflow

When the tabs do not fit

Base UI does not answer this — its list is a plain div with role="tablist" and whatever the stylesheet says. So the component has to. Each specimen below is the same seven tabs in a 20rem frame; the difference is real, not illustrated.

Keyboard navigation is unaffected either way: arrow keys move focus, and the browser scrolls a focused tab into view on its own.

Scroll on one line

Recommended

Specimen — drag or shift-scroll

  • The strip keeps one predictable height, so nothing below it moves as tabs are added.
  • Composes with ScrollArea (0007), which already owns the faded edge and the reserved scrollbar gutter.
  • Tabs off-screen are easy to miss; the fade is the only signal.
  • A sliding indicator has to travel inside the scroller, so D2's positioned bar needs the scroll offset handled.

Wrap to a second row

Specimen

  • Every tab stays visible and reachable with no gesture at all.
  • One CSS property, and it works before hydration.
  • The strip's height depends on its width, so the panel below shifts as the viewport changes.
  • The rule under the strip no longer reads as one edge; a wrapped row of tabs stops looking like a tab bar.

Leave it to the caller

Specimen — overflow clipped

Four tabs unreachable, and nothing says so

  • No opinion to be wrong about, and no scroll machinery in the bundle.
  • The default is a broken one: tabs that exist, are focusable, and cannot be seen or pointed at.
  • Every consumer solves the same problem again, differently.
Decided · 2026-09-10 Scroll on one line. The strip scrolls horizontally rather than wrapping, over ScrollArea (0007). The open item it carries: D2's indicator has to travel inside the scroller, so the bar's offset is measured against the scrolled content, not the viewport. No note.

What the proposal got wrong

Four decisions, four accepted options, no divergence — but the reasoning under two of them did not survive contact with the code.

  • D4's ScrollArea claim does not hold. The option's pro said the strip would compose with ScrollArea, “which already owns the faded edge and the reserved scrollbar gutter”. It owns neither on this axis: 0007 §04 scoped horizontal overflow out, so the mask in scrollarea.css.ts is to bottom and only the vertical bar reserves a gutter. Wrapping the strip in it would have bought nothing and cost something — Base UI puts a focusable viewport in the tab order when a scroll area overflows, which is a second tab stop immediately before the tab list, in a pattern whose whole point is one. TabList scrolls itself instead, with a thin native scrollbar that appears only when there is somewhere to scroll.
  • D4's open item was not real. The outcome recorded that a sliding indicator “has to travel inside the scroller, so the bar's offset is measured against the scrolled content”. It needed no code: the indicator is a child of the scroller and Base UI measures --active-tab-left against that same element, so the bar scrolls with the tabs for free.
  • onValueChange had to admit null. Under-specified rather than wrong: Base UI reports the set as having nothing active when the active tab is removed or disabled and no enabled tab can replace it. Typing the callback as (value: Value) => void would have been a lie, so it takes Value | null and controlled callers write (next) => next && setValue(next).
  • D3 did not anticipate that end joins the accessible name. A tab reading <Tab end={<Token>12</Token>}>Alerts</Tab> was announced as “Alerts12”. Fixed with a whitespace text node before the slot: it is not rendered as a flex item, so nothing moves on screen, and the name becomes “Alerts 12”. Worth knowing that whatever goes in a slot is read out, not decoration.
  • A disabled tab is focusable. Arrow keys land on it; it cannot be activated. That is the composite-widget convention rather than an oversight — skipping it would hide from a keyboard user that it exists — but nothing in the document said so, and the first test written against it asserted the opposite.
  • flex: none on the tab is load-bearing for D4. Without it the tabs shrink to fit, nothing ever overflows, and the scroller never scrolls. It is commented in tabs.css.ts because it does not look like a scrolling concern.

What the decisions got right

D1's late reversal paid for itself immediately: the AlongsideOtherContent story — a button beside the strip, a message above the panels — is three lines of JSX and needs nothing from the component, which is exactly what the three-part shape would have made impossible. D2 and D3 built as described with no surprises.

Questions for a future proposal

  • Horizontal overflow in ScrollArea. The mask and the reserved gutter are vertical-only by 0007 §04. If that is lifted, TabList should compose with it rather than keep its own scroller.
  • The indicator after SSR. renderBeforeHydration is off, so the bar lands one frame late. Turning it on means a script in the document head, which is a cost this component should not take on a caller's behalf alone.
  • A size ramp. One size ships. A second has to be sm | md | lg matching ButtonSize, and a tab strip has no shared control height to derive from — the same open question 0002 D1 left behind.
