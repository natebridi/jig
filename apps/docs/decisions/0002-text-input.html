Jig · decision 0002

Text Input

The first component built on Base UI, and the first that has to line up with something already shipped. Most of it follows from decision 0001 — what is left is a control-height ramp the system does not yet have, and how much of Base UI's Field becomes our public API.

01Context

Decision 0001 settled the foundation: a component that needs managed focus, portalling, or an ARIA relationship beyond a label is built on Base UI. A text input needs the label, description, error and validity relationships, so it qualifies — it is built over Field and Input from @base-ui/react at ~1.7.0.

What 0001 did not settle is the thing that actually makes this hard. Button has a size prop of sm | md | lg, but its height is derived from padding, not declared — button.css.ts sets padding and fontSize per size and lets the box fall where it falls. There is no control-height token, so there is nothing for an Input to line up against. Measured from the source, at a 16px root:

One more measured fact that decides D1. Button sets border: none; an input has a visible border. The reset sets box-sizing: border-box globally (packages/styles/src/reset.css.ts), so a border does not inflate a box whose height is declared — but it absolutely does inflate one whose height comes from padding. Copying Button's padding onto an input yields a control 2px taller than the button beside it.

Already settled

  • Built on Base UI. 0001 D2, behaviour test.
  • @base-ui/react at ~1.7.0, in dependencies. 0001 D1 and D4.
  • Base UI is not re-exported. Consumers import from @jig-ui/react only.
  • No as prop. Polymorphism stays on layout and typography components.
  • No spacing props. Margin comes from the parent; width goes through style.
  • Sizes are sm | md | lg, matching ButtonSize.
  • Focus uses focusRing from packages/components/src/focus-ring.ts.
  • Styling is a recipe() in input.css.ts, and the ref forwards to the HTMLInputElement.

Specimens below are built from the real token values, so heights and colours are exact. They render in this document's system sans rather than Work Sans, so letterforms are indicative only.

02Decisions

Accept one option per decision, or reject the whole set and leave a note.

D1 · control-height

The control-height ramp

This is the decision the whole component turns on, and it sets a precedent for every control after it — Select, Combobox, Textarea, Date picker. A search bar puts an Input and a Button on the same row; if their heights disagree by even 2px it reads as broken.

Each specimen shows a real md button beside the Input that option would produce, on a shared baseline.

Mirror Button exactly

Recommended

size.control = 1.69 / 2.41 / 2.65rem — Button's rendered heights, tokenised

  • Button can adopt the same token later with zero visual change, since the values are its current output.
  • Locks in the irregular ramp — the 3.8px md → lg step becomes system-wide truth.

  • Input and Button visibly disagree at lg from day one, and fixing it means refactoring Button, which is out of scope.
  • Ships a known misalignment to buy elegance the user cannot see.

No height token

  • No new tokens, and the smallest possible change.

Decided · 2026-08-15 Mirror Button exactly. A size.control ramp of 1.69 / 2.41 / 2.65rem, which is what Button renders today.

Reviewer's note, verbatim: "Tokenize the heights, but I'll want to tweak those values later so they aren't such odd values."

Worth recording precisely, because the tweak is not a token edit. These values align with Button only because they are Button's computed output; changing them moves Input off Button unless Button moves with it. So "tidy the numbers later" is the same piece of work as regularising Button's size ramp, already logged in section 03 — one future proposal covering both, not two. The token is the thing that makes that proposal a single edit rather than a hunt through every control.

D2 · field-surface

How much of Field is public

Base UI's Field is a set of composable parts — Field.Root, Field.Label, Field.Control, Field.Description, Field.Error, Field.Validity. They wire up the id, aria-describedby and validity relationships that make the label, hint and error text actually associated with the control. The question is how much of that composition our consumers see.

Decided · 2026-08-15 Props on one component. Field is composed inside Input; its parts are not exported.

Reviewer's note, verbatim: "Yes, I always want to make it as easy as possible to implement components. If someone wanted direct access to all those parts, they'd use BaseUI directly."

That reasoning generalises past this component, so it is the standing rule for the system: ease of use beats expressiveness at our layer, because the expressive layer already exists underneath. Future components should be proposed on that basis rather than re-arguing it.

D3 · validation-source

Where validity comes from

Base UI's Field tracks validity itself and exposes it as data attributes on the control — data-invalid, data-valid, data-dirty, data-touched, data-filled, data-focused. The decision is whether our styling reads those, or whether we carry our own React state alongside.

Base UI data attributes

Recommended

input.css.ts selects on what Field already sets

selectors: {
  '&[data-invalid]': {
    borderColor: color.control.invalidBorder
  },
  '&[data-disabled]': { … }
}

  • No duplicated state, so our styling cannot disagree with the field's real validity.
  • It is what we are paying Base UI for, and it works with native constraint validation and with Form-level server errors alike.
  • Styling stays entirely in CSS, which matches how every other component here is built.
  • Ties our stylesheet to Base UI's attribute names — a rename in a future minor is a silent visual break, which is exactly what 0001's tilde range is guarding against.

Our own invalid prop

A recipe variant we control

variants: {
  invalid: { true: {
    borderColor: color.control.invalidBorder

  • Insulated from Base UI's attribute names, and obvious to a consumer reading the props table.
  • Two sources of truth. A field can be data-invalid by native validation while our prop says otherwise, and the border will lie.
  • Re-implements the part of Field we adopted Base UI to get.
Decided · 2026-08-15 Base UI data attributes. input.css.ts selects on data-invalid, data-disabled and the rest; we hold no validity state of our own. The named risk stands: an attribute rename in a future Base UI minor is a silent visual break, which is what the ~1.7.0 range from 0001 D4 is there to contain.

D4 · control-colours

Colour tokens for controls

An input needs colours a button never did: a border, a placeholder, a filled surface, and an invalid state. The existing vocabulary is color.button.{variant}.{base-bg, hover-bg, active-bg, disabled-bg, text, disabled-text}, generated by buttonSet() in packages/tokens/src/utils.ts. Whatever we add should extend that shape rather than invent a second naming style — the question is who owns it.

Decided · 2026-08-15 Shared control set, color.control.*, generated by a controlSet() helper alongside buttonSet().

Reviewer's note, verbatim: "Add active state of blue border (same blue as primary button)." Added to the set above as active-border, aliased to {color.blue.450} — the same primitive color.button.primary.base-bg resolves to, so the two cannot drift apart.

Resolved — and it is a system rule, not an Input detail. Raised on review: the component would otherwise also spread focusRing, which paints a 2px black outline at :focus-visible, and a text input matches :focus-visible on click as well as on keyboard focus, so both would show at once. Reviewer's ruling, verbatim: "The active border is the focus state for text fields, and other field-like components. The ring is for things like buttons, links, or other components that don't have an existing outline that we can highlight."

So: a component that already draws a border highlights that border on focus and does not spread focusRing. A component with no border of its own gets the ring. Input therefore does not import focusRing at all, and Select, Combobox and Textarea will follow the same rule when they land. Recorded in the proposal checklist so it is asked of every future component.

One consequence worth noting: because D1 declares the control height, border thickness no longer affects geometry. A focused border can be 2px instead of 1px at zero layout cost, which a 1px colour swap cannot match for visibility. Built as a 1px colour change, faithful to the ruling — the thicker option is available whenever it is wanted.

03Deliberately not decided here

  • Regularising Button's size ramp. If D1 lands on mirroring, the irregular md → lg step becomes system-wide. That is worth its own proposal, and it is a refactor of a shipped component — explicitly out of scope for now.
  • Textarea, and multi-line. Shares the colour set but not the height ramp. Separate component, separate document.
  • Adornments — icons or buttons inside the control. There is an adorn module in the repo already; how it composes with a Base UI Field is a question for after this ships.

04As built

Built 2026-08-15. pnpm turbo typecheck test passes — 12 tasks, 46 tests, 8 of them new for Input — and the packed-consumer test installs, type-checks and resolves the tarball in isolation.

Files

  • packages/tokens/src/semantics/size.ts — new. size.control.{sm,md,lg}, computed from the same primitives button.css.ts uses rather than typed as literals, so the derivation is visible: 1.69 / 2.41 / 2.65rem.
  • packages/tokens/src/utils.ts — controlSet() alongside buttonSet().
  • packages/tokens/src/semantics/color-{light,dark}.ts, semantics/index.ts, build.ts — wiring. The resolver's foundation set lists its sources explicitly, so a new token group is invisible until it is added there too.
  • packages/components/src/input/ — input.tsx, input.css.ts, input.stories.tsx, input.test.tsx, index.ts; exported from src/index.ts.
  • packages/components/package.json, vite.config.ts — see the finding below.
Found in the build — 0001 D1 argued from a false premise The declaration gate was never the forcing function, and the real one pointed the other way.

0001 D1 reasoned that "wrapper components will re-export Base UI prop types, so Base UI will appear in the emitted declarations, and verifyDeclarations() will demand it be resolvable by the consumer." That did not happen. InputProps extends React's InputHTMLAttributes, not any Base UI type, so no Base UI type reaches the declarations at all and the gate had nothing to say.

What actually forced the question was the opposite problem. vite.config.ts externalised only react and react-dom, with a comment recording the intent that "the published package has no runtime dependencies" — so the first build inlined 42 KB of Base UI into dist/index.js (81.8 KB → 39.8 KB once fixed) while the new dependencies entry also made consumers install it. The worst of both: paid for twice, and a consumer using Base UI directly would have got two copies of its React context with certainty rather than by chance.

Resolved by externalising @base-ui/react and its subpaths in the bundle, which is what makes D1's decision real rather than nominal. But this changes a repo-wide property that predates 0001 and was never discussed: @jig-ui/react is no longer a zero-runtime-dependency package. That trade was implicit in accepting "Runtime dependency", and the 10.43 MB figure in D1 was presented and accepted — but the architectural commitment behind the config comment was not on the table. It deserves its own decision if it is to stand.

Smaller gaps in the proposal
  • The dark arm of the control set was never shown. D4's specimen listed light values only, so the nine dark aliases were chosen at build time and have had no review. They follow buttonSet()'s conventions (active-border tracks the primary button's fill per theme, invalid-border tracks danger's), but on a dark surface {color.red.500} sits at the same lightness as {color.gray.500} border it replaces, which may read weakly. Worth a look before another control adopts the set.
  • size collides with a native attribute. <input size> means "width in characters", so InputProps needs Omit<…, 'size'>. Every future control with a size ramp hits this; Button did not, because <button> has no such attribute.
  • Focus is styled with :focus, not a data attribute. D3 decided Base UI owns validity; focus is native and reliable, so [data-invalid] is the only Base UI attribute the stylesheet depends on. That is a smaller coupling than D3's risk note assumed.
  • The external error channel is Field.Root invalid, passed as undefined rather than false when absent — false would assert validity and override the browser's own constraint validation, which is exactly what D3 decided not to do.
