Smoke as glass

Swapping the smoke button's blur(4px) for a refracting SVG filter. The brief asked how to get that filter onto the page once, and only when it is needed. Measurement turned up a better answer than any of the ways of doing it in JavaScript — and a nastier problem than the one that was asked about.

Parked · 2026-09-04 Not being worked on. Left open rather than decided.

Parked the day it was written, on the grounds recorded in the Context section: the effect is Chromium-only, cannot be feature-detected, and an unresolvable reference silently removes the blur rather than falling back. 01Context

smoke is Button's variant for controls over imagery or video. Today it is a translucent veil plus backdrop-filter: blur(4px), in button.css.ts. Its fills are the one colour set in Jig built from literal oklch with an alpha channel rather than palette aliases — smokeButtonSet in packages/tokens/src/utils.ts — because an alias cannot carry alpha. None of that changes here; this is about the filter alone.

Everything below was measured in Chrome against the supplied filter rather than recalled. Where something could not be measured, it says so.

The filter works — and only in Chromium

backdrop-filter: url(#lg) renders the supplied filter correctly in Chrome. It is not supported in Firefox or Safari: both implement backdrop-filter but ignore SVG filter references. That is not folklore — it is an open entry against MDN's own compatibility data (mdn/browser-compat-data issue 24110, “SVG filters not supported in Firefox or Safari”) and a standing request on Mozilla Connect. MDN's compat table for backdrop-filter has no sub-feature for url(), so the property reads as broadly supported while this particular value is not.

And it cannot be feature-detected. CSS.supports('backdrop-filter','url(#lg)') returns true in Chrome because the value parses; a browser that parses it and renders nothing answers the same way. So @supports is not a route to a fallback. D2 is what to do about that.

The measurement that decides D1

The brief's question — embed the SVG once, and not at all when no smoke button is on the page — assumes the filter has to be an element in the document. It does not. A filter can be referenced from a stylesheet by URL, and the browser handles both halves of the requirement on its own. Three reference forms, tested:

With the rule .smoke { backdrop-filter: url(lg.svg#lg) } present in the stylesheet from first paint, counted at the server rather than in the page — the Resource Timing API does not report SVG filter fetches at all, which is why the first attempt at this measurement read zero in both cases and was thrown away:

The problem nobody asked about

A backdrop-filter whose url() cannot be resolved does not fall back — it wins the cascade and renders nothing. Measured with a missing id and with a missing file, both after a perfectly good blur(6px) on the line above:

Already settled by precedent

  • The fills do not change. color.button.smoke.* stays as it is, literal oklch with alpha, for the reason recorded in utils.ts: an alias cannot carry an alpha channel.
  • The filter is the component's, not the caller's. No prop exposes it, tunes it, or turns it off — the same rule that keeps icon sizing inside Button.
  • Whatever ships is guarded by prefers-reduced-motion? No — and deliberately. The filter does not animate; it is a static distortion. The guard belongs on transitions, and there is none here.
  • No new dependency. This is CSS and an SVG asset; nothing is installed, and @base-ui/react is untouched.
  • No new tokens. A filter is not a colour, a space or a type step, and Jig has no category for it — it lives in button.css.ts beside the variant it belongs to.
  • Theming stays :root-scoped, and the light and dark smoke fills already differ; the filter itself is achromatic and needs no theme variant.

02Decisions

Every specimen below is a real button over a real backdrop with the real filter applied — so this page only demonstrates the effect in a Chromium browser. In Firefox or Safari the glass specimens will show a plain veil, which is itself the thing D2 is about.

D1 · filter-delivery

How the filter reaches the page

The brief's actual question. The measurement above changes what the options are: the browser will already embed it once and only on demand, if the filter is a file rather than an element.

An SVG asset the CSS points at

Recommended

Specimen — what ships, and what the consumer does

packages/components/dist/
  styles.css
  smoke-filter.svg

  backdropFilter:
    'url(./smoke-filter.svg#lg)'

the consumer
  import '@jig-ui/react/styles.css'
  // nothing else: no provider,
  // no element, no mount effect

measured
  no smoke button
    → 0 requests
  one, or many
    → 1 request, cached
  • Answers both halves of the brief without a line of JavaScript, and without Jig growing its first singleton, ref count or DOM injection.
  • SSR-safe by construction: there is nothing to render, so nothing to get wrong on the server or hydrate on the client.
  • Nothing for a consumer to forget. The failure mode of the other two options is a smoke button that silently has no effect.
  • A second file has to ship and resolve. files in package.json already covers dist, but the relative URL resolves against the stylesheet, so a consumer who inlines or relocates the CSS without the asset breaks it.
  • Cross-origin rules apply. A stylesheet on a CDN referencing the SVG beside it is fine; a stylesheet copied to another origin without the asset is not — and that failure is silent, which is exactly what D2 has to cover.

A component the app renders once

Specimen — what the consumer writes

app root, once
  <SmokeFilter />
  <App />

renders
  <svg width="0" height="0">
    <filter id="jig-smoke">…</filter>
  </svg>

forget it, and every smoke button
loses its effect with no error
  • No asset resolution, no relative URLs, no cross-origin question. The filter is in the document by construction.
  • Explicit — a reader of the app root can see that the design system needs this.
  • A new kind of contract for Jig. Nothing in the library today asks the consumer to render anything, and the checklist has no category for “you must mount this once”.
  • Forgetting it fails silently and only on the pages with a smoke button. That is a bad failure to debug and impossible to type-check.
  • Still pays for itself on pages with no smoke button, unless the consumer conditionally renders it — which is the very bookkeeping the brief wanted to avoid.

Button injects it, ref-counted

Specimen — what Button would have to do

let count = 0, node = null

useEffect(() => {
  if (count++ === 0) {
    node = makeFilterSvg()
    document.body.append(node)
  }
  return () => {
    if (--count === 0) node.remove()
  }
}, [])

first DOM injection in Jig
first module-level state
no "use client" anywhere
  • Zero consumer action and exactly the requested semantics: present when a smoke button is, absent when none is.
  • No asset, no URL resolution.
  • Everything about it is a first for Jig: DOM injection, module-level mutable state, and an effect whose job is a side effect on document.
  • Hostile to server rendering, and Jig ships no "use client" directives — so this would push a client-only requirement into a package that has never had one.
  • A ref count under React 19's strict-mode double-invocation and concurrent unmounts is a genuine source of bugs, in exchange for what the browser already does for free.

D2 · degradation

What happens where the filter does not work

Three ways this ends up unsupported or unresolvable: Safari, Firefox, and a stylesheet that loaded without its SVG. All three produce the same thing, and the measurement above showed it is not “falls back to blur” — it is no backdrop effect at all. A smoke button over a photograph with no blur is the exact failure the variant exists to prevent.

Blur on the element, glass on a pseudo

Recommended

Specimen — third button's filter is deliberately unresolvable

the broken one is still blurred — the blur is on the element, not the pseudo

  • Measured: an unresolvable reference on the pseudo-element cannot touch the element's own blur. Safari and Firefox get exactly today's smoke button, so nothing regresses.
  • Needs no detection at all, which matters because the feature is not detectable.
  • Covers the 404, the cross-origin block and the offline first paint as the same case, rather than three separate ones.
  • A pseudo-element and an isolation: isolate on every smoke button, for an effect most of its users will never see.
  • Two stacked backdrop filters in Chromium rather than one, which is more work per frame, not less — and D3 has no measurement to say how much.

One declaration, accept the loss

Specimen — second button's filter is deliberately unresolvable

the broken one has no blur at all — this is what Safari gets

  • The simplest possible change: one property in button.css.ts, no pseudo-element, no stacking context.
  • One backdrop filter per button rather than two.
  • Regresses Safari and Firefox from a working blur to nothing — visible in the second specimen, and the majority of non-Chromium traffic.
  • Makes a missing asset a visual failure on every smoke button rather than a lost enhancement.

D3 · scope

Whether smoke changes, or a variant joins it

Not measured The frame cost of this filter is unknown, and this document could not measure it.

Frame timing needs requestAnimationFrame to run, and the automated browser available here never brings a tab to visibilityState: "visible", so rAF is starved and every harness reads zero. A harness is written and ready — open it and call run() to get median, p95 and worst frame times for 1, 6 and 24 buttons, blur versus glass, over a moving backdrop.

What can be said without measuring: feTurbulence with numOctaves="3" is the expensive primitive here, a backdrop-filter re-runs whenever the backdrop moves, and each button filters its own backdrop region — so cost scales with the number of smoke buttons on screen, not with the page. Worth knowing too: the first two primitives depend only on each other and never on SourceGraphic, so the noise is a static texture that could be baked to an image and fed in with feImage. That is the obvious optimisation if the numbers come back bad, and it is not proposed here because there is nothing yet to justify it.

Which makes this the hedge: if the cost turns out to matter, does it fall on everyone already using smoke, or only on callers who opt in?

Change smoke in place

Recommended

Specimen — the variant list stays as it is

variant="smoke" — same name, better effect

  • No new name to learn, no second variant that does almost the same thing, and every existing smoke button improves at once.
  • Keeps ButtonVariant at five, which the api types test already pins.
  • With D2's layering the change is purely additive — nothing that works today stops working.
  • If the filter turns out to be expensive, the cost lands on every existing caller with no way to decline short of a revert.
  • A caller who wanted the plain blur has no route back.

A sixth variant beside it

Specimen — the two side by side

two variants, and a caller has to know which to reach for

  • Opt-in, so an expensive effect can never be a surprise regression for an existing caller.
  • Both treatments stay available, which is useful if the glass reads badly over some imagery.
  • Two variants whose difference is invisible in Safari and Firefox, where they would render identically. A name that means nothing in half of browsers is hard to document honestly.
  • Grows the variant vocabulary for an effect, where the existing five name loudness. glass would be the first variant named after a texture.

D4 · tuning

How strong the distortion is at button size

The supplied filter was presumably tuned on something larger than a 38px-tall button. At this size baseFrequency="0.8" with scale="20" displaces by roughly half the control's height, which reads as static rather than as glass — and the label sits on top of it. The three settings below are the same filter chain with the turbulence and displacement turned down; everything else is identical.

The second plate in each specimen is a one-pixel stripe pattern, which is the honest test: fine detail is where refraction either looks like glass or looks like noise.

As supplied

Specimen — 0.8 / 3 octaves / scale 20

exactly the filter in the brief

  • The most obviously glassy of the three, and unmistakably an effect rather than a blur.
  • No retuning — ships what was asked for.
  • At button size the displacement is a large fraction of the control, so the backdrop is scrambled rather than refracted, and over fine detail it reads as television static.
  • Three octaves of turbulence is the most expensive of the three, on an effect whose cost is not yet measured.

Softened

Recommended

Specimen — 0.4 / 2 octaves / scale 8

same chain, larger noise cells, a third of the displacement

  • Reads as a warped pane rather than as noise, which is what the brief asked for in words.
  • One fewer octave and a smaller displacement radius, so it is the cheaper of the two visible effects.
  • The label stays comfortably legible over the fine-stripe plate, which is the case that matters for a control.
  • Less dramatic; on a plain backdrop it is close enough to the existing blur that some viewers will not notice a change at all.
  • Retuned by eye here rather than derived from anything, so the numbers are a starting point, not a system.

Barely there

Specimen — 0.18 / 1 octave / scale 4

one octave, minimal displacement — a slight lensing at the edges

  • Cheapest by a distance: one octave of turbulence and a small displacement.
  • Never competes with the label, at any backdrop.
  • Hard to justify the whole apparatus — an external asset, a pseudo-element and a Chromium-only feature — for something this close to the blur it replaces.
  • Most viewers would not be able to tell it from today's smoke button in a side-by-side.
