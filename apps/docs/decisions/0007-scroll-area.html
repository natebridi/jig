Jig · decision 0007

Scroll Area

A scrollable region with a scrollbar Jig draws rather than the platform. Proposed on its own rather than inside Dialog, because Dialog's inside-scroll pattern — title and actions pinned, body scrolling — is built on it, and a scrollbar designed as a detail of one component is a scrollbar that has to be redesigned for the next.

All four are decided. D1 was rejected once and rebuilt: it had wrongly treated reserving a gutter and revealing the bar on demand as alternatives, when what was wanted was both.

01Context

Nothing in Jig scrolls today. CodeBlock scrolls horizontally with a native bar and that is the whole of it. Dialog needs more: a long dialog should keep its title and its actions on screen while the body moves, which means an inner scroll region that is styled, that says whether it is at its top or bottom, and that does not change size when a platform decides to show a bar.

Base UI 1.7.0 — the range 0001 D4 pinned at ~1.7.0 — ships ScrollArea as Root / Viewport / Content / Scrollbar / Thumb / Corner. It hides the native scrollbar, tracks the scroll metrics, and publishes them as data attributes and custom properties. What it does not do is decide what any of it looks like, and that is what this document is for.

Already settled by precedent

  • Base UI, per 0001 D2's behaviour test. A scroll area tracks scroll metrics, computes thumb geometry, handles drag, and manages a touch-modality edge case in WebKit where momentum scrolling dispatches no events. That is behaviour, not styling, and it is already written.
  • Keyboard focus is Base UI's, and it is already right. The viewport carries tabIndex={0} only while it actually overflows, and -1 otherwise (viewport/ScrollAreaViewport.js:281), so a scrollable region is reachable by keyboard without a non-scrolling one adding a stray tab stop. Nothing for Jig to add, and nothing to get wrong.
  • The native scrollbar is hidden by Base UI, not by us — the viewport carries its own styleDisableScrollbar class and overflow: scroll inline.
  • One component, not six parts. 0002 D2's rule: the pieces are props rather than composable parts, because anyone who wants to assemble them by hand is better served by Base UI directly. Five of ScrollArea's six parts are invariant boilerplate, so <ScrollArea>{children}</ScrollArea> renders the lot.
  • Both axes, each hiding itself. Base UI unmounts a scrollbar whose axis does not overflow unless keepMounted is set. Jig takes that default; there is no orientation prop to get wrong.
  • Height is the caller's. A scroll area scrolls because something constrains it. That constraint goes through style or a flex parent, not a prop — box dimensions are not props.
  • No as prop, no spacing props, and the standard file set with an export from src/index.ts.
  • Scrollbar width is spacing.300 — 0.45rem, 7.2px — which lands in the usual 6–10px band for a drawn scrollbar without inventing an off-ramp value. The thumb takes radius.500 (7px), which at that width is a capsule.
  • Nested scroll areas are not designed for. Neither is a horizontal scroll area inside a vertical one; the corner part renders but nothing is designed against it.

What Dialog needs from it

Recorded here so the decisions below are answerable rather than abstract. Dialog (0008) will wrap Base UI's Dialog.Viewport for positioning and put a ScrollArea inside Dialog.Popup for the body. From this component it needs exactly three things:

  • A body that scrolls while the title and the action row stay put.
  • A way to draw a rule under a pinned title only once the body has been scrolled, so a short dialog has no spurious line across it. That is D2 and D4.
  • A scrollbar that does not shift the body's text when it appears. That is D1.

02Decisions

Every specimen below is a working scroll area — native bar hidden, thumb positioned from the scroll metrics, the same 16px minimum thumb and 500ms idle timeout Base UI uses. Scroll them.

D1 · scrollbar-presence · revised

What sits in the reserved gutter at rest

Revised after rejection — 2026-08-25 The first draft offered three options and argued that reserving a gutter and fading the bar were mutually exclusive — “a bar that fades cannot also hold a gutter open; an empty reserved strip is worse than either.” That was asserted, not shown, and it is wrong.

Rejected with: “Reserve area and fade in on hover and focus.” The two are orthogonal. Reserving the gutter buys the things reserving is for — no reflow when a region becomes scrollable, and no thumb sitting on top of the text — and none of that requires the bar to be painted while nobody is looking at it.

D2 settles the objection that drove the original recommendation. The case against fading was that a cropped body would look uncropped to a touch user who never produces a hover. With the gradient mask accepted, the content itself carries that signal permanently and on every input type, so the scrollbar no longer has to. The two decisions were argued separately and should not have been.

So the gutter is reserved — spacing.300, 7.2px — and the bar reveals on hover, on focus within the area, and on scroll. Focus matters because Base UI puts the viewport in the tab order whenever it overflows, so a keyboard user can land inside a scroll region and needs to see what they landed in. Scroll is the addition to the note: it is the only trigger a touch user ever fires, and it is what Base UI's data-scrolling attribute and its 500ms timeout exist for.

What is left open is what occupies the reserved strip while none of those are true. All three specimens below reserve the same width and reveal on the same three triggers. Tab into them, hover them, and scroll them.

Nothing at rest

Recommended

Clean until hovered, focused or scrolled

7.2px reserved · nothing painted at rest · the note, exactly

  • Exactly what was asked for, and the quietest of the three — a dialog at rest has no chrome down its right edge at all.
  • No reflow and no thumb over the text, which is the whole reason to reserve.
  • Nothing to keep in contrast at rest, so the track colour question in D3 only has to hold up while the bar is actually visible.
  • The reserved strip reads as asymmetric padding rather than as a rail, so the body text looks slightly off-centre in its box until something reveals the bar.
  • Gives the least indication of where to aim before the pointer arrives — you hover the general area and the thumb appears somewhere in it.

A painted track

The rail is permanent; the thumb is what fades

7.2px reserved · track at scrollbar.track · thumb reveals

  • The reserved space is legible as a scrollbar rail rather than as stray padding, which is the one real cost of the option above.
  • Says “this region scrolls” permanently and on every input type, without the thumb being painted over the text’s edge.
  • A permanent vertical line down every scrolling surface, including short ones inside a dialog where it is the loudest thing on the panel.
  • Reintroduces most of what the note was rejecting — the bar is still always there, only emptier.

A dimmed thumb

Always locatable, never loud

7.2px reserved · thumb at 35% · full on reveal

  • Keeps position information visible at rest — you can see how far down you are without touching anything, which neither of the others gives you.
  • The reveal is a strengthening rather than an appearance, so nothing moves or materialises under the pointer.
  • An opacity that is not a token. 35% is a number chosen by eye, and it has to hold against both themes and every surface a scroll area can sit on.
  • Dimmed-but-present is the least decisive of the three: too faint to rely on, too visible to be absent.
Decided · 2026-08-25 Nothing at rest. The gutter reserves spacing.300 (7.2px) so the body never reflows and the thumb never sits over the text, and the bar is painted only while the area is hovered, has focus within it, or is being scrolled. At rest a scroll area shows no chrome at all — the gradient mask from D2 is what says the content is cropped.

This resolves the contingency in D3. No option that paints a permanent rail was chosen, so color.scrollbar.track has no consumer and is not shipped: the set is thumb and thumb-hover only. Add track if a future surface needs a visible rail, rather than shipping a token nothing reads.

Build obligation. The reveal is three triggers, not one: :hover, :focus-within — Base UI puts the viewport in the tab order whenever it overflows, so a keyboard user can land inside a scroll region and must see what they landed in — and Base UI's data-scrolling, which is the only one a touch user ever fires. Missing the third makes the scrollbar invisible to touch entirely.

D2 · edge-affordance

What marks the cropped edge

A scrollbar says how much there is. It does not say where the content is cut, and in a Dialog those are different questions — the crop falls between a pinned title and the body, which is exactly the seam a reader needs drawn. Base UI publishes the two distances as pixel values precisely so this can be styled rather than guessed.

Whichever is chosen must appear only when scrolled. A short dialog with a rule across it, or a fade over content that is entirely visible, is worse than no treatment at all. Each specimen has a pinned header and footer so it is judged in the arrangement it exists for.

Hairline on the scrolled edge

Recommended

Rules fade in as you leave each end

Terms of service
Accept · Decline

1px · color.control.border · opacity from data-overflow-y-*

  • Draws the seam where it actually is — between the pinned row and the moving one — which is the thing a reader needs to understand the layout.
  • Obscures no content. Every character stays legible at full contrast.
  • Works on any background, because a line does not have to blend into one. A mask has to.
  • Less literally expressive than a fade: it marks the boundary rather than suggesting continuation.
  • One more rule to keep in step with whatever border the header already draws, or the two double up.

Gradient mask fade

Base UI's own example, on the real custom properties

Terms of service
Accept · Decline

mask-image · 28px ramp · clamped by --scroll-area-overflow-y-*

  • Reads as continuation rather than as a boundary — text visibly runs on past the edge, which is unambiguous.
  • Self-scaling: the ramp shortens as you approach either end, because it is clamped by the remaining distance.
  • Fades the content itself. The top line of a scrolled dialog is partly transparent, which is a legibility cost paid continuously.
  • mask-image on a scrolling element forces it onto its own compositor layer; on a long body that is a real cost, and it interacts badly with anything sticky inside.
  • Only works when the surface behind is flat — the fade goes to transparent, not to the popup's colour, so a patterned or image background shows through.

Nothing beyond the scrollbar

The bar is the only signal

Terms of service
Accept · Decline

no edge treatment · smallest surface

  • Nothing to build, nothing to keep in step, and no opinion imposed on a consumer who wants their own treatment.
  • The data attributes are still published by Base UI, so a caller can style the edge themselves without the component having chosen.
  • Leaves Dialog to solve it, which is how a scroll detail becomes a Dialog detail — the thing splitting this proposal out was meant to avoid.
  • A pinned header floating directly above moving text, with no seam, reads as a rendering error more than as a layout.
Decided · 2026-08-25 Gradient mask fade. Not the recommendation. The viewport carries a mask-image clamped by --scroll-area-overflow-y-start and -end, so the ramp shortens to nothing as each end is reached. The scrollbar is a sibling of the viewport rather than a child, so it is not masked with the content.

This accepts the three costs the option names: the top and bottom lines of a scrolled region are partly transparent; mask-image puts the scrolling element on its own compositor layer; and the fade goes to transparent rather than to a colour, so it only reads correctly over a flat background. Build obligation — state that last one in the component's documentation, because a ScrollArea placed over a patterned surface will show it through and the failure will not look like a ScrollArea bug.

It also changed D1. The argument for an always-painted scrollbar was that otherwise nothing tells a touch user the region is cropped; the mask now does that permanently and on every input type, which is why D1 was reopened rather than re-recommended unchanged.

D3 · scrollbar-colour

Where the scrollbar's colours come from

A drawn scrollbar needs a thumb colour, a hover colour, and — if D1 keeps the gutter — a track. The question is whether that is a set of its own or whether it borrows from color.control.*, which already carries a border and a hover border for every field-like control.

The two render differently, and the difference is legible below: control borders are tuned to sit quietly around an input, which is a step lighter than a thumb wants to be to read as a grabbable object.

A color.scrollbar set

Recommended

track warm.100 · thumb warm.300 · thumb-hover warm.400

3 tokens × 2 themes · hover the thumb

  • A thumb is a control you drag, and it can be tuned to read that way rather than inheriting a value chosen to be unobtrusive.
  • The same shape the system already uses for component-scoped colour — color.button.*, color.control.*, color.token.* — built with a small util beside them.
  • Retuning input borders later cannot silently restyle every scrollbar.
  • Three more semantics per theme for one component, before a second consumer exists.

Borrow color.control.*

border warm.200 · hover-border warm.300

0 new tokens · one step lighter than the set above

  • No new tokens, and the checklist's standing instruction to compose before adding.
  • A scrollbar inside a bordered surface matches the border around it exactly, which is one fewer grey in the system.
  • Visibly fainter, as above. An input border is drawn to recede; a thumb has to invite a drag.
  • Borrows a name that means something else. control.border on a thing that is not a border and not a control is the kind of alias that reads as a mistake in a year.
  • No third value, so a painted track would have to borrow again from somewhere else.
Decided · 2026-08-25 A color.scrollbar set. Three semantics per theme — track, thumb, thumb-hover — generated beside buttonSet, controlSet and tokenSet in packages/tokens/src/utils.ts.

One of the three was contingent on D1, and D1 settled it. track is only painted by an option that keeps a permanent rail, and “nothing at rest” does not. The set ships as thumb and thumb-hover; track is dropped rather than shipped unread.

D4 · overflow-state-api

How a parent reacts to scroll position

D2 draws the edge inside the scroll area. Dialog may want it outside — a rule belonging to the pinned title rather than to the body, so it spans the popup's full width including the gutter, and sits with the header's own padding. For that, something outside the scroll area has to know it has been scrolled.

Base UI already puts data-overflow-y-start and data-overflow-y-end on both Root and Viewport. The question is only whether Jig re-publishes that, adds a JavaScript channel alongside it, or leaves it at the DOM.

Data attributes only

Recommended

The parent styles a descendant selector — no React state

  <ScrollArea class="body">…</>
</div>

dialog.css.ts — the title's rule
selectors: {
  '&:has(~ .body[data-overflow-y-start])':
    { borderBottom: `1px solid ${line}` },
}

no callback, no re-render,
no state to keep in sync
  • Zero API. The attributes exist whether or not anyone reads them, so this option costs nothing to ship and cannot be wrong.
  • No re-render on scroll. A callback firing on every frame of a drag is a real cost in a dialog with a form in it.
  • The state is on the DOM node that owns it, which survives the value being read by CSS, by a test, or by a devtools inspection.
  • A consumer who genuinely needs the value in JavaScript — to disable an Accept button until the terms are scrolled to the bottom — has to reach for a MutationObserver or their own ref.

  • Public API added speculatively. No consumer needs it yet: Dialog's rule is a border, and a border is CSS.
  • Invites the mistake it looks like it solves — a caller putting scroll position in React state and re-rendering a dialog body on every scroll.

Decided · 2026-08-25 Data attributes only. No onEdgeChange. Base UI's data-overflow-y-start and -end are re-published on the ScrollArea root, and a parent that wants to react — Dialog drawing a rule under its title — does it in CSS with :has(). Nothing re-renders on scroll.

Revisit trigger, recorded rather than built: a consumer that needs the value in JavaScript, such as gating an Accept button on having read to the bottom.

03The API, as built

04Deliberately not proposed

  • A ScrollArea.Content equivalent. Base UI's Content part is optional and exists for state propagation; a single component renders it internally or not at all. Nothing is exposed.
  • Scroll position control. No scrollTo, no defaultScrollTop. A ref to the root plus querySelector is unpleasant, so if this is wanted the honest answer is an imperative handle, and that deserves its own decision rather than a prop bolted on here.
  • Horizontal-only styling. The horizontal scrollbar renders and works — it is Base UI's — but nothing in Jig is designed against it yet, and CodeBlock keeps its native bar until something asks otherwise.
  • The corner. Rendered, unstyled beyond the track colour. Both axes overflowing at once is not a layout Jig has.
  • Shadow-based edge affordances. An inset shadow at the cropped edge was considered and dropped: it reads as depth on a surface that has none, and Jig has no elevation vocabulary to draw on.
  • Overscroll behaviour. overscroll-behavior: contain inside a Dialog stops a scroll chaining to the page behind. That belongs to Dialog's modal handling, not here.

05As built

Built 2026-08-25. pnpm turbo typecheck test passes — 12 tasks, 136 tests across 15 files, 6 of the tests new — and the packed-consumer test installs and type-checks the tarball in isolation. The three reveal triggers, the mask and the focus ring were driven in a real browser, because none of them exist in jsdom.

Files

  • packages/tokens/src/utils.ts — new scrollbarSet, beside buttonSet, controlSet and tokenSet. Two tokens, not three, per the D1/D3 outcome.
  • packages/tokens/src/semantics/color-light.ts, color-dark.ts — scrollbar: scrollbarSet(theme). The resolver validates 424 tokens across both themes, up from 422.
  • packages/components/src/scrollarea/ — new. Component, styles, stories, tests, index.ts, exported from src/index.ts.
  • packages/components/src/refs.test.tsx — the ref lands on the root, not the viewport.
  • packages/components/scripts/packed-consumer-test.mjs — the dangling-var check is now fallback-aware. See below.
  • apps/playground/src/App.tsx — a scrolling area, a short one, and the pinned title/actions arrangement Dialog will compose.

What the proposal got wrong

  • data-scrolling does not exist. The Context figure listed it among the attributes Base UI publishes, and D1's outcome named it as the reveal-on-scroll mechanism. It is never emitted: the root's stateAttributesMapping maps the overflow booleans and explicitly drops cornerHidden, and has no entry for scrolling at all. Three DataAttributes enums in the package name the string, which is where the claim came from, but nothing writes it. The decision is delivered by reading state.scrolling through Base UI's function-form className — a documented API — rather than from the DOM. Verified in the browser: the bar carries three classes during a scroll and two 500ms after it stops.
  • height: 100% on the viewport silently breaks the obvious way to size one. It is what Base UI's own examples use, and it only resolves against a parent with a definite height. A caller writing style={{ maxHeight: '20rem' }} — the natural thing, and what the proposal's own API section shows — got a viewport sized to its content, no overflow, no scrollbar, and a scroll area that quietly did not scroll. The root is a flex column instead, with the viewport at flex: 1; min-height: 0, which works for a max-height, a fixed height and a flex parent alike. Same automatic-minimum-size trap that Stack hit.
  • The mask eats the focus ring, and the proposal never considered the two together. A mask applies to everything an element paints, its outline included — and the viewport is the element that takes focus. A ring drawn on it fades out at exactly the two edges the mask touches, so the focus indicator is faintest where the mask is strongest. Confirmed by moving the ring onto the viewport and looking: the left and right sides render at full strength, the top and bottom segments disappear entirely. The ring is drawn on the unmasked root instead, through &:has(.viewport:focus-visible), with the viewport's own outline suppressed.
  • “Reserve the gutter” did not say which axis. Only the vertical bar reserves. A strip along the bottom of every scroll area, held open for a horizontal bar that §04 says nothing in Jig is designed against, costs more than the reflow it would avoid — so the horizontal scrollbar overlays. Worth revisiting if a horizontal scroll area is ever designed.

What it taught

  • The packed-consumer guard was too blunt, and this was the first legitimate failure. It flagged every var() whose custom property is not declared in styles.css, which caught the two --scroll-area-overflow-y-* references Base UI writes onto the element at runtime. A reference carrying a fallback cannot render as nothing, which is the only failure the check exists to catch, so it now scans for a top-level comma and ignores those. Its teeth are intact: a bare var(--jig-not-a-token) still fails the run, which was checked by introducing one.
  • Base UI classifies programmatic scrolls as non-user and suppresses the scrolling state. A scroll driven by scrollTo rather than by wheel, key or pointer will not reveal the bar — the flag is cleared by onWheel, onPointerMove, onPointerEnter and onKeyDown on the viewport. Defensible, and it is the reason browser automation that scrolls without dispatching a wheel event shows no reveal at all. Anything that scrolls a region for the user and wants the bar seen has to solve that separately.
  • Both the root and the viewport carry role="presentation", so a test selecting the viewport by role silently gets the root. Reached structurally instead.
  • Accurate everywhere else. The gutter width, the two-token colour set, the mask clamped by the published distances, the CSS-only edge API, and Base UI's tabIndex handling all went in as written.
