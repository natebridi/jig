Jig · decision 0017

Structured List

Columns of content laid out like a table on a wide screen and stacked with their labels on a narrow one. The brief says layout only, no interaction — but “laid out like a table” and “reflows to stacked” are the two requirements that fight each other in the accessibility tree, and that is what most of this document is about.

Superseded in part by 0018 (2026-09-07). That document moves with to the cell (revising D4), replaces the shared grid template with flex rows and a columnWidths array, and makes a cell take its label from the column heading with label only as an override (revising D2's contract). D1 and D3 stand unchanged — the ARIA roles and the caller-set layout prop are what 0018 builds on. Nothing below has been edited; the decisions read as they were made.

01Context

Jig has nothing that lays content out in columns with a header. Grid distributes children across 24 tracks but knows nothing about rows, headers or labels; ListItem (0014) is one row of start–label–end and does not align anything with the row above it. This is the first component in the system that is tabular.

Carbon's Structured List, which the brief names, ships selectable and unselectable variants; the brief takes only the unselectable one. That removes rows from the tab order, removes aria-selected, and removes every keyboard question — so none of Carbon's interaction model is in scope here.

The requirement that fights itself

A table that reflows loses its table semantics. Setting display: block (or flex, or grid) on a <table> removes it from the accessibility tree as a table in many screen readers, and the row and cell relationships go with it — the markup stays valid, the announcement does not. This is long-documented rather than folklore: Adrian Roselli and Steve Faulkner both catalogue it, and Mozilla has carried bug 1005271 for it since 2014. Safari fixed its share in version 17; the pattern of the problem has not gone away.

The accepted repair is to put the roles back explicitly — role="table", rowgroup, row, columnheader, cell. Which is the fact that shapes D1: once every role has to be written out anyway, the <table> element itself is buying much less than it looks like it is.

What “labels to the left” implies

Stacked, each cell shows its column's label beside it. That label is the header cell from the top of the column, so every cell has to be able to reach its own column's header text. That is not a styling detail — it decides the API, which is D2. A component whose children are opaque ReactNode cannot know which column a cell is in.

Already settled by precedent

  • Hand-rolled, not Base UI. 0001 D2's test — managed focus, portalling, or an ARIA relationship beyond a label — is met by none of these. The brief removed interaction, so there is nothing to manage.
  • with names a Typography preset and defaults to body01, built from the shared typeStyles map imported from typography.css.ts rather than restated — exactly as Collapsible (0013 D2) and Link (0009 D3) do. The brief asks for this directly. What is open is only its scope, in D4.
  • Flat component with slot props, not compound parts — Dialog (0008), Collapsible (0013), SideNav (0014).
  • No spacing props; spacing comes from the parent, and box dimensions go through style.
  • Consumer props reach the root, which extends HTMLAttributes and spreads — the correction recorded in 0013's As built.
  • No as prop. 0014 D2 widened that rule to ListItem and its two-element union specifically; the checklist's new wording makes that framing the bar, and a Structured List does not clear it — the element it renders is D1's business, not the caller's.
  • Rules between rows use color.line, not color.control.border. 0012 D3 separated the two so a divider and a field border can move apart.
  • Ships .tsx, .css.ts, .stories.tsx, .test.tsx, index.ts, plus the export from src/index.ts; theming stays :root-scoped.

02Decisions

Specimens are real markup at real token values. The reflowing ones respond to the width of the specimen frame rather than the window, so they can be seen stacking inside a narrow option column — which is D3's subject as well as its medium.

D1 · semantics

What a screen reader hears

The brief calls this layout, not data. But it also says “laid out similar to a table” with “an optional header row”, and a header row is a claim about meaning: it says the cells beneath it are all the same kind of thing. Whether to make that claim in the accessibility tree is the decision.

Real <table>, roles re-applied

Recommended

Specimen — the markup

<table role="table">
 <thead role="rowgroup">
  <tr role="row">
   <th role="columnheader">Plan
 <tbody role="rowgroup">
  <tr role="row">
   <td role="cell">Starter

announced
 table, 3 columns, 4 rows
 Plan, column 1 — Starter
  • Correct with CSS on or off. If the stylesheet fails to load, it is still a table; if the reflow strips implicit roles, the explicit ones hold.
  • Column and row counts are announced, and header association comes free — a screen reader reads “Plan: Starter” without the component doing anything.
  • The elements document themselves. A reader of the DOM sees a table and knows what it is.
  • The roles are redundant in every browser that gets it right, and redundant ARIA is the kind of thing that rots — a future reader cannot tell whether they are load-bearing.
  • Table elements are the most constrained in CSS. display: contents on rows, subgrid, and reflow all interact awkwardly with them.

Divs carrying ARIA roles

Specimen — the markup

<div role="table">
 <div role="rowgroup">
  <div role="row">
   <div role="columnheader">Plan
 <div role="rowgroup">
  <div role="row">
   <div role="cell">Starter

announced — the same
 table, 3 columns, 4 rows

unless a role is dropped, and then
nothing is announced at all
  • Total freedom in CSS: grid, subgrid, container queries and reflow all behave normally, because none of the elements carry table layout rules.
  • One source of semantics rather than two, so nothing is redundant and nothing rots.
  • Every role is load-bearing and unenforced. Miss one role="row" and the whole structure collapses in the tree with no visual sign.
  • Rule one of ARIA is to prefer the native element. Choosing divs for a genuinely tabular structure argues against the grain, and needs the layout freedom to be worth it.

No table semantics at all

Specimen — the markup

<div>
 <div><span>Plan</span>…
 <div><span>Starter</span>…

announced
 Plan Requests Price
 Starter 10,000 Free
 read straight through, in DOM order

no counts, no column association,
no table navigation
  • Honest to the brief's own framing — “limited to only layout” — and the simplest thing that can work.
  • Nothing to get wrong and nothing to maintain; the reflow question disappears because there are no semantics to lose.
  • Right for the cases where the content genuinely is not tabular: a spec sheet, a summary panel, a pair of stacked facts.
  • The header row becomes decoration. A sighted reader gets column headings; a screen reader user gets an undifferentiated run of words, and has no way to tell which heading a value belongs to.
  • Refuses the one thing a header row is for. If the answer is that the content is not tabular, the component probably should not have headers either.
Decided · 2026-09-07 Divs carrying ARIA roles — against this document's recommendation. role="table", rowgroup, row, columnheader and cell on plain elements, with no <table> underneath them.

The layout freedom is what this buys, and D3's outcome is what spends it: a component that switches between a grid and a stacked block on a prop is exactly the case where table elements fight back. Taking both decisions together, this is the coherent pair.

The cost recorded against it stands and is now a build requirement. Every role is load-bearing and none is enforced by the element — miss one role="row" and the structure collapses in the accessibility tree with no visual sign. The component must emit them all itself, never accept them from a caller, and the tests must assert the full tree (getByRole('table'), columnheader, cell) in both layouts rather than only checking that the text renders.

D2 · api-shape

How the columns and rows are expressed

The stacked layout needs each cell to know its column's label, so the component has to be able to associate the two. That rules out the shape where children are opaque and pushes towards data, or towards making the caller repeat themselves.

Jig has precedent for both. Combobox takes items and groups as data (0011); SideNav takes composed children (0014). The question is which fits a grid whose cells must line up across rows.

the label is on the column, so every

  • The label lives in exactly one place and every cell can find it — which is what makes the stacked layout possible at all.
  • Column count and alignment are structural, so cells cannot drift out of line and a missing cell is detectable.
  • Matches Combobox's items, the existing precedent for a component that owns a repeated structure.
  • Cell values stay ReactNode, so a Token, a Link or an Icon still drops in.
  • Verbose for two rows of static content, which is a real share of the uses — a spec panel becomes a data structure.
  • Per-cell control (a span, an alignment, a className) needs somewhere to go, and object-shaped props grow awkwardly.

  • Terser than either neighbour for the common case, and the label is still written once.
  • Rows stay elements, so a caller can map over data or write them out by hand.
  • Association is positional. A row with cells in the wrong order is mislabelled when stacked, and looks fine when wide — the worst kind of bug.
  • Passing children through a component that reads their props means either cloning elements or a context, both of which are more machinery than the data option it is trying to avoid.
Decided · 2026-09-07 Composed children, with the cell named StructuredListCell. The note, verbatim:

“I want to call it StructuredListCell, but follow this pattern. This is best because it allows for content that isn't expressed as a string, like a link, icon or other components.”

So three exports: StructuredList, StructuredListRow, StructuredListCell — the full name on each, matching SideNav / SideNavSection rather than a bare Cell that would collide with anything else in a consumer's scope.

One correction to the record, since the archive should not carry it wrong. Both shapes could hold non-string content — the data-driven option's fourth pro says its cell values stay ReactNode, so a Token, a Link or an Icon drops into either. What composition actually buys is writing that rich content inline rather than inside an object literal, and having somewhere natural to put per-cell props later. The choice stands; the reason in the record is the stronger one.

The two costs this option was marked down for are now build requirements: the column label is written on both the header and every cell beneath it, so the component should warn in development when a cell's label matches no column; and nothing enforces equal cell counts per row, so a short row should warn too. Both are the warnInDev pattern Dialog and SideNav already use.

D3 · reflow-trigger

What decides when it stacks

The brief says “on smaller screens”. Every specimen in this document stacks on its own width instead — which is why they can be seen reflowing inside a narrow option column while the window stays wide. That difference is the decision. Narrow the window to see the first option behave; the second and third are already stacking.

Decided · 2026-09-07 A layout prop the caller sets — against this document's recommendation. layout?: Responsive<'columns' | 'stacked'>, through the existing responsiveConditions, so no container query enters the system and there stays exactly one way to express “responsive” in Jig.

Default: {{ xs: 'stacked', md: 'columns' }} — the value the option's own specimen carried, and the one that matches the brief's “stacked on smaller screens” without the caller writing anything. A caller who wants one layout at every width passes the bare string.

The cost the option was marked down for is accepted knowingly: placed in a sidebar or a dialog, the list stays in column mode at exactly the widths where it does not fit, and the caller has to hand-tune the breakpoint per placement. The stories should show that case rather than only the full-width one.

The decision this document is about, reappearing one layer down

D1 chose ARIA roles because display changes strip table semantics. The first draft of the stacked layout then hid the header row with display: none — which does exactly the same thing to the columnheader elements, leaving an ARIA table whose cells have no headers to associate with. The comment above the line said why that would be wrong; the line did it anyway.

The header row is now moved off-screen with a zero-area clip instead, so the roles are identical in both layouts. Verified in a browser rather than argued:

What the decisions did not settle

  • The visible label had to be hidden from assistive technology. D1's prose raised it as a concern and no option resolved it: stacked, every cell shows its column's name and the columnheader announces the same word, so a screen reader reads “Plan Plan Starter”. The label carries aria-hidden="true" — it is a visual repeat of something already in the tree.
  • How rows line up was never specified. Three ways to make cells share columns: display: contents on the row (drops its box, and has a history of dropping the element from the accessibility tree with it), subgrid nested through both rowgroups, or giving every row the same template. The last one is what shipped — columns align because they are the same fractions of the same width. With ARIA roles carrying the entire structure, anything that risks those roles is the wrong trade.
  • A headerless list had no column count. The brief made headers optional but nothing said where the count comes from without them. It now falls back to counting the first row's cells, with an explicit columns prop as the escape hatch when the children cannot be introspected — a mapped array inside a fragment, say. The introspection is best-effort by design and warns rather than guesses.
  • The row rule was in the wrong place. A border on each cell is cut into one segment per column by the column-gap between them, which reads as three underlines rather than one line under the row. Moved to the row, which is the grid and spans the gaps.
  • process is not reachable outside dev.ts. The dev warnings walk every row and cell, which is worth skipping in production — but the narrow process declaration is module-scoped, deliberately, so the package never pulls in Node's globals. Added isDev() beside warnInDev rather than redeclaring it, which is the rule that module exists to enforce.

Found after the fact, on the playground

The default layout was broken and every test passed. Put on the playground page, layout={{ xs: 'stacked', md: 'columns' }} — the default — rendered with no header row and doubled row spacing at every width.

The cause is particular to the marker-class pattern: a responsive value puts both markers on the same element, and the wider one only wins on the properties it actually sets. The columns branch set display on the header row; the stacked branch set the whole off-screen clip. So at md the header became display: grid while staying absolutely positioned at one pixel square, and the stacked row padding survived underneath the columns cell padding. Both branches now declare the same property set, with a comment saying they have to be kept in step.

Why the tests did not catch it, which is the more useful half. jsdom applies no stylesheet and evaluates no media query, so a unit test cannot see either marker — and the tests that do exist pass layout as a single string, which puts one marker on the element and never creates the collision. The component was verified through the accessibility tree, which was correct throughout; the layout was only ever verified by looking at it. Any future responsive marker pair in Jig has the same hole.

What the decisions got right

D1 and D3 turned out to be a pair. Because the structure is roles on plain elements, switching between a grid and a stacked block is a class swap with nothing to work around — the layout freedom D1 was marked down for buying is exactly what D3 spends. D2's composed shape made the rich-cell story trivial: a Token, a Link and an Icon go into cells without being described first. And D4's weight override behaves as its outcome predicted — the header tracks the cells at any preset, so with="caption01" gives a small list with a small bold header rather than a mismatch.

Questions for a future proposal

  • The container query D3 declined. Its accepted cost is now visible in a story: InANarrowContainer puts two lists side by side at 17rem, where the default still says columns and only the one told layout="stacked" reads properly. That story exists to make the cost checkable rather than theoretical.
  • The columns prop is a symptom. It exists because reading child props is best-effort. A context would make the count, the column labels and the cell-position checks exact — and Jig still has no context anywhere, which is a decision worth making deliberately rather than by accumulation.
  • Nothing validates cell order. The warnings catch a wrong cell count and a label matching no header, but a row whose cells are in a different order from the headers is silently mislabelled when stacked and looks correct when wide — the failure mode D2's hybrid option was rejected for. Composed children have the same hole, one step further along.
