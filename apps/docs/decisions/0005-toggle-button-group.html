Toggle Button Group

Ported directly from Base UI. No new item component and no group styling — ToggleButton itself becomes the child, which means rewriting it over Base UI's Toggle. That is a refactor of a shipped component, and the decisions below are about what it costs.

01Context

A group of toggles needs roving tabindex, arrow-key navigation and a shared value — behaviour ToggleButton cannot coordinate across siblings. That clears 0001 D2's behaviour test, so the group is @base-ui/react's ToggleGroup at the ~1.7.0 range 0001 D4 pinned.

Revised before decision — 2026-08-17 The first draft proposed a separate ToggleButtonGroup.Item, on the grounds that ToggleButton could not be the child. Two claims behind that were wrong.

First: it said Base UI's Toggle throws outside a group. It does not. useToggleGroupContext() is a bare useContext returning undefined with no guard, and Toggle branches on it — standalone it runs useControlled over pressed/defaultPressed, which is exactly ToggleButton's current semantics; in a group it derives pressed from groupValue.indexOf(value) > -1 and calls setGroupValue. One component, both modes, already built.

Second: D3 claimed a generic Value would type-check each item's value prop. It cannot. React children are opaque ReactNode, so a parent's type argument never reaches them — no arrangement of these components can catch a typo'd item value at compile time. That claim is removed from D3 below, which changes its argument substantially.

So ToggleButton is rewritten over Base UI's Toggle and becomes the group child directly. Confirmed against package/toggle/Toggle.js in the installed 1.7.0.

Already settled

  • No new item component. Direct instruction. ToggleButton is the child of ToggleButtonGroup.
  • ToggleButton is rewritten over Base UI's Toggle, which is what makes one component serve both modes. Authorised explicitly: "I'm open to changes in ToggleButton if that is what is required."
  • No dedicated group styling. The group is an unstyled ToggleGroup div; items keep the exact button({ color: 'ghost', pressed, size }) class they render today, shared with IconButton.
  • The icon still swaps weight on press — regular to fill, and pressedIcon where given. Inside a group the pressed state lives in Base UI, so this reads it through Toggle's render prop rather than local state. A CSS-only approach cannot do it: the two weights are different SVG paths, not a style.
  • value is added to ToggleButton, optional in the type. It is required in practice inside a group, and Base UI logs a development error when it is missing — but the type cannot express "required only when nested", so the runtime warning is the check.
  • disabled merges: the group's disabled state ORs with the item's, which Base UI already does.
  • Orientation and loopFocus pass through unchanged from Base UI's defaults.

02Decisions

All three are API questions. Specimens are code, not renders.

D1 · select-mode

Single- vs multi-select as an API

Base UI expresses both through one component and a multiple boolean, with the value always an array. The value's meaning changes shape underneath that boolean, which a boolean cannot reflect in the type.

One component, multiple

Recommended

Mirrors Base UI exactly

<ToggleButtonGroup defaultValue={['bold']}>
  <ToggleButton value="bold">Bold</ToggleButton>
  <ToggleButton value="italic">Italic</ToggleButton>
</ToggleButtonGroup>

<ToggleButtonGroup multiple defaultValue={['bold']}>
  …

value is always Value[] — single-select
is "an array of at most one"
  • Literally the port that was asked for — same shape as Base UI's docs, so their examples transfer.
  • Switching a group from single to multi-select is one prop.
  • onValueChange always hands back an array, so the common "which one is selected" case reads value[0] at every call site.

Two components

Value type matches the mode

<ToggleButtonGroup defaultValue="bold">
  // value: string | undefined
  <ToggleButton value="bold">Bold</ToggleButton>
</ToggleButtonGroup>

<MultiToggleButtonGroup defaultValue={['bold']}>
  // value: string[]
  <ToggleButton value="bold">Bold</ToggleButton>
</MultiToggleButtonGroup>

same child either way
  • The type at each call site matches what is being modelled; single-select stays a single value.
  • Costs less than it did in the first draft — the item is shared now, so this is two wrappers, not two wrappers and two items.
  • Two components to export, test and document for what Base UI treats as one prop, and a name to invent for the second.
  • A redesign of Base UI's API rather than the port that was asked for.
Decided · 2026-08-17 One component, multiple. ToggleButtonGroup takes the boolean and the value is always an array, matching Base UI exactly. Callers reading a single selection take value[0].

D2 · cancel-contract

How a handler vetoes a toggle

This is the one real casualty of the rewrite. ToggleButton today documents and tests that an onClick handler calling preventDefault() cancels the toggle (togglebutton.test.tsx, "lets a handler cancel the toggle with preventDefault"). Base UI's Toggle does not read defaultPrevented at all — it calls onPressedChange(next, details) first and checks details.isCanceled.

Left alone, that test fails and every existing preventDefault call site silently starts toggling.

Adopt details.cancel()

Recommended

Base UI's own mechanism, surfaced on our prop

<ToggleButton
  onPressedChange={(pressed, details) => {
    if (!allowed) details.cancel();
  }}
>Bold</ToggleButton>

works identically inside a group —
cancelling also vetoes the group commit

// breaking: this no longer cancels
onClick={(e) => e.preventDefault()}
  • The mechanism designed for the job, and the only one that also vetoes the group value commit — preventDefault could never do that.
  • No dependence on the order Base UI merges a consumer's onClick against its own, which is internal behaviour that could change in a minor.
  • Breaking. A documented, tested contract changes, and the failure mode is silent — the toggle just starts moving.
  • Migration is mechanical but must be found by hand; nothing type-errors.

Preserve preventDefault

Bridge it onto details.cancel() internally

// inside ToggleButton
onPressedChange={(next, details) => {
  if (details.event.defaultPrevented) {
    details.cancel();
    return;
  }
  onPressedChange?.(next);
}}

consumer code is unchanged:
onClick={(e) => e.preventDefault()}
  • Nothing breaks. The existing test passes untouched and no call site moves.
  • Keeps our public surface free of Base UI's details object, which 0001 settled consumers should not have to know about.
  • Depends on Base UI merging the consumer's onClick before its own, so that defaultPrevented is already set when it reads it. That ordering is undocumented, and a silent break if it changes.
  • Leaves no way to veto a group commit, since preventDefault carries no signal Base UI reads.

Support both

Bridge preventDefault, and pass details through

onPressedChange?: (
  pressed: boolean,
  details: ToggleChangeDetails
) => void

preventDefault still cancels,
details.cancel() also cancels

two ways to do one thing,
both documented forever
  • No break, and the group-veto case is reachable for anyone who needs it.
  • Two mechanisms for one job, and the weaker one silently does less inside a group than outside it.
  • Carries both of the other options' costs: the ordering dependency and Base UI's object on our surface.
Decided · 2026-08-17 Adopt details.cancel(). onPressedChange gains a second argument and preventDefault on onClick no longer vetoes a toggle.

This is a breaking change with a silent failure mode, which is the reason it is recorded rather than left to the implementation. Obligations on the build:

  • The existing test — "lets a handler cancel the toggle with preventDefault" — is rewritten against details.cancel() rather than deleted, so the veto behaviour stays pinned under its new mechanism.
  • The repository is swept for onClick handlers on ToggleButton that call preventDefault; nothing type-errors, so they have to be found by reading.
  • The gain is recorded too: cancelling now also vetoes the group value commit, which preventDefault could never reach.

D3 · value-typing

How strictly the group's value is typed

Base UI's ToggleGroup<Value extends string> is generic, so value, defaultValue and onValueChange can be narrowed to a union.

What it cannot do — corrected from the first draft — is check the items. React children are opaque ReactNode, so a ToggleButton's value is never compared against the group's union no matter how this is arranged. A typo'd item value is a runtime mismatch under either option, which removes the main argument for the generic.

Stay generic

Recommended

<Value extends string = string>, same as Base UI

<ToggleButtonGroup
  defaultValue={['bold']}
  onValueChange={(v) => { // v: ('bold'|'italic')[] }}
>

inferred from defaultValue —
rarely written by hand

// still not checked, either way:
<ToggleButton value="blod" />
  • The handler and any state fed from it are narrowed, so a switch over the value is exhaustively checked.
  • Adding it later is a breaking type change; adding it now costs nothing at call sites, since it is inferred.
  • A generic in the props table for a benefit that stops at the group's own boundary.

Plain string

value: string throughout

<ToggleButtonGroup
  defaultValue={['bold']}
  onValueChange={(v: string[]) => { … }}
>

simplest possible surface

// not checked here either:
<ToggleButton value="blod" />
  • Nothing generic to read or explain, which matters more now that the item-checking benefit turned out not to exist.
  • Consumers who want narrowing can still assert at their own boundary.
  • A switch over the returned value is never exhaustive, and adding the generic later breaks anyone who wrote an explicit annotation.
Decided · 2026-08-17 Stay generic. <Value extends string = string> on the group, inferred from defaultValue in the common case.

Accepted on the narrower case that survived the correction: it narrows onValueChange and anything fed from it, so a switch over the value is exhaustive. It does not check item values, and the component's documentation should not imply that it does.

03The API, on the recommended set

04Deliberately not proposed

  • A segmented or connected visual treatment. Out of scope by instruction — items keep their normal radius and spacing, with no shared border or overlap. A future proposal once a real toolbar exists to design against.
  • Vertical orientation styling. orientation="vertical" passes through for free, but nothing here designs for a column.
  • Requiring value by type inside a group. Not expressible — the type cannot know it is nested. Base UI's development-mode error is the check.
  • Applying the same treatment to Button. ToggleButton moves onto Base UI here; Button, IconButton and the shared recipe are untouched.

05As built

Built 2026-08-17. pnpm turbo typecheck test --force passes — 12 tasks, 82 tests across 10 files, 12 of them new — the packed-consumer test resolves the tarball in isolation, and two groups are in the playground.

Files

  • src/togglebutton/togglebutton.tsx — rewritten over Base UI's Toggle; gains value, and onPressedChange gains the details argument.
  • src/togglebuttongroup/ — new. Component, styles, stories, tests, exported from src/index.ts alongside ToggleChangeDetails.
  • apps/playground/src/App.tsx — a single-select and a multi-select group.
  • No new tokens, and no change to button.css.ts. A grouped and an ungrouped toggle render the identical class.
A test passed for the wrong reason, and hid a real bug The first rewrite spread consumer props onto the element inside render, after Base UI's own — which replaced its onClick outright.

Any consumer passing onClick would have got a button that no longer toggled at all. It went unnoticed at first because the old preventDefault test still passed — not because the veto worked, but because Base UI's handler had been discarded and nothing happened either way. A green test asserting the absence of an effect cannot tell "correctly cancelled" from "completely broken".

Fixed by passing consumer props to Toggle instead, so Base UI merges handlers rather than being overwritten by them. A regression test now presses a button that carries its own onClick and asserts both that the handler ran and that the toggle moved.

"No group styling" needed one line of layout after all Read literally, it produced a bare div whose buttons flowed as inline boxes with whitespace between them.

The group carries display: inline-flex and a flex-direction taken from orientation — the same axis it already declares to assistive technology. Nothing decorative: no gap, no border, no radius, no background. Callers wanting spacing pass a className, which is also how a segmented treatment would arrive later without changing this file's contract.

Flagged rather than assumed: this is a judgment call inside a settled item, and if "no styling" was meant to include layout, deleting the file is the change.

Smaller findings
  • ToggleChangeDetails is declared locally, not re-exported. It names the two members worth calling — cancel() and event — while the object passed at runtime is Base UI's richer one. That keeps 0001's rule that consumers never import Base UI types, and it costs nothing because the structural subset satisfies the callback position.
  • value had to be omitted from the inherited button attributes. ButtonHTMLAttributes already declares a native value, which would have silently merged with the group identity of the same name.
  • The migration surface was exactly one file. A sweep for preventDefault on ToggleButton found only the test itself — no playground or story call sites — so D2's breaking change cost one rewritten test in practice.
  • The proposal's API sketch used icons that do not exist. Section 03 showed icon="text-b" and icon="text-italic"; the curated set has neither. Corrected above to star and eye.
  • exactOptionalPropertyTypes is on repo-wide, so an optional prop rejects an explicitly-passed undefined. It surfaced spreading Storybook args into a component with an explicit type argument, and it is worth knowing before writing the next generic component.
