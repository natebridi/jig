Jig · decision 0014

Sidebar navigation

Three components — a generic row, a section, and the nav that holds them. Most of it follows from precedent. What does not is a hard constraint in the HTML spec: the brief asks for a row that is entirely a link and that can hold a button, and those two things cannot both be true of the same element.

  • 2026-09-04

01Context

Twenty-one components in, Jig has nothing that lays out a row. Every list-like arrangement in the playground and in Storybook is a hand-composed Stack direction="row", which is fine once and drift by the fourth time. It also has no way to say you are here: no selected state, no aria-current, and no colour for either.

The brief is a docs sidebar, built from a generic [start]–[label]–[end] row that other things can reuse. So the row is the piece worth getting right; the section and the nav around it are mostly composition.

The constraint everything else bends around

The brief asks for two things that HTML does not allow together: “the entire item can be a link… although remember the start end items can be interactive as well”. Both quotes below are from the WHATWG HTML Standard, fetched rather than recalled.

Jig has met this exact collision once already. 0011 D3 decided “Jig Tokens as the chips” for the multiple Combobox, and the build found that Token owns a remove button while Combobox.ChipRemove is also a button and is the only one wired to the combobox's removal. Nesting them is invalid HTML, so the chip wears Token's styles and the button inside it is Base UI's. That is recorded in 0011's As built, and it is the same problem one document earlier — which is why it is a decision here rather than something to discover during the build.

Base UI, checked against 0001 D2

Registry rather than memory: npm view @base-ui/react reports 1.7.0 as the latest version and the only dist-tag, with no deprecated field. It is already pinned at ~1.7.0 in packages/components/package.json, so nothing installs either way.

Base UI does ship a NavigationMenu, and it is not this. Its parts are Root, List, Item, Content, Trigger, Portal, Positioner, Viewport, Backdrop, Popup, Arrow, Link, Icon — a menu bar that opens portalled popups. The one part that looks useful in isolation, NavigationMenuLink, cannot be used in isolation:

Two things the brief names that Jig does not have

The brief lists “avatar, icon, text, image, button, token, etc.” as slot content. Jig has Icon, Token, Typography and IconButton; it has no Avatar and no Checkbox. Both would be caller-supplied markup today. That is not a blocker — the slots take ReactNode, so anything renders — but it does mean the avatar and checkbox cases below are drawn with hand-rolled stand-ins, and neither is proposed here. Base UI ships an Avatar (Root / Image / Fallback) whenever that becomes its own document. Superseded in part by D1's outcome: the checkbox is no longer a start candidate at all — that slot renders inside the anchor and therefore takes non-interactive content only.

Already settled by precedent

Everything here follows an existing rule and is not up for debate in this document. Listing it is what keeps the decision count honest.

  • Hand-rolled, not Base UI. 0001 D2's behaviour test, with the source above as the evidence. No new dependency, and none of the three components portals, traps focus, or needs an ARIA relationship beyond a label.
  • aria-current="page" marks the current item. It is what Base UI's own NavigationMenuLink sets and what the APG disclosure-nav pattern specifies. Only the colour is open, in D3.
  • Flat components with slot props, not compound parts — Dialog (0008), Collapsible (0013). So <ListItem start={…} end={…}>, not <ListItem.Start>.
  • The slots take ReactNode and reserve a fixed-width box so labels line up down the column. What goes in the box is the caller's; the box is the component's — the same division buttonIconSize establishes.
  • SideNav renders <nav> and takes an accessible name; a second nav on the same page needs its own aria-label.
  • Header and footer are pinned and the item list scrolls between them, in a ScrollArea — the arrangement Dialog already uses (0008 D3) and which the playground demonstrates.
  • No as prop — polymorphism stays on layout and typography components (polymorphic.ts).
  • No spacing props; spacing comes from the parent, and box dimensions go through style.
  • Consumer props reach the root: each component extends HTMLAttributes and spreads, per ScrollArea and the correction recorded in 0013's As built.
  • Refs type to the rendered element and are asserted in refs.test.tsx.
  • Focus is the ring from focus-ring.ts — none of these draw a field border, so 0002 D4 gives them the ring rather than a border highlight.
  • Any motion is hand-declared with a prefers-reduced-motion guard; Jig has no motion tokens and a duration ramp is its own proposal (0013's As built).
  • Theming stays :root-scoped, and each component ships .tsx, .css.ts, .stories.tsx, .test.tsx, index.ts plus the export from src/index.ts.

02Decisions

Accept one option per decision, or reject the whole set and leave a note. The rows in every specimen are real markup with real anchors and buttons, so hover, focus and the hit areas are the ones being proposed — hover a row to see its clickable region outlined.

D1 · row-interactivity

How a whole-row link lives with interactive slots

The spec quotes above rule out the obvious reading of the brief. A row that is an <a> cannot contain the delete button, the checkbox, or the overflow menu that the end slot is meant to hold. Three ways out, and the choice sets what ListItem can be used for.

Stretched link

Recommended

Specimen — hover a row

  • Getting started
  • Notifications 12

the anchor spreads ::after { inset: 0 }; the button is lifted above it

  • The whole row is the link — the hit target a sidebar needs — while the DOM holds one anchor and one button as siblings. Valid, and one link in the accessibility tree.
  • The trailing button stays reachable by mouse and by tab, because it is a real sibling rather than a descendant.
  • Degrades honestly: a row with no interactive end needs no lifting at all.
  • The overlay eats text selection — a user cannot drag-select the label. Real, and the reason this pattern is wrong for a row of prose.
  • Every interactive thing in a slot must be lifted with position: relative. The component can do that for its own slots, but not for arbitrary ReactNode a caller nests deeper.
  • A positioned ancestor breaks it silently. The overlay escapes the label's overflow: hidden only because that label is position: static, so it is not the overlay's containing block. Giving the label position: relative — for a badge, a tooltip anchor — clips the overlay back to the text. Measured in this page: hit-testing the row's left edge returns the anchor normally, and the bare li once the label is positioned.

Row is the anchor

Specimen — hover a row

  • Getting started new
  • Notifications 12

end slot restricted to non-interactive content — a Token, a count

  • The simplest correct thing. No overlay, no stacking context, no lifting; text selection still works.
  • Impossible to build an invalid row, because the type refuses the case that would be invalid.
  • Refuses a stated part of the brief. No delete button, no checkbox, no overflow menu in a linked row — which is a menu pattern the docs page itself may want later.
  • The refusal can only be documented, not typed: ReactNode cannot express “nothing focusable in here”, so it is a runtime warning at best.

Siblings, no stretch

Specimen — hover a row

  • Getting started
  • Notifications 12

the anchor is the label and nothing more

  • Nothing clever at all. No overlay, no z-index, no rule about what may go in a slot; text selection intact.
  • The hit area is honest — what looks clickable is clickable, and what is not, is not.
  • The row stops feeling like a nav row. Clicking the padding, the icon, or the gap does nothing, which in a sidebar reads as broken.
  • Small targets. In a narrow sidebar the label is most of the row, but on a short label like “API” the target is tiny — a WCAG 2.5.8 problem the other two options do not have.
Decided · 2026-09-04 Siblings, no stretch — with the anchor taking everything that is not the button.

The note, verbatim:

“If the item is a link and has an action, I think it is safe to have the two elements as siblings, but with the anchor encompassing everything that isn't the button. Let's get rid of the checkbox as a ‘start’ element to make that easier. That way nothing interactive can be in the ‘start’, and it can be included with the <a> tag.”

That refinement answers the option's own strongest objection. The specimen above drew the anchor around the label alone, which is what made the targets small; with the start slot and the row's padding inside the anchor, the link is everything up to the button and the tiny-target problem goes with it — no overlay, no stacking context, and text selection intact.

Two rules follow, and they are now part of the component's contract:

  • start takes non-interactive content only. It renders inside the anchor, so a checkbox or button there would be the exact spec violation this decision exists to avoid. Checkboxes are out of the slot vocabulary.
  • end is the only interactive slot, and it is a sibling of the anchor rather than a descendant.

D2 · list-semantics · revised

What element a row renders as

Rejected in the first round. The note: “I don't want to get into full polymorphism, but could we allow ‘as’ with a tightly scoped list of possible elements? Thinking <li> by default, with <div> as an option. I imagine there will be other aria attributes to consider when building a navigation list.”

The first round framed this as a choice between markup shapes and never offered the obvious third thing: let the caller pick, from two. Reframed accordingly. All three options below still put the list semantics on the container — that part was not what was rejected.

This amends a standing rule, so it is worth saying plainly. The checklist reads: “Polymorphic as: layout and typography components only, via the shared PolymorphicProps utility in polymorphic.ts.” ListItem is neither. Options A and B widen that rule; option C is the one that leaves it alone. Whichever is taken, the rule's wording changes with it rather than being quietly contradicted.

On the note's last point — the other ARIA to consider. With a real <li> inside a list, the browser computes position and count, which is what produces “3 of 8”. A <div> chain has to carry aria-setsize and aria-posinset by hand, and only stays correct if every consumer remembers. That is the real cost of the escape hatch, and it is why every option below keeps li as the default rather than the option. aria-current="page" is already settled; the section triggers carry aria-expanded / aria-controls from Collapsible.

as: 'li' | 'div', on ListItem

  • Exactly the two elements asked for, and the default is the one that carries the semantics — so the sidebar is right without anyone choosing.
  • Goes through the existing PolymorphicProps utility, so props and the ref stay correlated to the element; refs.test.tsx already asserts that shape for six components.
  • A two-member union is checkable at a glance and cannot drift into “any element”.
  • Widens a rule that has held since polymorphic.ts was written, and the memory of it. The amendment has to be written into the checklist or it will read as an inconsistency later.
  • Nothing stops as="li" outside a list, which is invalid markup the type cannot catch.

  • Always valid: an li can only appear where a list container put it.

  • Implicit. The rendered element is invisible at the call site, which is the thing the no-polymorphism rule was protecting against in the first place.

Decided · 2026-09-04 as: 'li' | 'div' on ListItem, defaulting to 'li'. Through the existing PolymorphicProps utility, so props and the ref stay correlated to the element — the same route Stack, Grid, Typography and Adorn take. The container still emits <ul role="list">, so the default configuration is the one with full list semantics and nobody has to ask for them.

This amends a standing rule, and the amendment is part of the build. Two places currently say as is for layout and typography components only, and both are now wrong:

  • .claude/skills/propose/checklist.md — “Polymorphic as: layout and typography components only”. It governs the next proposal, so leaving it stale would have the next document contradict this one.
  • The project memory jig-polymorphic-as-prop, which records the 2026-08-14 decision and the instruction not to add as to a new component without asking. That instruction held: it was asked, and this is the answer.

The new wording both should carry: layout and typography components, plus ListItem, whose union is exactly 'li' | 'div'. Polymorphism is still never reopened to arbitrary ElementType, and the correlation tests in api.types.test.tsx and the packed-consumer fixture extend to cover the new union.

The cost accepted with it: nothing stops as="li" outside a list, which is invalid markup no type can catch. And a caller who takes the div escape hatch owns aria-setsize and aria-posinset from then on.

D3 · selected-state · revised

Where the selected icon sits

Rejected in the first round. The note: “Use the ghost button background, but do not use the accent color. Instead, I'd like an additional ‘selectedIcon’ prop (def=false), so I can set an icon that only appears when a item is selected. When selectedIcon is true the space should be preserved so list items line up.”

Two of the three parts are now settled by the note and are not up for debate below: the fill is color.button.ghost.activeBg with no colour change to the label, and the prop is selectedIcon?: IconName | false, defaulting to false. Using activeBg rather than hoverBg keeps selected one step clear of a hovered neighbour; a hovered selected row stays at activeBg rather than moving again.

Jig has already solved the reserving half of this. Combobox's tick does exactly what the note asks for, and the comment in combobox.css.ts is worth quoting because it also records how:

Decided · 2026-09-04 Leading gutter, in front of the start slot. The whole of the selected state, assembled from this round's note and this option:
  • Fill is color.button.ghost.activeBg, one step past the hover fill so selected and hovered stay distinguishable. The label keeps color.text.primary — no accent colour.
  • selectedIcon?: IconName | false, defaulting to false. When set, a fixed-width box sits at the leading edge of every row in the list and the glyph inside it is revealed only on the selected one.
  • Reserved with visibility: hidden, never display: none — the box has to keep its space or the labels shift by a tick's width as the selection moves. Combobox's indicator already does exactly this, and collapsible-style drift is avoided by copying its mechanism rather than inventing a second one.
  • aria-current="page" carries the state; the fill and the tick are decoration.

Two costs go in with it. The gutter plus the start slot puts roughly 2.5em in front of the label, which is a real bite out of a narrow sidebar. And the gutter is reserved per item, so a list where only some rows set selectedIcon will not line up — the stories and prop docs say to set it consistently across a list, because nothing in the type can enforce it.

D4 · section-disclosure

What a collapsing section header is

SideNavSection takes an optional label and can collapse. Jig shipped a Collapsible yesterday, so the reuse question is immediate — and so is the friction, because 0013 D3 chose plus/minus as the disclosure glyph over a rotating caret. In a sidebar section header a caret is the convention and a plus reads as “add an item”.

Collapsible's trigger is also heavier than a section label wants: full width, body01 by default, spacing.400 of vertical padding, glyph at the trailing edge. The specimens put the two side by side at real values.

D5 · item-density

Whether ListItem takes a size ramp

The checklist asks it directly: does this share a control height with other interactive controls? A sidebar row does not sit inline with a Button, so it may opt out — but ListItem is meant to be generic, and a settings row beside an Input is a real future case.

The constraint that decides it: a row's height has to be able to grow with its content. An avatar or an image in the start slot is taller than a line of text, and a fixed height either clips it or has to be retuned per slot.

height falls out of the content, exactly as Button's does

  • Button's own approach — it “derives its size from padding alone” (0002 D1's note), so a row and a button at the same size stay in step without a shared height token.

Row height falls out of the content the way Button's does, so an avatar or an image in the start slot makes the row taller instead of overflowing a fixed box. The names are the ones the checklist requires of any size prop, and md and lg share a vertical step — Button's existing irregularity, inherited deliberately rather than quietly corrected here.

Two collisions with components Jig already had

Both were invisible to the tests and only appeared with the nav on a real page, at a real width.

  • ScrollArea's wrapper fights a truncating label. Base UI's ScrollArea puts a min-width: fit-content wrapper inside the viewport — which is exactly what makes horizontal scrolling work when content really is wider. A nav row wants the opposite: its label is white-space: nowrap so that it can ellipsise, and against a fit-content ancestor the nowrap wins. The list grew to its longest label, so nothing truncated, the trailing end slot was pushed out of sight, and the section disclosure indicators went with it — three symptoms, one cause. Worse, that min-width is an inline style, so no class selector can outrank it; the fix needs !important, scoped to SideNav. Confirmed by reading the rendered attribute rather than inferred.
  • Jig refs are not spreadable between Jig components. Every component declares ref?: Ref<X>, not ref?: Ref<X> | undefined. That is fine while the target is an intrinsic element, and SideNavSection is the first component in the system to wrap another Jig component — at which point exactOptionalPropertyTypes refuses the pass-through: Type 'Ref<HTMLDivElement> | undefined' is not assignable to type 'Ref<HTMLDivElement>'. Worked around with a conditional spread rather than changing the repo-wide convention for one caller.

What the proposal got wrong

Nothing structural — but the same gap 0013 had, and in a way that is worth recording because it points the opposite direction. No decision said what a disabled row looks like, and the first build shipped one that rendered at full contrast with a pointer cursor. The trap is the mirror image of Collapsible's: there, Base UI keeps the trigger focusable and marks it aria-disabled, so :disabled matched nothing; here the row's control is a plain <button disabled>, so the native pseudo-class is right and the attribute selector would have been wrong. Two components, two opposite hooks, and no way to tell which without looking.

What it got right

  • D1 verified by tab order. Walking the rendered nav gives link:Combobox then btn:Remove Combobox — the link and its sibling action, both reachable, in that order. That is the whole decision, and it holds.
  • D3's mechanism transplanted cleanly. Copying Combobox's tick gutter rather than inventing a second one meant the reserving behaviour worked first time: every row holds the gutter, visibility hides the glyph, labels keep one column.
  • D2 cost nothing. The two-member as union went through PolymorphicProps with no friction, and the ref correlates to the element without a cast at the call site.
  • D4's predicted cost was the real one. Its outcome warned that Collapsible's trigger has no horizontal padding and would leave a section header misaligned with its rows. It did. Collapsible exposes no hook for its trigger, so SideNavSection reaches in with a descendant rule on the trigger recipe's base class — the route button.css.ts already takes to position an Icon inside a Button.

Questions for a future proposal

  • A one-axis ScrollArea. The !important above is a scoped patch on another component's internals, which is not where it belongs. A ScrollArea that can be told it only scrolls vertically would fix it properly — and every future consumer that truncates text will want the same.
  • ref?: Ref<X> | undefined repo-wide. One component wrapping another will keep happening now that the system is large enough for it. The conditional-spread workaround is fine once and noise by the fourth time.
  • Avatar. Named in the brief, drawn with a stand-in in every specimen and story here. Base UI ships Root / Image / Fallback, and the start slot is now a real consumer waiting for it.
  • A disabled-state convention. Two components now express disabled two different ways for good reasons on both sides. A line in the checklist saying how to tell which applies would have saved the bug in this build and the one in 0013.
