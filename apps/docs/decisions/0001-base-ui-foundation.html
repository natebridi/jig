Jig · decision 0001

Base UI as a foundation

Interactive components are about to get harder than anything in the system today. This decides whether Base UI carries that weight, on what terms, and where the boundary sits — without touching a single component already built.

  • Decided
  • proposed 2026-08-15
  • decided 2026-08-15
  • 4 decisions

01Context

Everything in packages/components/src/ today is hand-rolled and, with one exception, structurally simple: Button, IconButton, ToggleButton, Icon, Stack, Grid, Typography. The exception is Tooltip, which is the first component to need real interaction behaviour — open/close intent, delays, focus and pointer handling, an aria-describedby relationship, and positioning against a trigger. It runs to a few hundred hand-written lines.

The queue ahead is mostly harder than that: text input, select, combobox, menu, dialog, tabs. Each one carries a focus-management and ARIA burden that is expensive to write and easy to get subtly wrong. Base UI is the proposal for carrying that burden.

One fact shapes several of the decisions below: @jig-ui/react currently has no runtime dependencies at all. Its package.json declares only react and react-dom as peers; everything else is a devDependency. Adopting Base UI ends that, and the build already has a gate that will force the question — verifyDeclarations() in packages/components/vite.config.ts fails the build if any emitted .d.ts imports a package the consumer will not have installed.

All package figures and dates below were read from the npm registry on 2026-08-15 via npm view, against @base-ui/react 1.7.0.

Correction — 2026-08-15 The first draft of this document cited the wrong package. It used @base-ui-components/react, which is deprecated and renamed; its npm metadata reads "Package was renamed to @base-ui/react." Because the old name stopped publishing at 1.0.0-rc.0 in December 2025, the draft read that as a release candidate abandoned for eight months and argued from it.

The live package is @base-ui/react. It reached stable 1.0.0 on 2025-12-11 and has shipped a minor roughly monthly since, most recently 1.7.0 on 2026-08-04. D4 has been rewritten against the real history and D1's dependency figures corrected; D2 and D3 were unaffected.

Already settled

These follow from an existing rule or from an explicit instruction, and are not up for debate here.

  • No existing component is refactored. Direct instruction. Tooltip in particular keeps its hand-rolled implementation.
  • Base UI is unstyled and stays that way. All styling remains vanilla-extract in *.css.ts; Base UI contributes behaviour and ARIA only.
  • Theming stays :root-scoped. Base UI's DirectionProvider and friends do not change that.
  • The as prop rule is unchanged. Polymorphism stays on layout and typography components. Base UI's own render prop is an internal detail of a wrapper, not a new public API.
  • Base UI is not re-exported. Consumers import from @jig-ui/react and should not need to know Base UI exists.

02Decisions

Accept one option per decision, or reject the whole set and leave a note. Only D2 and D3 block the Input component; D1 and D4 are packaging calls that can be revisited more cheaply.

D1 · dependency-shape

How Base UI is depended on

Because wrapper components will re-export Base UI prop types, Base UI will appear in the emitted declarations, and verifyDeclarations() will demand it be resolvable by the consumer. That forces a choice between a real dependency and a peer dependency — the current state, where nothing is installed, is not available.

Total transitive weight either way: 10.43 MB unpacked. Base UI itself is 9.49 MB, with @floating-ui/* (523 KB across four packages), @base-ui/utils (270 KB), @babel/runtime (118 KB) and use-sync-external-store (28 KB) behind it. Its date-fns and @date-fns/tz peers are marked optional in peerDependenciesMeta, so they cost nothing unless a date component is used.

  • Exactly one copy in the tree, so Base UI context always resolves.

  • Leaks the implementation. Dropping Base UI later becomes a breaking change to our install instructions.
  • Adding a required peer to an existing package is itself a breaking change, and the version range becomes a support surface.
Decided · 2026-08-15 Runtime dependency. @base-ui/react goes in dependencies. Base UI stays an implementation detail that consumers never name, and @jig-ui/react gains its first runtime dependency.

Correction from implementation, 2026-08-15. The argument above is wrong about why the choice was forced. No Base UI type reaches the emitted declarations, so verifyDeclarations() never applied. The real constraint was that vite.config.ts bundled Base UI into the output rather than externalising it — making the package install it and ship an inlined copy. Externalising it is what makes this decision real, and doing so ends the repo's zero-runtime-dependency property, which was a deliberate choice recorded in that config and was not on the table here. The decision stands; the reasoning is corrected, and the architectural trade is flagged in 0002's As built.

D2 · adoption-boundary

Where the Base UI boundary sits

"Use Base UI for new components" is too vague to act on consistently. The system needs a written test that decides, for any given component, whether it is built on Base UI or by hand — otherwise the boundary is set by whoever happens to build each one.

Below, the queue sorted by each candidate rule. Base UI against hand-rolled.

Decided · 2026-08-15 Behaviour test. A new component is built on Base UI when it needs managed focus, portalling, or an ARIA relationship beyond a label. Everything else is hand-rolled. This is the rule new proposals are checked against.

D3 · positioning-rule

Two positioning systems

This is the sharpest conflict in the proposal. The system has a standing rule that overlays use native CSS anchor positioning and the Popover API, with no positioning library and no fallbacks — that is how Tooltip is built. Base UI positions its overlays with @floating-ui/react-dom, which is a positioning library, and it is not optional: it is a hard dependency of the package.

Since Tooltip is explicitly not being refactored, some version of "two systems" is unavoidable. The decision is whether that is a stated rule or an accident.

Decided · 2026-08-15 Scope the rule by origin. The native anchor-positioning rule applies to hand-rolled overlays; Base UI overlays use Base UI's own positioning. Both are correct, and neither is debt. Tooltip is not booked for migration.

D4 · version-pin

How the version is ranged

Base UI is stable and actively maintained. 1.0.0 shipped on 11 December 2025 and it has released a minor roughly every month since, reaching 1.7.0 on 4 August 2026. Under semver that means minors are additive and the caret range is doing what it was designed for — so this is a straightforward question about how quickly we want other people's changes to reach our consumers, not a question about risk in a pre-release.

Release history — @base-ui/react, npm registry, 2026-08-15

Exact pin

package.json

"dependencies": {
  "@base-ui/react": "1.7.0"
}

every install, every consumer,
byte-identical until we change it
  • A design system is a compatibility promise. What we tested is exactly what every consumer runs.
  • Upgrades become a deliberate, reviewable change with a changeset attached, and Storybook is the place they get checked.
  • Roughly monthly upgrade chores, and consumers cannot pick up a Base UI fix without a release from us.
  • Two copies in the tree get more likely, since an exact pin cannot dedupe with a consumer's own caret range.

Tilde range

Recommended

package.json

"dependencies": {
  "@base-ui/react": "~1.7.0"
}

takes 1.7.1, 1.7.2, …
holds at the 1.7 minor
  • Patches reach consumers without a release from us, which is the case where waiting on us has no upside for anyone.
  • Minor upgrades stay deliberate and reviewable, so new behaviour never arrives unannounced.
  • Dedupes with a consumer already on ~1.7.x or ^1.7.x, softening D1's two-copies problem.
  • Still a roughly monthly decision to take the next minor.
  • Rests on the publisher's semver discipline: a patch that changes behaviour reaches consumers unreviewed.

Caret range

package.json

"dependencies": {
  "@base-ui/react": "^1.7.0"
}

picks up 1.8, 1.9, … automatically
dedupes with the consumer's own copy
  • Dedupes with a consumer already on Base UI, which is the practical fix for the two-copies problem.
  • Fixes reach consumers without a release from us.
  • A monthly minor we have never seen can change behaviour underneath our components, and the bug report arrives at us.
  • Our Storybook and a consumer's app can be running different Base UI versions, so visual review proves less than it appears to.
Decided · 2026-08-15 Tilde range, ~1.7.0. Patches flow to consumers; minors are taken deliberately.

Reviewer's note, verbatim: "I do want to pin to a version for stability, but I think you have old info or are looking at teh wrong package. The most recent release of @base-ui/react is 1.7.0 and is only 12 days old." Then, on the amendment: "First adjust to ~1.7.0 to allow for patches. That's reasonable and safe."

This decision was amended the same day it was made. It first came back as an exact pin, decided against a draft that had the wrong package — see the correction notice in section 01. The draft's argument for an exact pin was that a pre-release makes no compatibility promise, and that reason evaporated once the real package turned out to be stable at 1.7.0 with a monthly cadence. The Tilde range option was added after that correction and the recommendation moved onto it; Exact pin is kept above as it was originally recommended, so the reversal stays legible.

03What follows

D2 puts a text input on Base UI, so decision 0002 works up Input as a wrapper over Base UI's Field and Input parts — which is what makes label, description, error and validity wiring available to it. The open forks there are the control-height ramp that Button currently dodges, how much of Field is exposed as our public API, and where validation state lives.
