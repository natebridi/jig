Jig · decision 0010

A colour axis on Typography

Typography can only render one colour. Every other shade of prose in the system is a hardcoded color: somewhere — which is now also the only way to get a link's hover wrong.

  • Built
  • 2026-08-28
  • 4 decisions

01Context

TypographyOwnProps is with, balance and the spacing props. There is no colour among them, and the recipe's base paints color.text.primary unconditionally. So Typography renders exactly one colour, and secondary, muted, accent and danger prose is reached by setting color: by hand — in a component's own .css.ts, or in a consumer's stylesheet.

That was a tolerable gap until last week. 0009 D3 decided the text Link inherits its colour from whatever encloses it, and the follow-up work added a <role>-hover token beside each of the six text roles, plus a linkHoverFor(role) helper that sets a colour and its hover pair together. A link can only hover correctly if the thing that set the colour also declared the pair.

Three Jig components declare it today — Typography (primary), Dialog's description (secondary) and Tooltip (inverse). Four do not, and two of those are prose slots that plainly carry links:

So the question is not really about hovers. It is whether the system has a supported way to say “this prose is secondary” at all. The hover pair is the thing that made its absence visible.

One complication worth stating before the options. Adorn already has a colour axis — with="muted | accent | danger", plus mono, which is a font-family switch riding the same prop. And with is also Typography's prop name, where it means a type preset. The system therefore already spells one concept two ways, and a new axis on Typography cannot be called with even if that would have been the consistent choice.

Already settled by precedent

  • Whichever option wins applies linkHoverFor automatically. Pairing the colour with its hover is the entire reason this is being proposed; it is not a fork.
  • The default is primary, which is what Typography paints today. No consumer's markup changes appearance.
  • The roles come from the existing color.text.* semantics. No new tokens — the -hover siblings already shipped.
  • The prop type is a hand-written union, not derived from the token object. Same reason the spacing props are hand-declared: a generated union renders as an unreadable blob in Storybook's docs table.
  • No change to as. Colour and semantics stay independent, exactly as with and as already are.
  • Adorn keeps its mono option wherever the colours land. It switches font family, not colour, and D4 is about the colours only.
  • @jig-ui/react is 0.1.0. A breaking rename is cheap now and will not be later.

02Decisions

Accept one option per decision, or reject the whole set and leave a note. Notes are the refinement channel — partial acceptance goes there in plain English.

All four came back accepted in one round, two of them against the recommendation — D3 took every role rather than holding inverse back, and D4 left Adorn's prop name alone. Both outcomes record what that costs and how the cost is being handled. Every option is kept, including the ones not taken.

D1 · colour-axis-home

Where a paragraph's colour comes from

Hover each link in the specimens: the first two give a link the hover that belongs to the text around it, and do so without the call site knowing that hovers exist.

A colour axis on Typography

Recommended

One prop; the hover pair rides along

Primary prose, with a link in it.

Secondary prose, with a link in it.

Muted prose, with a link in it.

Danger prose, with a link in it.

<Typography tone="muted"> · hover a link — each takes its own role's partner

  • Closes the gap for consumers, not just for Jig. Today an app that wants muted prose must write color: itself, which is precisely the case no amount of internal wiring can reach.
  • The pairing becomes impossible to forget rather than merely easy to remember: there is no way to set the colour that does not also set the hover.
  • Removes four of the seven hardcoded sites outright — Input's description and error, and CodeBlock's two, all become a Typography with a tone.
  • Typography is already the component that owns how text looks. A colour axis is less of an addition than it is a missing half.
  • A second prop that overlaps with as and with on the same component, on a signature that is currently three props wide.
  • Leaves Adorn spelling the same concept differently unless D4 also lands, which is a rename.

Make Adorn block-capable

The colour axis already exists — widen what can wear it

today — inline only
AdornElement =
  'span' | 'strong' | 'em' | 'b'
  | 'i' | 'code' | 'mark' | 'abbr'

widened
AdornElement = … | 'p' | 'div'

<Adorn as="p" with="muted">
  Muted prose, with
  <Link href>a link</Link> in it.
</Adorn>

but the type preset lives on the other
component, so both are needed anyway
<Typography with="body02">
  <Adorn with="muted">…</Adorn>
</Typography>
  • No new axis anywhere. The colour vocabulary stays in one component, which is where a reader would look for it second.
  • Adorn's colours already pair cleanly with the new hover tokens; only the element list widens.
  • Splits one paragraph's styling across two components — size and family from Typography, colour from Adorn — so the common case needs both and a nested element.
  • Adorn is built for phrases: its whole doc comment argues that as should not render “something that has no business holding a phrase”. A <div> is exactly that.
  • Still leaves Typography unable to say what colour it is, so the consumer writing plain muted prose reaches for color: anyway.

No axis; wire the call sites

Six mechanical lines, and the status quo otherwise

input.css.ts
- color: color.text.muted,
+ ...linkHoverFor('muted'),

- color: color.text.danger,
+ ...linkHoverFor('danger'),

codeblock.css.ts   x2
adorn.css.ts       x3 variants

and for anyone outside Jig
.myProse {
  color: var(--color-text-muted);
  /* nothing tells them this line
     exists, or what to set it to */
}
  • Smallest possible change, entirely mechanical, and it does fix every case that exists inside Jig today.
  • Adds no API surface, so nothing new to document, name or version.
  • Fixes the symptom and leaves the cause. Typography still cannot express a colour, so consumers still hardcode, and hardcoded text is exactly where the pairing is missed.
  • The coupling is permanent and unenforced: every future component that paints text has to remember a second line, and forgetting it produces a subtly wrong hover rather than an error.
  • Leaves the system with no answer to “how do I make this paragraph secondary”, which is a question a design system should not need a decision document to answer.
Decided · 2026-08-28 A colour axis on Typography. The recipe's base stops painting a colour; a tone variant paints it instead, and each case sets the role and its hover partner together through linkHoverFor.

The consequence worth writing down is what it removes. Four of the seven hardcoded text colours stop being hardcoded — Input's description and error, and CodeBlock's bar and label all become a Typography with a tone, and inherit the pairing rather than declaring it. What is left is Tooltip, which needs inverse on a popup that is not a Typography, and Adorn, which D4 leaves in place.

D2 · axis-name

What the axis is called

with is unavailable: on Typography it already names the type preset. Whatever is chosen here is the word the system will use for “which semantic text colour” from now on, including in D4.

tone

Recommended

Reads as a register, which is what these roles are

<Typography with="body01" tone="muted">
  A caption.
</Typography>

<Typography as="p" tone="danger">
  That card was declined.
</Typography>

the two axes read as different questions
with  → how big, what family
tone  → how loud, what register
  • Names the meaning rather than the mechanism. These roles are not colours a caller picks — danger is a register, and it is a different colour in each theme.
  • Free of collisions: no HTML attribute called tone, and it does not clash with Token's color, which genuinely names a hue.
  • Reads correctly beside with, so the two axes look like two questions rather than two spellings of one.
  • A word the system has not used before, so it has to be learned once.

color

What CSS calls it, and what Token already calls its own axis

<Typography color="muted">A caption.</Typography>

but Token's `color` names a hue…
<Token color="fuschia">   a hue
<Typography color="muted"> a role

…and the DOM has one too
<font color>  <input color>
React will not warn if it leaks
through a spread onto an element.
  • Immediately guessable. Nobody has to be told what it does.
  • Matches Token's prop name, so the system uses one word for “the colour axis”.
  • Matches Token's name while meaning something else — a hue there, a semantic role here. 0006 D2 went out of its way to keep those two ideas apart.
  • A real HTML attribute, so it has to be excluded from the spread by hand on a polymorphic component that forwards element props.

text

Names the token group the values come from

<Typography text="muted">A caption.</Typography>

traces straight to the token
text="muted"  →  color.text.muted
              →  color.text.mutedHover

but on a text component it reads as
"the text", not "the text colour"
<Typography text="danger">
  <-- looks like a content prop
  • Traceable: the prop value and the token path are the same word, so there is nothing to map.
  • On a component whose entire job is text, a prop called text reads as the content, not the colour of it. That is the sort of ambiguity that gets a prop misused once per new hire.
  • Would leave Adorn under D4 with text="muted" on an element that might be a <code>, which reads worse still.
Decided · 2026-08-28 tone. The word the system uses for “which semantic text colour”, sitting beside with for the type preset and as for the semantics — three axes, three questions.

D4 then declined to spread it to Adorn, so tone is Typography's alone for now. See D4's outcome for what that costs.

D3 · role-coverage

Which roles the axis exposes

Six color.text.* roles exist. They were not all written for prose, and exposing one that is not is how a prop gets used somewhere it cannot work. Each specimen shows the roles included and, faded, the ones left out — both themes, resting colour and hover partner.

Five — every role but inverse

Recommended

rest · hover

primaryresthover
secondaryresthover
mutedresthover
accentresthover
dangerresthover
inverseexcludedexcluded
  • inverse is the one role that is not a register but a context: it only works on an inverted surface, which the component cannot see. Offered as a tone it would look like a colour choice and produce invisible text on the body surface.
  • The other five are all legitimate on the page's own background, in both themes, with a hover partner that already exists.
  • Tooltip — the one component that genuinely needs inverse — already declares it directly in its own stylesheet and does not need a prop.
  • The axis is then not a straight mirror of the token group, so the mapping has one documented exception.

All six

rest · hover — note where inverse lands

primaryresthover
secondaryresthover
mutedresthover
accentresthover
dangerresthover
inverseresthover

tone="inverse" only works on an inverted surface like this one.

On the body surface it is this, which is nothing.

  • A straight mirror of color.text.*: no exception to remember, and no question about where the sixth went.
  • Legitimate for anyone building their own inverted panel, who currently has no way to reach the role at all.
  • Five of the six work anywhere and the sixth works in one place. That is not a set; it is five options and a trap, as the second line of the specimen shows.
  • Nothing can warn about the misuse: whether the surface behind is inverted is not knowable from the component.

Three — primary muted danger

Only the registers with an unambiguous job

primaryresthover
mutedresthover
dangerresthover
secondaryexcludedexcluded
accentexcludedexcluded
inverseexcludedexcluded
  • Three obviously distinct registers, with no pair a caller has to squint to tell apart.
  • Additive later: a role can be added to a union without breaking anyone, where removing one cannot.
  • Excludes secondary, which Dialog and CodeBlock both already use for real prose — so those sites keep hardcoding and the change fixes less than it could.
  • secondary and muted sit two ramp steps apart and are used for different things; collapsing to one loses a distinction the tokens deliberately draw.
Decided · 2026-08-28 All six roles, inverse included — against the recommendation, which was to hold it back.

The cost is accepted with it, and it is the one this option named: five of the six work on any surface and inverse works on exactly one, with no way to warn about the misuse. Whether the surface behind is inverted is not knowable from inside the component — not at render time, and not from computed style either, since the background may be painted by any ancestor. tone="inverse" on the body surface renders text the same colour as the page, which is the failure the specimen above shows.

So the guard has to be documentation, and it is being treated as part of the build rather than as a nicety: the prop's own JSDoc says inverse requires an inverted surface, and the Storybook story for it renders on color.surfaces.inverse rather than on the default canvas — showing it anywhere else would teach the mistake. Flagged because it is a resolution to a problem the option raised and did not settle.

Tooltip is not being refactored onto the prop. Its popup is not a Typography, and it already declares the inverse pair in its own stylesheet correctly.

D4 · adorn-alignment

What happens to Adorn's colour axis

Adorn colours a phrase; Typography would colour a block. They are both needed, and after D1 they would both name the same three roles — under two different prop names, because Adorn spells it with.

Adorn's with also carries mono, which is a font-family switch rather than a colour. Every option below leaves mono on with, where it belongs.

Rename Adorn's colours to match

Recommended

One word for one concept, at both scales

before
<Adorn with="muted">   a colour
<Adorn with="mono">    a family
<Typography with="body01"> a preset

after
<Adorn tone="muted">
<Adorn with="mono">         unchanged
<Typography with="body01" tone="muted">

and they compose
<Typography tone="muted">
  Mostly quiet, with a
  <Adorn tone="danger">warning</Adorn>.
</Typography>
  • One word for one concept at both scales, so a reader who learns tone on a paragraph already knows it on a phrase.
  • Untangles Adorn's with, which currently means “colour, or else a font family” — two unrelated ideas on one prop.
  • A breaking change that costs almost nothing at 0.1.0, and cannot be made cheaply after 1.0.
  • It is still a breaking change, and Adorn's colours are the only part of its API most callers use.
  • Adorn then has two style props, with and tone, where one of them holds a single option.

Leave Adorn alone

Two names, one concept

<Typography tone="muted">
  Mostly quiet, with a
  <Adorn with="danger">warning</Adorn>.
</Typography>

so `with` means, depending on where
Typography with  → a type preset
Adorn      with  → a colour or a family
Typography tone  → a colour
Adorn      tone  → does not exist
  • No breaking change, and no migration for anyone already using Adorn.
  • Defers the rename until there is a reason to touch Adorn anyway.
  • Ships the inconsistency the specimen shows, and makes it worse rather than merely inherited: today with is ambiguous, and afterwards it is ambiguous next to a clearer name for the same idea.
  • Every later decision about Adorn inherits the awkwardness, and the rename only gets more expensive.

Fold Adorn's colours in

Adorn keeps only what Typography cannot do

Adorn drops its colours entirely
AdornStyle = 'muted' | 'accent' | 'danger' | 'mono'

so a coloured phrase becomes
<Typography as="span" tone="danger">
  warning
</Typography>

which loses the semantics Adorn exists for
<Adorn as="strong" with="danger">  gone
<Adorn as="em" with="accent">      gone
  • Exactly one place in the system names a text colour, which is the cleanest possible answer to the naming question.
  • Adorn's element list — strong, em, code, mark, abbr — is the point of it, and Typography's list does not overlap. Colouring an emphasised phrase would become impossible without losing the emphasis.
  • Reduces Adorn to a single mono option, at which point it is a font-family class wearing a component.
Decided · 2026-08-28 Leave Adorn alone — against the recommendation, which was to rename. Adorn keeps with="muted | accent | danger | mono", and no caller has to migrate.

The accepted cost is that the system now spells one concept two ways: <Typography tone="muted"> and <Adorn with="muted"> mean the same thing. That is deliberate as of today, so it should not be quietly “fixed” later without a decision that supersedes this one.

One thing this decision does not cover, resolved here and flagged as carried: D4 was a question about the prop name, not about whether Adorn declares hover pairs. Its three colour variants set color: color.text.X today and nothing else, so a Link inside <Adorn with="danger"> would rest on danger and hover to primary's partner — the exact bug this document exists to remove. So Adorn's three colour cases switch to linkHoverFor internally. That is not a rename, not breaking, and not a migration, so it sits inside what “leave Adorn alone” allows — but say so if the intent was to leave it untouched entirely.

03The API, as decided

04Deliberately not proposed

  • A generated tone union. Deriving the prop type from the color.text.* object would keep the two in step automatically, and renders as an unreadable expanded type in Storybook's props table. Same reason the spacing props are hand-declared. The parity check in validate.ts is where a missing role gets caught instead.
  • Arbitrary colours. tone names a role from the semantic set; it is not a way to pass #ff0000. Anything outside the set goes through style, and takes responsibility for its own link hover.
  • A matching background axis. Inverted panels, callouts and cards are a surface question, not a type one, and would want color.surfaces.*. Worth its own proposal if wanted; adding it here would smuggle a layout decision into a typography one.
  • Removing linkHoverFor. It stays regardless. Tooltip needs it for inverse, which D3 recommends keeping off the prop, and any consumer painting their own text still needs a supported way to declare the pair.

05As built

Built 2026-08-28. Both decisions taken against the recommendation went in as accepted. One line of D1's outcome turned out to be wrong and is corrected below.

Files

  • Changed typography/typography.css.ts — colour moves off the base onto a tone variant built from linkHoverFor, defaulting to primary.
  • Changed typography/typography.tsx — the tone prop and the TypographyTone union, exported from both index files.
  • Changed adorn/adorn.css.ts — its three colour cases and mono now declare hover pairs. Prop name untouched, per D4.
  • Changed input/input.css.ts, codeblock/codeblock.css.ts — four sites wired. See the correction below for why they were wired rather than converted.
  • Changed typography.stories.tsx — Tones, InverseTone and ProseWithLinks. api.types.test.tsx — four assertions on the tone union and on Adorn keeping with.

A correction to D1's outcome

D1's outcome said Input's description and error and CodeBlock's bar and label “become a Typography with a tone”. They cannot, and they have not.

  • Input's two are rendered by Base UI as Field.Description and Field.Error, which accept a className, not a component. Replacing them with a Typography would drop the Field wiring that supplies aria-describedby and the error match — trading an accessibility guarantee for a styling tidy-up.
  • Their line-height is 1.4; caption01, the preset at the same size, is 1. Converting would have changed how every existing field renders.
  • CodeBlock's bar is a flex container holding the label and the copy button, not a run of text.

All four therefore keep their style() and call linkHoverFor, which is what actually delivers the pairing — the same treatment Dialog and Tooltip already had. The decision itself is unaffected: D1 was about the axis existing, and it exists. What was wrong was a claim about how far it would reach, and the honest count is that the axis serves consumers and new code, while these four internal sites stay wired by hand.

What the proposal got right

  • The mechanism needed no adjustment. tone maps one-to-one onto linkHoverFor, and the recipe variant orders after the base without a specificity fight.
  • Moving colour off the base changed nothing visually, because defaultVariants.tone = 'primary' reproduces exactly what the base painted.
  • D4's carried consequence — wiring Adorn without renaming it — was correct and cost three lines.

The inverse guard, as built

D3's outcome committed to documentation as the only available guard, and this is it: the tone prop's JSDoc states the precondition and why it cannot be checked, and InverseTone is the one story that renders on color.surfaces.inverse, with a caption underneath saying what happens elsewhere. No story shows inverse on the default canvas.

Worth a future proposal

  • Nothing enforces the pairing. A future component can still write color: color.text.muted and skip linkHoverFor. A lint rule — ban color.text.* outside link-hover.css.ts — would close it properly, and is a tooling decision rather than a design one.
  • Two names for one concept is now shipped, deliberately (D4). If it grates in use, the rename is the same work it was today and no more.
  • Typography still cannot invert a surface, only the ink on one. tone="inverse" needs a caller-supplied background, which is the surface axis explicitly deferred in §04.

Verification

pnpm turbo typecheck test: 12 tasks, 136 tests, all passing. Hover was measured in the browser rather than eyeballed — for each of primary, secondary, muted and danger, in both themes, the hovered lightness moves away from the surface and never matches the resting value.
