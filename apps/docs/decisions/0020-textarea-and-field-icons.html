Jig · decision 0020

Textarea, and a leading icon for fields

Jig has no multi-line field, and no field has ever carried an icon. 0002 deferred both, by name, to a later document — this is it. The two arrive together because the icon is the same slot in both controls, and a Textarea that does not match Input is not worth shipping.

  • follows 0002, 0011

01Context

Input shipped in 0002 and closed with a list of things it would not settle. Two of them are this document: “Textarea, and multi-line. Shares the colour set but not the height ramp. Separate component, separate document.” and “Adornments — icons or buttons inside the control … a question for after this ships.”

Base UI has no textarea component at ~1.7.0 — the installed package exposes input, field, number-field and otp-field, and nothing multi-line. It does not need to. Field.Control takes Base UI's standard render prop (BaseUIComponentProps in internals/types.d.ts), so render={<textarea />} swaps the element while keeping the id, aria-describedby and validity wiring that Field.Root hands out. The same Field.Root already carries data-invalid, data-disabled and data-focused on itself (fieldValidityMapping in internals/field-constants/constants.mjs), which matters for where the icon can live.

What field-sizing: content actually costs

The auto-growing textarea is now a CSS property rather than a scrollHeight listener. It is Baseline newly available as of 16 June 2026 — Chrome and Edge 123 (March 2024), Safari 26.2 (12 December 2025), Firefox 152 (16 June 2026), per web-features and MDN. That is three months old today, and newer than anything else Jig depends on. It is still consistent with the standing baseline — overlays already use native CSS anchor positioning and the Popover API with no fallback — but it is the newest thing in the system, and worth naming as such rather than discovering later.

The property also has a trap that shapes three of the decisions below. Per MDN, rows and cols have no effect on a <textarea> with field-sizing: content. So the obvious way to express “show three lines” stops working exactly where the feature works, and an empty textarea sizes to its content — one line. The floor has to come from min-height, which means arithmetic in lh units (Chrome 109, Safari 16.4, Firefox 120; Baseline since November 2023, so not the constraint).

The resize handle writes an inline height

resize: vertical and field-sizing: content are not independent. Dragging the grip sets an inline height on the element, and an explicit height re-imposes fixed sizing — MDN's own advice is to “avoid setting fixed width and height” for this reason. Measured, on the same md textarea:

A one-line textarea does not match an Input by default

0002 D1 tokenised size.control.{sm,md,lg} precisely so a bordered control lines up with a Button beside it, and 0006 had Token subtract from the same values rather than declare its own. A textarea's height is not fixed, but its block padding still decides where its first line of text sits — and whether a one-line box agrees with an Input. Already settled by precedent

Everything here follows an existing rule and is not up for debate in this document.

  • Built on Base UI's Field, composed internally. 0001 D2; 0002 D2 made “props on one component” the standing rule — ease of use beats expressiveness at our layer, because the expressive layer already exists underneath.
  • Validity comes from Base UI. error sets Field.Root invalid as true | undefined, never false; the stylesheet reads [data-invalid]. 0002 D3, and the as-built note.
  • Colours are color.control.*. The set is shared by every field-like control by design — no new semantic group. 0002 D4.
  • Focus highlights the border, not focusRing. A bordered control matches :focus-visible on click as well as on keyboard focus; spreading the ring would double-paint. 0002 D4.
  • label, description, error, disabled, name behave exactly as on Input, and className / style land on the field wrapper — it is the element the parent layout sees.
  • Sizes are sm | md | lg, matching ButtonSize, via a recipe().
  • Label, description and error styles are re-exported from input.css.ts, the way combobox.css.ts already does. No shared field module is extracted here.
  • The icon is icon?: IconName from the curated set, sized by the component, not the caller. Button set that shape (buttonIconSize); a field's icon is 1.15em, the value Combobox and Token already use.
  • The icon is decorative and non-interactive — aria-hidden (Icon's default when no label) and pointer-events: none, so it never steals a click meant for the control. Leading edge only; no iconPosition.
  • No as prop, so <Input as="textarea"> is not on the table. Polymorphism stays on layout, typography and ListItem (0014 D2).
  • No spacing props; width goes through style on the wrapper.
  • Native-attribute collisions are omitted from the inherited props, as size already is on Input. For a textarea that means rows and cols — which field-sizing makes inert anyway.
  • ref forwards to the rendered element — HTMLTextAreaElement — enforced by refs.test.tsx.
  • Horizontal sizing is unchanged. width: 100% stays on the control, so only the block axis is content-sized.

Specimens below are built from the real token values and follow this document's light/dark theme. The textareas are live <textarea> elements with real field-sizing: content — type in them. They render in this document's system sans rather than Work Sans, so letterforms are indicative only.

02Decisions

Accept one option per decision, or reject the whole set and leave a note. Notes are the refinement channel — partial acceptance goes there in plain English.

D1 · component-shape

One component or two

A multi-line field shares Input's label, description, error, colour set and size ramp, and differs in three props and one element. That is close enough that a multiline flag on Input is a genuine option rather than a straw man — and it is how several systems ship it. The cost lands in the type surface: the element under the props changes, so InputHTMLAttributes, the ref type, and the three textarea-only props all have to correlate on one boolean.

A separate Textarea

Recommended

Two components, two flat prop types

<Input label="Subject" icon="pencil-simple" />

<Textarea
  label="Release note"
  icon="pencil-simple"
  lines={3}
  description="Markdown is fine."
/>

InputProps    extends Omit<InputHTMLAttributes, 'size'>
TextareaProps extends Omit<TextareaHTMLAttributes,
                          'size' | 'rows' | 'cols'>
Release note
Markdown is fine.
  • Each prop type describes one element. No conditional props, no ref that changes shape with a boolean.
  • Autocomplete offers lines only where it means something, and never offers type="email" on a textarea.
  • One component per element is what every other Jig component does.
  • Two entries in the barrel and two stories files, for a component that is largely Input with a different element.
  • Shared chrome is duplicated by re-export rather than extracted, so a change to the field wrapper is a change in two files.

Input multiline

One component, a discriminated union

<Input label="Subject" icon="pencil-simple" />

<Input multiline
  label="Release note"
  icon="pencil-simple"
  lines={3}
/>

type InputProps =
  | ({ multiline?: false; ref?: Ref<HTMLInputElement> }
      & Omit<InputHTMLAttributes, 'size'>)
  | ({ multiline: true; lines?: number; maxLines?: number;
       ref?: Ref<HTMLTextAreaElement> }
      & Omit<TextareaHTMLAttributes, 'size'|'rows'|'cols'>)
Release note
  • One import, one mental model, one stylesheet. The shared chrome cannot drift.
  • Switching a field from one line to many is a one-word change at the call site.
  • The union is load-bearing and hostile to spread props: <Input {...props} /> where props is a variable no longer narrows, which is exactly how form libraries call it.
  • Every future field-like control has to decide whether it also collapses into Input. Combobox already decided not to.
  • It is a breaking change to a shipped component's exported type, not an addition.
Decided · 2026-09-13 A separate Textarea. Two components, two flat prop types. TextareaProps extends Omit<TextareaHTMLAttributes, 'size' | 'rows' | 'cols'> and its ref is an HTMLTextAreaElement; InputProps is unchanged apart from the new icon.

Input's exported type therefore stays additive — the leading icon is the only thing that changes about it, which is what keeps D2's regression surface as small as it is.

D2 · icon-slot

Where the leading icon sits in the box

This is the change to Input, and the Textarea inherits it. Today the <input> is the bordered box: input.css.ts puts the border, background, radius, height and all four state colours on the control itself. Combobox could not do that — it has chips and a caret in the box — so combobox.css.ts moved the border to a wrapper and left the input bare. A non-interactive icon can go either way, and the choice decides whether a shipped stylesheet gets restructured.

Both specimens are live and both have resize: vertical. Look at where the grip sits.

Overlaid icon

Recommended

The control is still the bordered box

<Field.Root class=field>
  <Field.Label />
  <span class=slot>              position: relative
    <Icon class=glyph />         position: absolute
    <Field.Control class=control/>  border, lead padding
  </span>
</Field.Root>
Search issues

grip sits in the real corner

  • input.css.ts's control recipe is untouched — border, hover, focus, [data-invalid], [data-disabled] all keep working on the element they already target. The change is one new class and one padding variant.
  • The resize grip is on the bordered element, where a native textarea puts it. In the wrapper option it floats one padding step inside the border.
  • One offset expression, calc((size.control.X − 1.15em) / 2), centres the icon on a single-line control and on a textarea's first line — provided D5 derives the block padding.
  • The leading padding is a calc that has to stay in step with the icon size; change one and you must change the other.
  • Two field-like controls now build their box two different ways, which a reader has to notice.

Wrapper owns the border

The shape Combobox already ships

<Field.Root class=field>
  <Field.Label />
  <span class=control>            flex, border, padding
    <Icon class=glyph />         a flex item
    <Field.Control class=input/>    border: none, padding: 0
  </span>
</Field.Root>

grip floats inside the border

  • Every field-like control builds its box the same way, and the icon is a real flex item — no calc, no overlap to reason about.
  • Trailing adornments, a clear button, a character count all drop straight in later.
  • The state colours can key off Field.Root's own data-invalid / data-disabled / data-focused, so no :has() sniffing is needed.
  • Restructures a shipped component: the <input> stops being the bordered element, and every rule in input.css.ts's control recipe moves. That is the whole regression surface of 0002, re-opened for an icon.
  • The resize grip renders inside the padding rather than on the border, which reads as a misalignment on every multi-line field.
Decided · 2026-09-13 Overlaid icon; the control keeps its border. A position: relative slot wraps Field.Control, the Icon is absolutely positioned inside it at calc((size.control.X − 1.15em) / 2), and the control gains a leading-padding variant of calc(spacing.X + 1.15em + gap).

input.css.ts's control recipe is not restructured: border, hover, :focus, [data-invalid] and [data-disabled] keep targeting the element they already target. Jig now builds a field box two ways — overlay here, wrapper in combobox.css.ts — and that split is deliberate: a wrapper is unavoidable where the box holds interactive children, and unnecessary where it holds a decorative glyph. Whoever adds a trailing or interactive adornment inherits that line and should re-read it before crossing it.

D3 · growth-envelope

How far the box is allowed to grow

lines defaults to 3 and becomes min-height; that much is forced by the measurements above. The open question is the other end. A field that grows without limit will, given a pasted changelog, push the submit button below the fold — and the user cannot shrink it back if D4 lands on resize: none. A cap turns unbounded growth into a scroll, at the price of another prop.

All three specimens are live. Paste a dozen lines into each.

lines + maxLines

Recommended

lines={3} maxLines={6}

lines?: number     // default 3
maxLines?: number  // no cap

H = size.control.X
min-height: calc(H + (n-1)*1lh)
max-height: calc(H + (m-1)*1lh)
// n = lines, m = maxLines

floor 3 · cap 6

  • Both ends of the envelope are expressed in the same unit, by the same formula, and read the same way at the call site.
  • The cap also bounds a manual drag, because max-height clamps an inline height.
  • Unset by default, so nothing changes for a caller who does not want a cap.
  • Two props where one might do, and a caller can set maxLines below lines — CSS resolves that in min-height's favour, silently.

lines only

lines={3} — no cap

lines?: number     // default 3

H = size.control.X
min-height: calc(H + (n-1)*1lh)
// no max-height: the page
// scrolls, not the field

floor 3 · no cap

  • One prop, one number, nothing to get wrong. The whole value is always visible — no nested scroll region, which is the better accessibility default.
  • Smallest API to extend later; maxLines can be added without breaking anyone.
  • A long value walks the rest of the form off the screen, and the component offers no way to prevent it.
  • Every consumer that needs a cap reaches for style={{ maxHeight }} and has to redo the lh arithmetic by hand.

lines takes a range

lines={[3, 6]}

lines?: number
     | [min: number, max: number]

// 3       -> floor 3, no cap
// [3, 6]  -> floor 3, cap 6

floor 3 · cap 6

  • One prop holds one concept — the envelope — and the ordering makes an inverted range obvious at the call site.
  • A tuple prop is a shape nothing else in Jig uses, and it reads worse in Storybook's controls and in autodocs than two numbers.
  • lines={[3, 6]} allocates a new array every render, so a memoised consumer sees a changed prop on every pass.
Decided · 2026-09-13 lines + maxLines. lines defaults to 3 and sets min-height; maxLines is undefined by default and sets max-height. Both are calc(size.control.X + (n − 1) * 1lh), which D5 makes exact.

The known sharp edge stands as argued: maxLines below lines resolves in min-height's favour, silently. Worth a dev-time warning through dev.ts rather than a runtime clamp, so the CSS stays the single source of the geometry.

D4 · resize-vs-grow

What the resize grip is allowed to do

Vertical resize and auto-growth are both wanted, and the platform does not let them coexist: the grip writes an inline height, and from that moment the box is fixed — measured above, 120.00px through seven more lines of typing, and nothing ever clears it. So this is not a styling detail, it is a choice about which of the two behaviours a field has after the first drag.

It is not as bad as it sounds: whatever envelope D3 sets clamps the drag too, so a user can only pick a height within the range the component already allows.

resize: vertical, drag wins

Recommended

Grow until someone says otherwise

resize: vertical;
field-sizing: content;

// min-height / max-height
// clamp the drag as well

auto-grows · drag to override

  • Explicit user intent beats an automatic default — someone who drags a field to a height has said what they want.
  • No new prop, and the behaviour matches what people expect of a textarea on the web.
  • The drag is bounded by lines / maxLines, so it cannot escape the component's envelope.
  • The auto-growth is silently gone afterwards, with no affordance to restore it.
  • A stray one-pixel drag has the same effect as a deliberate resize.

A resize prop

resize?: 'vertical' | 'none', default 'vertical'

resize?: 'vertical' | 'none'
// default 'vertical'

<Textarea label="Note" />
<Textarea … resize="none" />

same field, both settings

  • A form that must not reflow can turn the grip off; everyone else gets the default the ask specified.
  • Purely additive — a caller who never passes it sees the recommended behaviour.
  • A third sizing prop on a component that already has lines and maxLines, for a distinction most callers will never think about.
  • Invites resize="horizontal" and "both" as follow-up requests, which the ask explicitly rules out.

resize: none

The component owns the height, always

resize: none;
field-sizing: content;

// growth is the only thing
// that moves the height

grows · cannot be dragged

  • One height model, never two. The field is always exactly as tall as its content within the envelope, in every session and on every device.
  • Nothing can put the component into a state it cannot get out of.
  • Removes an affordance people expect, and the ask asked for vertical resize.
  • A touch user has no grip anyway, so this only takes something away from pointer users.
Decided · 2026-09-13 resize: vertical, fixed, with no prop — the drag wins. Auto-growth runs until someone drags the grip, at which point the inline height the browser writes takes over permanently.

Accepted with the measured consequence in view: nothing restores the growth afterwards. What makes it safe is that the drag cannot leave the envelope — min-height and max-height from D3 clamp any specified height — so the worst case is a field parked somewhere between lines and maxLines. The stories should show that explicitly, because it is the one behaviour of this component that a reader cannot infer from the props.

D5 · block-padding

Where the first line of text sits

Input declares a height and lets the browser centre one line inside it. A textarea has no height to declare, so its block padding is what puts the first line somewhere — and that decides whether a one-line Textarea agrees with an Input beside it, and whether the icon offset from D2 is one expression or two.

Each specimen puts a real <input> next to a one-line textarea at sm, where the disagreement is largest.

  • Collapses the line-count floor to size.control.X + (lines − 1) × 1lh: one control, plus a line for each line after the first.

  • It depends on line-height, so changing the textarea's line-height silently moves the padding.

Decided · 2026-09-13 Derived from size.control: padding-block: calc((size.control.X − 2px − 1lh) / 2), with the inline padding staying Input's. A one-line Textarea is a control height at all three sizes — measured 27.05 / 38.55 / 42.40px against Input's 27.04 / 38.55 / 42.40px.

This is the decision the other two lean on, and it is now load-bearing: it is what collapses D3's floor to size.control.X + (lines − 1) × 1lh and what lets D2 use one icon offset for both controls. Like Token's subtraction in 0006 D1, it is composed in the component layer rather than tokenised — so textarea.css.ts joins token.css.ts as a file that breaks if size.control moves, and it also breaks if the textarea's line-height moves. Both dependencies belong in a comment at the declaration.

03Deliberately not decided here

  • Trailing and interactive adornments — a clear button, a password reveal, a unit suffix. All of them are focusable or clickable, which raises questions about tab order and hit targets that a decorative leading icon does not. If D2 lands on the wrapper they become cheap; if it lands on the overlay they need their own document either way.
  • A shared field module. With Input, Combobox and now Textarea re-exporting field, label, description and error from input/input.css.ts, the case for extracting them is stronger than it was at two consumers. It is still a refactor of shipped code, and it should not ride along inside a new component.
  • Whether Combobox adopts the same icon slot. It has the room and it is the same visual. It also has chips and a trigger, so its box is the one place the wrapper is not optional.
  • Character counts, maxLength affordances and autosize-on-paste animation. Behaviour on top of the control, not part of it.
  • A JavaScript fallback for field-sizing. Not proposed: the property is Baseline, and Jig's standing position is native CSS with no fallback — overlays already rely on anchor positioning on the same terms. Recorded here so that it is a decision rather than an oversight.

One-line Textarea against Input, at a 16px root: 27.05 / 38.55 / 42.40px against 27.04 / 38.55 / 42.40px — the same 0.02 / 0.00 / 0.00px deltas the proposal predicted. The derived block padding computes to 3.68 / 7.42 / 6.65px, as tabled.

D2's single offset expression also holds where it mattered most, which the specimens could not show: the glyph's centre sits on the first line box's centre to within 0.01px, and stays there as the box grows from 82px to 234px. On Input it centres to within 0.01px at all three sizes, with the icon-to-text gap landing on spacing.200 (4.49px) and spacing.300 (7.21px) exactly.

D4's mitigation is now measured rather than reasoned. On a field with lines={2} maxLines={5}: an inline height: 400px — what a long drag writes — renders at 125.43px, the cap; an inline height: 10px renders at 60.27px, the floor. The drag genuinely cannot leave the envelope.

Found in the build — D1 is load-bearing for a reason the proposal did not give Field.Control's props are typed for the <input> it renders by default, and render does not re-type them.

The proposal treated render={<textarea />} as a clean element swap. It is, at runtime — Base UI's state attributes survive it, and the built component carries data-invalid on the <textarea> exactly as Input does on its input. But the prop type is BaseUIComponentProps<'input', State>, so every handler on TextareaProps carries an HTMLTextAreaElement where Base UI declares an HTMLInputElement, and tsc rejects the spread outright: 

Type 'ClipboardEventHandler<HTMLTextAreaElement>' is not
assignable to type '(event: BaseUIEvent<ClipboardEvent<
HTMLInputElement>>) => void'.

Resolved with one cast at that boundary, props as ComponentProps<typeof Field.Control>, so the props still travel through Field.Control and Field's own value tracking (filled, dirty) keeps working. Putting them on the render element instead would type cleanly and quietly bypass that.

This is a fact about D1 the document did not have. D1 was argued on the consumer's type surface — spread props, narrowing, autocomplete. It turns out a second, harder reason points the same way: one component covering both elements would need this cast and a discriminated union on top of it, with a single ref and a single set of handlers straddling two element types. The recommendation was right; one of its strongest arguments was not in the document.

Smaller gaps in the proposal
  • The line count could not be a createVar(). lines and maxLines are runtime numbers, and assigning a generated variable name inline needs @vanilla-extract/dynamic, which the package does not have and which 0001's posture argues against adding. The envelope therefore uses hand-written custom properties — --jig-textarea-height, --jig-textarea-lines, --jig-textarea-max-height — following Combobox's --jig-combobox-min-width.
  • The two ends of the envelope are not symmetric, and cannot be. The floor is a count the stylesheet does the arithmetic on (calc(var(--jig-textarea-height) + (var(--jig-textarea-lines, 3) - 1) * 1lh)). The cap cannot be, because absence of a cap has to reach CSS as max-height: none, and no arithmetic produces none. So the component hands over a whole value and the stylesheet falls back: max-height: var(--jig-textarea-max-height, none). Relying on an unset variable to invalidate the declaration would have worked by the same mechanism combobox.css.ts already warns about — and for the same reason, it is not what shipped.
  • The leading padding had to be a compound variant, not a hasIcon style. The size variants declare padding as a shorthand and recipe variants are emitted in declaration order, so a paddingInlineStart inside hasIcon is overwritten by whichever size follows it. Compounds are emitted last. Button's iconOnly padding is compounded for exactly this reason; the proposal presented it as a single padding variant.
  • The growth cannot be tested in jsdom, and pretending otherwise would be worse than not testing it. jsdom implements neither field-sizing nor lh, so a height assertion there measures jsdom's zeroes. The suite asserts the custom properties that produce the envelope; the geometry is asserted in the browser, and the numbers are in this document.
  • The maxLines < lines warning went to dev.ts as the outcome asked, and is covered both ways — it fires when the envelope is inverted and stays silent when it is not.
Worth its own proposal
  • The field module, now at three consumers. textarea.css.ts re-exports field, label, description and error from input/input.css.ts, joining combobox.css.ts — and it now also re-exports slot, glyph and fieldIconSize. That is six names travelling by re-export from a file named after one component. 0020 §03 left extraction out of scope at two consumers; at three, with the icon slot added, it is the next thing to do.
  • Nothing in the system stops a decorative icon from being the only label. icon is aria-hidden and label is optional, so <Input icon="magnifying-glass" /> type-checks and renders a field with no accessible name at all — which was already true before this change, and which the icon makes more tempting. A dev.ts warning, or a type that requires one of label / aria-label, is a small decision that would cover every field-like control at once.
