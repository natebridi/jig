Jig · decision 0018

Structured List, revised

Three changes to a component built yesterday: the type prop moves to the cell, rows become flex so columns can be given widths, and a cell should be able to take its label from the header above it. The first is small. The other two each need a mechanism Jig does not have yet.

  • Built
  • 2026-09-07

01Context

This supersedes parts of 0017, which is Built. Specifically: D4 put with on the list and this moves it to the cell; the rows were built as grids sharing one template and this makes them flex; and D2's contract — a label written on every cell — becomes a fallback rather than the only route. 0017's own decisions stay readable as they were made; nothing in it is edited.

Two of the three were already on 0017's list of open questions. Its As built recorded that “a context would make the count, the column labels and the cell-position checks exact — and Jig still has no context anywhere, which is a decision worth making deliberately rather than by accumulation”, and that “nothing validates cell order”. D3 below is that decision arriving.

What the codebase has, and has not

The rule D2 runs into

The checklist is explicit: “Other components get spacing from their parent, and box dimensions go through style, not props.” A width prop on a cell is exactly what that forbids. One option below amends the rule the way 0014 D2 amended the as rule — deliberately and in writing — and the others work within it.

Worth being clear about why flex changes anything. Grid rows shared one template, so a column width was declared once and every row obeyed it. Flex rows each lay out independently, so alignment is no longer structural: it holds only while every row's nth cell resolves to the same width. That is the property D2 is really choosing how to preserve.

Already settled by precedent

  • The ARIA roles do not change. role="table", rowgroup, row, columnheader, cell on plain elements, emitted by the components and never accepted from a caller (0017 D1). Flex does nothing to them — the roles were chosen precisely so layout could move.
  • The stacked layout still moves the header row off-screen rather than removing it, and the visible per-cell label stays aria-hidden (0017's As built). Whatever D3 chooses, that is about where the label's text comes from, not whether it is announced.
  • layout stays a caller-set Responsive prop with the same default (0017 D3). Both marker branches must keep declaring the same property set — the bug 0017's As built records.
  • Headings keep taking their preset at weight 600 rather than a quieter one (0017 D4). Only which preset, and where it is set, is open.
  • Three components, one folder, full names on each. No as prop; consumer props reach the root; refs type to the rendered element.
  • No new tokens and no new dependency — every value here is an existing spacing step or type preset.

D1 · type-scope

Where the type prop lives

The brief: “the use case is for individual columns/cells, not primarily the whole list”. Primarily is the word doing the work — a cell-level prop is wanted, and whether a list-level default survives beside it is the question.

The per-column option was declined, so a column whose cells are set to something else will have a heading that does not match them — a mono column under a sans heading, say. That is now a known and accepted mismatch rather than an oversight; the caller's route is to set the list's with to whatever the headings should be.

D2 · column-widths

How a column gets a width

Flex rows are the ask. The consequence is that alignment stops being structural: grid rows shared one template, flex rows each resolve independently, and the columns only line up while every row's nth cell comes out the same width. So the real question is where that width is declared, and the checklist rules out the most obvious answer — box dimensions go through style, not props.

  • Keeps alignment structural in the only way flex allows: one declaration, applied to every row's nth cell, so rows cannot drift apart.
  • Stays inside the checklist — a column width is a property of the list's shape, not a box dimension on a component.
  • Reads like the thing it replaces. ['9rem', 'auto', '6rem'] is a track list by another name, so nothing is lost from the grid version.
  • Positional, and 0017 rejected its hybrid option for being positional. The mitigation is that this is one array on the parent rather than a per-row correspondence, so there is one place to get it wrong instead of one per row.
  • A new prop whose values are CSS lengths, which is the thing the checklist is nervous about even if it is not literally a box dimension.

Decided · 2026-09-07 columnWidths, an array on the list. Rows become display: flex with a column-gap; cells default to flex: 1 1 0 with min-width: 0, and columnWidths overrides that per column position. Values are flex shorthands or lengths — ['4.5rem', 'auto', '3rem'] reads as the track list it replaces.

D3 makes this simpler than the option described. The specimen implied position-based CSS — nth-child rules generated up to some bounded column count. With context accepted in D3 the cell already knows its own index, so it can read columnWidths[index] and set its own flex directly. No generated rules, no upper bound on columns, and the two decisions compose rather than stacking two mechanisms. Build it that way.

The costs recorded stand. Alignment is no longer structural — it holds because every row's nth cell resolves to the same width, not because they share a template — and the mapping is positional, which is what 0017 rejected its hybrid option for. The mitigation is that this is one array on the parent rather than a per-row correspondence. columnWidths applies only in the column layout; stacked rows are unaffected.

D3 · label-source

How a cell learns its label

The ask: a cell should take its label from the header above it, with label only as an override. Today it is required on every cell — the duplication 0017 D2 accepted and its As built flagged twice.

For a cell to find its own header it needs two things it does not have: the list's headers, and its own column index. Both live above it. The three ways to get them down differ in what they cost the rest of the system.

label="..." still wins when given
  • Exact. The cell's index comes from the row that actually rendered it, so the label cannot drift out of step with the column the way a hand-written one can.
  • Survives everything cloning does not — fragments, map, a caller's own wrapper component around a cell.
  • Makes 0017's open question about cell-order validation answerable: with the index known, a mismatched label override becomes a precise warning.
  • The first context in Jig. Nothing in the library holds state above its children today, and adding one sets the precedent for every component after it.
  • Three components become coupled through an invisible channel — a cell rendered outside a row silently gets no label rather than failing.

  • Precedented — Tooltip already clones the child it is given to attach handlers and an anchor name.
  • No new state mechanism, and the injection is visible in the component that does it rather than hidden in a provider.
  • Fragile in exactly the ways 0017's As built already recorded for its best-effort child introspection: a fragment or a wrapper defeats it, and it fails silently.
  • Two levels of cloning is more machinery than a context, not less — and it rewrites the caller's elements rather than reading from above them.

  • Nothing new to build, and no new coupling between the three components.
  • Everything about a cell is visible at the cell — nothing arrives from a channel the reader cannot see.

Decided · 2026-09-07 React context — the first in Jig. The list provides its headers and columnWidths; the row provides each cell's index; the cell reads headers[index] for its label and columnWidths[index] for its width. An explicit label still wins when given, which is the brief.

This sets a precedent, and the precedent is the point of the decision. Nothing in the library has held state above its children until now. The rule this establishes: context is for a component family whose parts are meaningless apart — list, row, cell — and never for passing configuration between components a consumer composes freely. A future component wanting one should have to clear that bar.

Two things 0017 left open become answerable and should be built now that the index is known: a label override that matches no header is a precise warning rather than a guess, and cell order can finally be validated — the failure mode 0017's As built recorded as impossible to catch, where a row whose cells are ordered differently from the headers looks correct wide and is mislabelled stacked.

The cost accepted with it: a cell rendered outside a row gets no label and no width rather than failing loudly. That should be a development warning too.

D3 deleted more than it added

The context was accepted to solve one problem — a cell finding its label. It removed three other things on the way, none of which the decision anticipated:

  • The columns prop is gone. It existed only to feed the grid's template a count when headers could not supply one. Flex rows need no count, so it had nothing left to do.
  • So is cellsInFirstRow. 0017's best-effort walk through the list's grandchildren, guessing a column count from the first row, deleted outright.
  • The row-count warning became exact. It used to introspect children from the list; the row now knows its own cell count and reads the expected one from context, so it is a comparison of two numbers rather than a guess that bailed on fragments.

That is the argument for context stated better than the decision stated it: not that it makes the label possible, but that it makes the component stop guessing.

What the build corrected

  • flex: 1 1 0 does not parse everywhere. A unitless zero in the flex shorthand is rejected by some CSS parsers — jsdom's among them, which is how it surfaced: the value went in and came back as an empty string. toFlex emits 1 1 0% instead, which is identical in layout and parses everywhere. Verified in a real browser afterwards, where the computed values are 0 0 10rem, 1 1 0%, 0 0 8rem.
  • The context value needed | undefined written out. Under exactOptionalPropertyTypes an optional property and one explicitly typed | undefined are different things, and the provider always passes both keys. The same variance rule that bit SideNavSection's ref in 0014.
  • A bare length had to mean “fixed”. The outcome said columnWidths accepts “flex shorthands or lengths” without saying what a length means. Written as a flex value, 4.5rem would be 1 1 4.5rem — a column that still grows, which is not what a track list of that shape implies. toFlex maps a bare length to 0 0 <length>, 'auto' to 1 1 0%, and passes anything containing a space through untouched.
  • Only a string heading can become a label. headers takes ReactNode, so a heading built from elements has no text a cell can safely reuse. Those columns fall back to needing an explicit label, which the prop docs now say.

What the decisions got right

D1 cost almost nothing, as predicted: the list already set type on the root and cells already inherited it, so a cell preset is one recipe variant emitted after the list's and CSS resolves the precedence. Verified in a browser — one row renders at 12.64px, 15.52px and 10.56px across three cells. And D2's outcome was right that D3 made it simpler: because the cell knows its index, columnWidths is read and applied inline by the cell, with no generated nth-child rules and no upper bound on column count.

Questions for a future proposal

  • Headings cannot follow their column's type. D1 declined the per-column option, so a column whose cells are caption02 still has a heading at the list's preset. Visible in the playground's config table. Fixing it means headers becoming objects, which is the breaking change D1 rejected — worth revisiting only if the mismatch proves to matter.
  • The context precedent now needs enforcing. D3's outcome set the bar — a family whose parts are meaningless apart — but nothing in the checklist says so. It should, or the second context will be added by analogy rather than by argument.
  • Alignment is now a runtime property, not a structural one. Rows lay out independently; they line up because every nth cell gets the same flex. Nothing catches a row with the wrong number of cells beyond a development warning, and nothing at all catches a caller who wraps a cell in their own component — the index context would be lost and the cell would take the default share silently.
